= Bitemporal full-text search: implementation plan

Full-text search over a table's documents, answered at any valid time and system time.
The behavioural specification is link:fts.allium[fts.allium].
The link:rtdb-fts-improvement-plan.md[RTDB FTS improvement plan] describes the Arrow migration and ranked query design.

== Shape

Search is a plugin behind generic extension points in the core.
The core knows only that a trie may carry *derived artefacts*: extra files built from a trie's data file or its group's data files and recorded on the relevant catalog entries.
It does not know what a search index is.

[cols="1,3"]
|===
| Core extension point | What search plugs into it

| Artefact records on `TrieDetails` (`format`, `index`)
| A record per search file carries kind `search`, the index definition's id and version, opaque statistics, and the scope.
  A shared file is recorded on every member.

| `ArtefactsAdded` and `ArtefactsRemoved` source and replica messages (`replication`)
| The index lane publishes a built search file; the leader accepts it while its trie is live and every node records it.
  The lane publishes removal of the retired file's records, and every node removes them.

| Artefact deletion in trie GC (`maintenance`)
| GC deletes a trie's artefacts before its data and meta files.
  It deletes shared files when it collects the last member.

| The artefact lane (`maintenance`)
| A deterministic job per eligible live trie or partition group lacking a file, run like compaction jobs.
  Once a definition leaves force, the lane retires its artefacts: it publishes `ArtefactsRemoved` for their records, then deletes their objects, unrecorded ones included.

| The scan accelerator (`query`)
| Before a scan opens, an accelerator may narrow `Scan.iids` to a candidate superset; the scan's resolution and `PageFilter` decide the result.
  It may also answer a `MATCH` the scan evaluates (`Scan.matches`) for the rows of whole data files, by page and row.

| Scalar functions (`plan`, `expr`, `sql`)
| `MATCH(column, query)` and `SEARCH_SCORE(column, query)`, evaluated on resolved rows with the analyzer in `rtdb-text`.

| Mutations (`sql`, `tx`)
| `CREATE SEARCH INDEX` and `DROP SEARCH INDEX` write documents to `xt.search_indexes` at their log position.
|===

Switching search off is a node option (`search.enabled`) and a Cargo feature (`search` on `rtdb-node`).
With either off, nothing builds search files and `MATCH` is evaluated by scanning, with identical results.
Trie GC deletes artefacts whatever the setting, so turning search off leaves nothing behind.

== Decisions

* *Index text runs, with where they are visible.*
  A search document is a run of one entity's versions with the same tokens in one column, with its visibility rectangles from the scan's own resolver.
* *A partition group shares one file.*
  Each tiered compaction job writes one bucket, so the lane waits until all sibling tries are live.
  It indexes eligible siblings in bucket order when their combined data fits `GROUP_BYTES` and a quarter of the node's memory budget.
  Compaction still builds search files inline for eligible outputs that cannot form a shared file based on their own key or size.
  A scan reads a shared file once and takes candidates and row-level MATCH answers from its selected members.
  If the shared file needs repair after a member's data file has been collected, the lane publishes an individual file for each surviving trie.
* *A search file only nominates candidates, and answers MATCH exactly.*
  The scan resolves each candidate's full history and `PageFilter` re-checks the predicate on the resolved row.
  A `MATCH` with a constant query in a scan predicate becomes a column the scan evaluates: from the search file of the row's data file, null included, and from the row's value where there is none.
* *A missing search file is never an error.*
  The accelerator treats it as absent and builds the trie's search file itself from the immutable data file, which is what makes deleting one always safe.
* *One analyzer feeds every format.*
  `rtdb-text` produces pre-tokenized text for Tantivy format 11 and Arrow formats 12 through 14.
  The residual predicate uses the same analyzer.
* *Paged posting blocks keep scoring windows whole.*
  The durable Arrow writer uses bounded slices of a long term's document and position buffers to write each block.
  On-demand builds materialize page-sized buffers so their individual retained memory charges cover only the allocations they hold.
  The format 11 reader retains converted Arrow batches when admitted and otherwise serves them from a temporary mapped Arrow file.
* *The artefact record locates the Arrow root.*
  Format 14 puts paths to term, posting, document and IID visibility pages in that root.
  Format 15 can inline the authenticated root in the catalog, groups compatible primaries into packs and maps logical versions to primary Arrow rows.
  See link:rtdb-fts-snapshot-native.md[the format 15 design] for the write and read paths.
  Each directory authenticates the child ranges it references.
  Ranked point scans use one frontier for persisted windows, covered live posting pages and pending candidates.
  The verifier can hand off the projected winning rows from that same snapshot.
* *Canonical inputs produce deterministic files.*
  A retry produces the same bytes for the same owner, input files and definition.
  The lane repairs supported historical formats without changing their definition version.
* *Definitions are documents.*
  `xt.search_indexes` is written by the indexer, so the definitions in force are a function of log position and readable as of any basis.

`node/tests/search.rs` holds the oracle: every accelerated query is compared with the same predicate widened so that it is never pushed to the scan, across valid and system times, over tries with and without search files, an uncovered L0 tail and live rows.

== Pack layout

Format 15 packs can span partition groups when the primary members have disjoint IID prefixes and share one recency.
The format 15 builder preserves logical row versions across primary rewrites and constructs new packs from current primary files.
An independent lifecycle for posting bytes across primary rewrites remains a separate design choice.
