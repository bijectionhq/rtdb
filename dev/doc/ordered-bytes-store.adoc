= The ordered-bytes store

RTDB serves one generic contract to its embedding host: versioned ordered bytes.
The host keeps every meaning above it: labels, worlds, indexes, catalogs and decisions are keys the host writes.
This is the layering FoundationDB uses, an ordered key-value store with conflict ranges and every data model above it.
The `rtdb.owned.*` and Bijection-specific `rtdb.v1.*` actions are retired onto this contract one family at a time.

== Operations

The wire is `rust/proto/rtdb.store.v1.proto`, served as Flight `DoAction` calls on an unscoped database route.

The release-checked contract uses one ASCII `x-rtdb-store-release` metadata value in a new Flight `Handshake` with verified credentials on a store-serving route.
The exact package version is compared byte for byte, and the successful handshake returns the linked version in the same metadata field with the session credentials and an empty response stream.
The session retains the agreement for subsequent store actions, including through the Flight gateway.
On an assigned follower or a gateway-routed fresh reader, the handshake binds the session to the exact admitted database attachment.
The gateway acknowledges a fresh handshake when the writer serves the selected fresh reader route.
After agreement, reader routes admit `Read`, `Watch` and `Rank` on that attachment.
The assigned follower reads from its locally applied cut and rechecks the assignment and the observed key generation before returning data.
An unknown or expired bearer on the assigned follower returns `UNAUTHENTICATED`, so the client can open a new release-checked session.
A store action takes its release from that session, and a release header on the action is rejected.
A listener without a linked release refuses release offers before issuing a session.
Activation requires the same exact published `store` package on both peers, RTDB's store operations using the linked implementation, and every Store client negotiating on connect, including the direct Basic-auth route.

`rtdb.store.v1.Read`:: Returns the live entries of each requested range, ascending by key, at one version.
The reply carries the serving node's clock sample at the read, `clock_micros`, so the host opens its present in the clock domain that stamps commits.
With `reverse`, each page descends by key: the limit counts from the range's end and a stopped page names its smallest key, before which the next page resumes.
A reverse read equals the ascending read at the same version reversed, for every projection and filter, so "the latest at or before" is a one-entry read and no caller inverts its keys.
All ranges of one request read the same version.
Flight verifies that every requested range has a page at the selected version of the admitted incarnation before returning Read results or handing pages to Rank.
The Default driver holds one applied view while it materializes the whole batch, including each batch issued by Rank.
A page stops at its limit and names the key to resume after.
A projection selects what each entry returns of its value: the whole value, nothing, or one byte slice at a fixed offset.
Every projection equals reading the whole value and projecting it afterwards.
A read may carry a value filter, in the wire form of Bijection's `ValueFilter`, which RTDB vendors as `rust/vendor/bijection-store-filter`.
The store runs the filter on each whole value before projecting it and returns only the entries that pass; the limit counts returned entries.
A filtered read returns exactly what an unfiltered read of the same ranges and version returns after filtering, and it still covers every key of its ranges.
Bijection defines what a filter means; RTDB only runs it next to the data.
With `arrow`, each page is one Arrow IPC stream with columns `key`, `written` and `value`.

`rtdb.store.v1.StorageSizes`:: Returns the installation-wide logical size rollup with the selected retained version and its incarnation.
An unscoped database read grant admits the projection.
Prefix-limited store grants cannot authorize the installation-wide projection.
Each bucket names one structural key family (16 or 17) and one opaque tablet, and reports the full encoded key and value byte counts of the entries visible at that cut.
Family 16 also counts its presence markers, and the reserved host partition is excluded from all buckets.
The same key contributes its replacement size once, and deletion removes its contribution.
A reopened or restored store rebuilds the rollup from its retained entries.
An increasing reconciliation epoch rebuilds the rollup from a census at a single cut, and an epoch already seen by that index lineage reuses the complete rollup.

`rtdb.store.v1.Append`:: Commits its writes and bounded-counter updates at a new version, unless a write committed after `since` intersects one of its read ranges, the clock falls outside its window, or a `Bound` leaves `[min, max]`.
A refused append names the first conflicting read range (or first failing bound) and writes nothing.
Its reads are judged first; then the writer's clock, sampled at the ordering point, is judged against the append's window `[not_before, before)`.
A sample outside it answers `outside` (early or late), writes nothing and keeps no receipt, so a retry under the same key is judged again.
Next, each `Bound { key, delta, min, max }` is evaluated at the append's version over a 64-bit signed big-endian integer stored at `key` (absent key = `0`).
If `current + delta` leaves `[min, max]` or overflows `i64`, the whole append refuses with `bound` naming that index, writes nothing, and records a receipt under its idempotency key.
Concurrent `Bound`s on the same key never add to `reads` and never conflict with each other.
A committing append receives its stamp: the clock sample in microseconds and the commit's version.
The store overwrites every stamp placeholder of the writes (16 zero bytes at a named offset of a key or value) with the stamp's encoding, micros big-endian with the sign bit flipped and then the version big-endian, so stamped keys sort in commit order.
A key placeholder lies at or past the key's partition prefix (a big-endian `u16` length, then that many bytes).
A placeholder out of bounds, over non-zero bytes or inside the prefix, a value placeholder on a delete, a `Bound` with `min > max`, a malformed or unconfined derive, and a stamped key that could land on another write's key (equal length and equal bytes outside both placeholders) are request errors, decided before anything is ordered.
An append with no writes, bounds or derived writes only validates: it is recorded at a new version with no effects, the version it answers it validated through.
Every outcome but `outside` is a receipt under the append's idempotency key, so a retry returns the first outcome: a commit with its first stamp, a conflict, a bound refusal, a claim refusal, or a validation with its version, even after a later write that a fresh judgement would conflict with.
The key belongs to its first request; another request under it is refused.
A verified unscoped writer may set `required_basis` to the earliest exact version the new effects depend on.
The resolver checks the inclusive physical floor and the existence of that version before admitting the append.
A writer detects this capability through `x-rtdb-store-retained-basis: 1` on the authenticated Flight handshake.
A committed retry answers its original outcome. Reopening a retained basis requires current admission.

`rtdb.store.v1.FenceWriter`:: Orders an installation's writer assignment on the same version line as Append.
A verified installation-wide write credential can close the installation at a higher positive epoch, or claim the initial or exact closed epoch with an opaque 16-byte writer identity.
An exact retry confirms the current fence without advancing the store.
A changed incarnation, an earlier epoch or an incompatible request at the same epoch refuses.
After installation of a fence, a new Append requires the live writer's exact epoch and identity in `writer_fence`.
An exact retry still recovers the previously ordered append's receipt.
The authenticated writer handshake advertises `x-rtdb-store-writer-fence: 1`.
A checkpoint preserves the fence at its selected cut, and a restored incarnation starts with that epoch closed for a new claim.
Fence changes produce no byte-key writes or range-watch matches.

An authenticated access probe supports checking isolation at an exact placed Store endpoint.
The caller sends the 16 incarnation bytes in the binary `x-rtdb-store-access-probe-bin` metadata of a new Flight handshake.
A verified principal denied database read access receives `PERMISSION_DENIED` with `StoreAccessDenial` in `x-rtdb-store-access-denial-bin`.
The denial binds the selected database, current incarnation and authenticated principal.
Probes issue no session.

*Derived writes.* A write may be a _derive_ (`AppendRequest.derives`, encoded by Bijection's `store_read::derive` and vendored verbatim as `rust/vendor/bijection-store-derive`), also called retire-on-write.
It names a row's derived-line manifest prefix, the lookup levels in which its previous line is found (the target world's own, then each ancestor bounded by its fork stamp), an interval `[from, to)` of the `i64` valid axis (each bound a fixed instant or the stamp's micros plus an offset, so a period bound placed as `now + d`, start or end, takes the stamp), and the row's new derived entries over that interval, or `Close` on a unit's closure, or `Purge` on erasure or expiry, or `Backfill`: a path backfill's entries for the row's history, written as given and added to the line's inventory so a purge deletes them. A `Close` and a `Purge` also name the compaction bases of the row's counted paths (`CountedBase`: the path's record identity, its value lanes, and where its bases lie), read from Bijection's catalog without reading the store.
Each entry is one of five kinds, each with one exact law:

* a _marker_ (a path or posting entry): a stamped enter where its coverage begins, and a stamped leave marker (an empty value) where an entry the new image does not re-enter loses coverage;
* a _boundary_ (counted search statistics): a stamped precomputed delta; the row contributes the boundaries of its segments that reach the line's horizon (the furthest valid instant any of its writes asserted), and the store writes exactly the difference of that set;
* an _edged_ boundary (a timeline aggregate): a record keyed by its valid-time edge, `identity ‖ ordered(edge) ‖ stamp ‖ ordinal`, `+v` where coverage begins and `−v` where it ends, so a read at instant `t` sums the records with edge at or before `t`; an erasure retracts it unless it is retained;
* a _single_ (an expiry entry): one key, deleted when its entry loses coverage;
* a _claim_ (a unique path's claimed value): an edged count, `+1` where coverage begins and `−1` where it ends, under the value's identity; once every derive of the append applied, the store sums the identity's records over the derive's levels (each inherited level's records under its own world, stamped at or before its fork) and refuses the whole append with `claimed` naming that derive when any instant of the claim's new coverage counts more than one claimant (`claim_exceeded`). It writes nothing and records a receipt. This is the one judgment a derive makes, on the filled key at ordering, so a claim over a field placed as `now + d` is judged at the value the stamp gives it.

An entry's identity may carry stamp placeholders the store fills at the ordering point, before it diffs the line.
A _key stamp_ is 16 zero bytes that take the stamp's encoding (for a commit-stamped column).
An _instant placeholder_ (`KeyInstant { offset, escapes, plus_micros }`) is 8 zero bytes that take the stamp's micros plus `plus_micros`, saturating, big-endian with the sign bit flipped: the first eight bytes of the stamp's encoding, and the order bytes of an Instant or Int64 sort key or fact cell.
Each zero byte of an instant's fill is followed by `escapes` bytes `0xff`, one per escaped segment enclosing the placeholder, so a filled key sorts where that instant does.
This is how a write whose time is acceptance-relative takes the commit's stamp, never the writer's entry instant (T7): a default-validity series `at` or timeline `validFrom`, an aggregate boundary at the stamp, or a field placed as `now + d`, wherever it sits in an ordered, claim, vector filter, spatial partition or aggregate group key.
An edged entry's values may carry _value instants_ (`ValueInstant { offset, plus_micros }`): the stamp's micros plus `plus_micros` is added to the big-endian `i128` sum at `offset` of its enter value and subtracted at the same offset of its leave value, so a maintained sum over such a field counts the stamp.
An entry carries at most one key stamp and any number of instant placeholders; each lies at or past the partition and world prefix, inside the identity, over zero bytes, apart from every other, with at most four escapes, or the derive is a request error.

At the ordering point, after the reads, the window and the bounds are judged, the store takes the latest manifest, at or below its bound, of the first level that has one, re-roots it into the target world, and applies Bijection's one total function `apply`: an entry the line already holds identically over the whole interval writes nothing, so an identical re-put emits no index key.
It stores the new manifest at the stamp, with every concrete key it wrote (markers, singles, statistics and presence deltas, claims and unretained edged records): the exact inventory a `Close` or a `Purge` deletes.
A `Close` (Bijection aggregates-close-2) deletes that inventory across every manifest version, at every stamp, retracting nothing at its own, and re-derives each named compaction base that folded some of it in without it: it reads the base (an aggregate edge's under the path's floor, or a statistics or presence path's newest), the row's line as of the base's cut, and the row's records compaction left beside the base, and subtracts lane by lane what the row folded in, through the vendored `close`. So no read at any cut, before the closure or after it, counts or reveals the closed row through a derived key, and the writer read nothing. It keeps the line's versions and stores a closed one on top; a closed line takes no further write, and a `Close` of a closed line or of a row with no line writes nothing.
A `Purge` does the same on an open line and deletes every manifest version; on a closed line it deletes only the versions, so a destruction changes no derived read. Retained edged records are never inventoried and survive both.
These are the store's only reads at ordering besides the manifests and the claims, each answered under the append's earlier derived writes; a stored record that does not match its path's lanes is a store fault (`rtdb.store/corrupt-derived-record`).
Derives apply in write order, before plain writes, and each sees the manifest left by earlier derives of the same row in the same append.
Emitted writes count toward no request size limit, and are recorded in the transaction's effects, so recovery replays them without re-deriving and a vendored upgrade never rewrites history.
A derive's entries and lookup levels share its manifest's partition prefix (entries also its world), no plain write may overlap a derive's manifest prefix, and nothing derived is returned.
*Applying a derive never changes an append's outcome*: the store reads the manifest only to emit, never to judge, and a malformed stored manifest is a store fault, not an outcome. Only the claims, judged after every derive applied, over the claimed values' records and never over a manifest, may refuse it.
Its emitted writes refuse later appends and wake watches like any other write, so conflicts and wakes are exact per row.
The store decodes no value and knows no index.
RTDB pins the vendored source by SHA-256 (`DERIVE_DIGEST`) and refuses a mismatched `derive_digest` with `rtdb.store/derive-version`.

`rtdb.store.v1.Watch`:: Reports the first version after `after` that wrote into one of its ranges, waiting up to a bounded time.
It always reports how far it inspected, so a caller resumes from there.

== Invariants

* Keys are compared bytewise and ranges are half-open.
* Append windows judge the writer's raw `source_log_time` observation, independent of the strictly increasing SQL `system_time`.
* A version is a commit position within one incarnation of the database.
  A restore or reset starts a new incarnation, and a request naming another one is refused.
* The conflict condition is range intersection only.
  A write outside every read range never refuses an append.
  The host makes labels key partitions, so a write the reader's label does not admit lies outside the reader's ranges and never refuses it.
* Validation and invalidation are the same matching: `Watch` reports exactly the versions that would refuse an `Append` reading the same ranges.
  Conflicts are judged over the stamped keys.
* *Stamp micros strictly increase along versions*, as XTDB's system time does (`TxResolver`: `max(now, latest + 1 µs)`).
  An append's time is its writer's clock sample, or one microsecond past the head's when the sample does not exceed it (`tx/src/system_time.rs`: `automatic_time`), whatever wrote the head: a store append, a v1 transaction, or a classic transaction stamped one tick past its predecessor or at a supplied time ahead of the clock.
  Whether an append is `outside` depends on that time and its window alone.
  The store decides the window and the stamp through Bijection's `fact_store::persistence::judge::admit`, which RTDB vendors byte for byte as `rust/vendor/bijection-store-judge` (pinned by SHA-256 in both repositories).
* The writer's clock never issues a sample below one it has issued, and the clock's own contract ensures it, not the appends.
  A Multi writer holds a durable clock lease (`Record::Lease { until }`), renewed on the clock's schedule and never per append: it samples only while its clock plus the drift bound is before `until`, and a successor writer starts only once its clock passes the predecessor's `until` plus the drift bound.
  The successor waits once, at takeover, and that wait depends on the lease alone, never on whether the last commits were hidden.
  A sample at or below the head's time is smoothed past it, never refused and never waited out, so the judge's regression outcome is unreachable.
* A commit's system time is its smoothed time, and so is a conflict's, a bound refusal's and a validation's record time.
  The writer samples its clock for each append at that append's ordering point, a batched group included; samples taken in one microsecond get successive times, and nothing waits.

== Atomic multi-place commits

A host transaction that spans places needs no port change: one `Append` already orders every write of every partition prefix at one stamp, judges all its read ranges together and answers one outcome.
Bijection's atomic multi-label branch landing (round-4 T2) is one ordinary `Append`.
Each replayed root's reads lie inside its own label's partitions, all of them inside the lander's, and the append's window is the intersection of the roots' windows.
Every root's writes, the landing record and the disclosure audit commit at that one stamp, or a conflict, bound refusal or `outside` writes nothing anywhere.
A lower place learns the landing only through the keys written into it: its own writes and the stamp the host turns into that place's own opaque token.

== Mechanism

The store is one relation, `store.entries`, on the main branch of the v1 branch index.
An entry's id is its key bytes and its `v` cell holds the value.
`Append` is a v1 transaction whose guards are `Guard::Unwritten { range, since }` and whose one operation is `Op::Store`, its writes, bounds and window.
The resolver judges the guards over the same branch index every other guard reads, then the window against its clock sample, which becomes the commit's system time, and then each `Bound` against the live 8-byte signed big-endian entry (absent = `0`).
It fills the placeholders and applies the stamped writes and updated bound counters as puts and deletes of `store.entries`.
A failing bound records `Outcome::Refused` with `rtdb.store/bound` and its index as a receipt under the append's key and writes nothing.
The append's smoothed time is judged by `store_judge::admit` (the vendored `judge.rs`): outside the window it answers `outside`; otherwise a write-free append validates and any other commits with stamp `{ time, position }`.
No pending timed v1 transaction blocks a store append, and no shared-main time floor raises one: each append settles at its own position.

=== Multi history reclamation

The Multi writer can order an exclusive history floor at a settled, guarded cut.
An advancing request is refused while an ordered pin, scoped hold or surviving native branch ancestry protects the affected history.
A successful reclaim authorization closes older cuts to new snapshots, range guards, watches, forks and exports.
The retained fold preserves the byte value visible at the floor, newer events and exact append receipts.
The normal checkpoint cycle publishes that fold and trims under the existing journal recovery rules.
The writer can then collect superseded manifests outside the retained checkpoint, journal and pin closure.

== Ordering ceiling and sharded resolution

An installation's appends share one version line.
Today one holder bounds ordering, resolution and its resident set (object storage is elastic).
RTDB's target splits an ordering tier from place-sharded resolvers and storage, with epoch-fenced place handoff and no change to commit order (`verification/tla/ShardedOrder.tla`).
A conflict and a validation carry no stamp, and their records take the sample as their time, as a commit does.
A write-free append is therefore not a v1 validation (`Transact::validates_only`), which answers at the acquired basis without a record: it is ordered and appended like a commit, so every append needs write access.
`Read` reads a branch view at the selected cut, and `Watch` filters the v1 change feed by key range.

Scan pushdown, columnar projection and batching are mechanism under this contract.
The host's contract suite (`fact_store::persistence::contract` in Bijection) runs one case list against this store and against its reference store.
Each must return what an unpushed read followed by host-side filtering returns.

== Positions name transactions in Default (T7)

System time strictly increases with position in the shared Default partition, classic, v1 and store transactions alike, as XTDB's does (`TxResolver`: `max(now, latest + 1 µs)`; a supplied time at or before the latest aborts with `invalid-system-time`, "specified system-time must be later than current tx").
A time basis (`TimeBasis`, a SQL snapshot token) therefore names one transaction, as in XTDB.
RTDB's own structures still name a transaction by its position, `TransactionKey.tx_id`, with its system time beside it.
The transaction buffer positions every staged event (`EventPosition { transaction, ordinal }`, `TransactionBuffer::stage_event`), and block pages and data files carry `_event_position` whenever a live table holds positioned events.
`EventHeader::written_in(key)` is the one test that an event belongs to a transaction: its position names the transaction and its system time is the transaction's.

* Replica and replay decoders check each event of a transaction's write with `written_in` (`tx/src/replica.rs`, `tx/src/replica/worlds.rs`, `tx/src/hosted_control/replay_rank.rs`); relation adoption already compares the event position's transaction.
* An ordered purge floor names its transaction: each `floors` entry is `{ handle, at, tx }`, and a replay attributes a floor to itself by `tx` (`query/src/owned_purge.rs`, `verify_purge_floors`). `owned_purge_floor` still answers the floor's system time, which bounds historical reads.
* The owned position mask names its commit by `TransactionKey` (`QueryContext::owned_position_mask`, `open_owned_*_with_position_mask`); `ReadHeldPositionPoint.v1` and `ReadHeldPositionValidDuring.v1` carry `[tx_id: i64 BE][system time: i64 BE][first masked: u32 BE]`.
* An exact Root fork (`PublishWorldCut` clock modes 10 and 12) names its publication by `[tx_id: i64 BE][system time: i64 BE]` and reads it at its own position cut (`fork_root_publication_at`).
* Search acceleration matches a candidate's winning event by its position (`_rtdb_owned_event_position`), not by its system time.
* Classic migration refuses a second committed transaction at the cut's system time, and `before` is strict by position and time.
* A capture with no replica suffix matches its parent basis by the checkpoint's source position as well as its time (`admit_capture`).
* Already position-exact: the live stage's commit-position check (`validate_append`), compaction's row heap (`(iid, system_from, position order, ...)`; an erase's same-time grouping only places rows conservatively), owned change edges (`ChangeEdgeOrder::Publication`; a time projection refuses an unexamined tie), and exact publication reads (`with_owned_transaction_cut`).
* As-of reads stay time reads: a world clock reading at system time `T`, an accepted held group at `T` and the classic Changes cursor read the state after every transaction stamped at or before `T`.
* Every world fork cut names its basis by position, a historical (as-of time) one included: a historical hold's cut is the publication its session selected (`OwnedReadSession::historical_publication`), and `OwnedForkCut::positioned_basis` always answers a `TransactionKey`, whose system time is only a coordinate (`OwnedForkCut::basis`).
  Checkpoints, suffix captures and suffix pins match it by position (`matches_fork_checkpoint`, `copy_fork_suffix`, `OwnedForkCut::matches_basis`, the agent's `SuffixCut`).

== Verification obligations (T7)

* V9′: `TransactState::resolve_store`'s clock decision equals `judge::admit(head, last, time, not_before, before, write_free)`, where `time` is the sample smoothed past the head (`automatic_time`, Verus area `system_time`).
  Control: re-adding `stamped && now == floor` must break it.
* `PositionNamedRecovery.tla`: recovery groups events by position and keeps transactions atomic (`TxAtomic`); grouping by system time with ties merges two transactions (control config).
* `WriterClockLease.tla`: samples stay monotone across takeover and restore, and the takeover wait is independent of hidden appends; fencing on the last stamp keeps monotonicity but breaks the paired-history invariant (control config).
