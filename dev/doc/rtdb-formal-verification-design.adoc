= RTDB formal verification design
:toc:
:sectnums:

== Decision and scope

RTDB's Rust-native engine should refine a reference database defined by an ordered history of atomic transaction batches.
A successful observation has to be one that the reference database permits at the observation's admitted basis.
A successful commit acknowledgement has to name an applied batch that remains recoverable under the declared provider contracts.
A maintenance transition may change the representation of the history while preserving its observable answers and the availability promised to readers and recovery.

The unit of the first assurance claim is one database and its replica and maintenance processes.
An individual SQL statement, cursor, or transaction may have a different lifetime for its read basis.
The cross-database consistency of a query needs a separate contract for the vector of bases it uses.
Consensus, physical erasure from all copies, external source effects, and broad SQL optimizer correctness are separate extensions with their own requirements.
The plan covers SQL and native entry points where they reach the same kernel effect, including any exported, admin, startup, and replay paths that can publish, open, or delete a representation.

The requirements below are proposed targets.
The status and scope of completed results live in the evidence ledger.
The unresolved product choice is the lifetime of a previously admitted read across compaction and collection.
Both a bounded lease and a coordinated pin are candidates.
A native diagnostic reproduces an open-cursor failure under explicit collection. link:rtdb-verification.adoc[Existing study brief] · link:../../verification/results/2026-11-21.adoc[Evidence ledger]

=== Key terms

[cols="1,3",options="header"]
|===
|Term |Meaning

|Commit position
|An identity in the logical order of committed batches for a database.
A source position, replica position, transaction ID, and system timestamp each have their own mapping to that order.
The mapping has to be stated and checked at the boundary that uses it.

|Admission horizon
|The prefix of committed history the engine admits a read to observe.
ERASE semantics use the admitted history.

|Requested system time
|The time coordinate at which the query asks which version of an entity was visible within the admitted history.
A fresh query for an old system time and a continuation of an already admitted read are different operations.

|Valid time
|The time coordinate to which an entity fact applies.
Validity spans use half-open intervals.

|Representation generation
|A coherent physical catalog and the immutable buffers and objects reachable through it.
Several generations can implement the same logical history.
A physical generation identifier and a logical read basis can advance independently.

|Reader entitlement
|The right to use a generation, or an independently owned immutable copy sufficient to answer the read.
A lease or pin implementation must account for active storage operations as well as the lifetime of the handle.

|Recoverable root
|A checkpoint root with the required closure of readable objects and a sufficient replay suffix.
Recovery policy determines which roots are eligible.

|Derived evidence
|An index or summary used to reduce query work while preserving the reference observation.
Its provenance determines the answers for which it can be used.
|===

== Reference semantics

=== Ordered history and transaction resolution

Let the reference history be a sequence of complete committed batches.
Each batch contains an ordered sequence of facts.
The order of two operations in one batch remains observable even when they have the same system timestamp.
Apply advances the public history as one step.
A refusal, aborted batch, or still-private tentative batch leaves the public history unchanged.

A transaction's resolving view consists of an eligible committed basis and the ordered prefix of operations already resolved inside that transaction.
A pipelined resolver may also consume staged predecessors if the publication protocol guarantees that they become exactly its committed predecessors before its effects are visible.
The protocol must discard or re-resolve dependent work if that condition ceases to hold.
The proof fixes which effects determine an eligible predecessor, including any predicate reads used to decide a conditional write.
Validation of a version alone is sufficient only when the version covers every decision input relevant to the allowed ordering.

A source receipt proves acceptance at its documented stage.
A commit receipt proves application of the admitted batch and the recovery promise stated for that provider.
The model separates acceptance, append, delivery, apply, and acknowledgement.
For any API with retry identity, a stable identity binds to one request or one durable result for its stated lifetime.
Repeated delivery of a replica record and client resubmission after an ambiguous reply have distinct identities and contracts.

=== Point and range answers

Use the following executable interface for the reference evaluator.
The actual implementation may use ordered histories, intervals, polygons, or sorted immutable files.

[source,text]
----
Admit(history, horizon) -> captured history
ResolvePoint(captured, entity, requested_system_time, valid_time) -> row or absence
ResolveRange(captured, entity, system_window, valid_window) -> visible fragments
Observe(query, admitted basis, representation) -> rows or specified refusal
----

For a point, first select the admitted prefix.
Apply the latest applicable ERASE for the entity in the captured history, respecting within-batch order.
Then select the last surviving event for that entity that covers the valid point and is visible at the requested system coordinate.
A winning PUT supplies the row and a winning DELETE supplies absence.
A prior ERASE can leave a subsequent PUT visible only under the normal time and ordering rules.
The source-to-model map must state whether committed ordering and system timestamps alone determine precedence or need an additional transaction or operation coordinate.

For a range, the returned fragments represent exactly the same answers at every included point.
They carry the identity and system origin needed by exposed projections and later visibility operations.
For each answerable point, a row origin contributes at most one visible answer for its entity.
When fragment decomposition is an implementation detail, compare the induced point observations.
When a supported projection exposes system endpoints, valid endpoints, row identity, cardinality, or order, compare those observations as required by that projection.
Half-open bounds, equal endpoints, unbounded queries, and representable extrema are part of the domain.
Treat sentinel encodings as explicit conventions in the refinement map.

Two snapshots of the same history may choose different admissible physical representations.
Equivalent representations must agree on every observable read within their shared entitlement.
For successful accelerated search, normalize the query arguments, analyzer and corpus at the same admitted basis before comparing outputs.
Correctness of cancellation and resource refusal is a separate observation from the rows of a successful result.

=== Abstraction and simulation relations

Relate an engine state to an abstract state through the applied log prefix, a coherent catalog and its live overlays, snapshots admitted to that prefix or a lawful earlier basis, and any outstanding durability and reclamation obligations.
A concrete apply step corresponds to one abstract commit, and a physical compaction or cache operation leaves the abstract history unchanged.
A staged write changes only its resolver view.
A recovery step may replay several concrete records while reconstructing the same committed prefix.
When proving a step composition, state which intermediate observations are visible and which are internal.
For concurrent models, every concrete observable trace must be permitted by the reference contract at the same declared boundary.

Record the refinement map for each component as a program definition or a reviewable table next to the model.
List the production fields that implement each abstract coordinate, the writer and synchronization point that establishes it, and the processing stage that consumes it.
Examples include authoritative term, applied position, admitted prefix, generation identity, immutable object identity, and original event order in a compacted page.
Treat a mismatch between those fields and the abstract premise as an open proof obligation until the production path establishes it.

=== Shared law signatures

The following schematic predicates identify the checks that should agree across the formal models, production contracts, and replay oracle.
The brackets around a time span denote inclusion and exclusion at its stated endpoints.
The term `required` is determined by the declared representation and fallback contract.

[source,text]
----
WholeCommit:
  visible_after = visible_before
  or visible_after = append(visible_before, one_complete_admitted_batch)

EligibleResolution:
  publish(batch, predecessor) implies
    exists legal_order where predecessor precedes batch
    and resolved(batch) = evaluate_operations(predecessor, batch.in_original_order)

StableObservation:
  entitled(handle, state) and read(handle, query, state) succeeds with answer
    imply answer is allowed by Observe(query, handle.captured_history)

TemporalPointRefinement:
  for every (entity, system, valid) in the query window,
    project_fragments(engine_range, entity, system, valid)
    = ResolvePoint(captured, entity, system, valid)

RecoverableAcknowledgement:
  commit_acknowledged(batch) implies applied(batch)
  and every supported recovered state contains batch in its committed history

ProtectedObject:
  object in required(entitled_handles, protected_operations, eligible_recovery)
    implies the exact object is readable under the provider contract

SafeReclaim:
  authorize_delete(object, epoch) implies no protected obligation needs object
  and a protection obligation cannot be acquired for that identity during deletion

DerivedQueryRefinement:
  accelerated_success(query, basis) implies
    observed_result is in the results allowed by complete_scan(query, basis)
----

The acknowledgement law quantifies over failures in the supported deployment contract.
The protected-object law distinguishes logical reachability from an available I/O path.
For progress, formulate eventual closure or reclamation as a temporal property of a service suffix in which its fairness and availability assumptions hold.
For ranked pruning, maintain a frontier that covers every qualifying row still unexamined through either a pending candidate or an unread window.
A cutoff may remove a row only once the remaining bounds and tie rules prove that the reference result has been retained.

== Requirements

Each requirement has a stable identifier and an acceptance observation.
These identifiers refine the earlier study's TX-1, SNAP-1, TIME-1, COMPACT-1, GC-1, and FTS-1.
A claim of validity is relative to the guarantees and assumptions in this document.
A claim of expressiveness requires a witnessed acceptance program for each required positive scenario and the specified outcome for each refusal.

=== Safety and refinement

[cols="1,3,3",options="header"]
|===
|ID |Guarantee |Observable acceptance criterion

|TX-1
|A complete admitted batch becomes visible as one ordered transition.
Displaced terms, sequence gaps, duplicates, incomplete batches, refusals, and private writes cannot independently advance public history.
|A transfer exposes both legs at the same basis.
A delayed record from a displaced leader leaves the applied position and rows unchanged.
Replay of an already applied record leaves the same result.

|TX-2
|Every state-dependent result is consistent with the allowed serial resolution order.
A batch resolves its own earlier operations in their original order and consumes only eligible predecessor work.
|Two conditional increments produce the outcome of two serialized increments.
A conditional operation can observe a prior operation of its own batch.
An aborted batch leaves the external view unchanged.

|SNAP-1
|Each read observes its admitted history for the promised lifetime.
The engine refuses or waits for requests beyond what the selected node can lawfully serve according to the API contract.
|A cursor opened before another commit continues to observe its original view.
A fresh admission observes the later state when the basis policy requires it.
A future basis yields the specified timeout, wait, or refusal.

|TIME-1
|Point and range reads agree with the bitemporal reference evaluation, including operation precedence, clipping, and interval endpoints.
|Open and closed history queries agree at every cell boundary in the fixture.
Same-system-time operations produce the correct final point answer in either original operation order.

|TIME-2
|DELETE changes the specified valid span from its system-time position forward where it wins.
ERASE suppresses earlier versions in a fresh view that includes the ERASE, including views asking for an earlier system coordinate.
|A historical query under a pre-erase admitted view and a fresh historical query under the post-erase horizon yield their separately specified answers.
Subsequent reinsertion is visible only in its admitted system and valid ranges.

|DUR-1
|Every successful commit acknowledgement names an admitted, applied batch and implies the specified recoverability.
A recovered durable prefix and replay suffix reconstruct the same visible history.
|Interrupt before and after append, delivery, apply, and acknowledgement.
On restart, validate returned receipts against the recovered history and compare exact rows and positions.

|DUR-2
|A root eligible for recovery names a complete, readable dependency closure plus a sufficient replay suffix.
Root selection and deletion of old checkpoints preserve at least one usable recovery path for the supported fault model.
|With a lost publication reply or omitted listing entry, recovery still finds a usable representation or retained log according to its contract.
A pending copy cannot count as a complete dependency.

|COMPACT-1
|Eligible compaction preserves every in-scope read at a fixed basis.
Publication changes the selected coverage coherently, including complete sibling groups, without hiding or duplicating rows.
|Observe the same basis before, during, and after publication of a partition group.
Compare narrow historical reads and full-range output, including an IID and valid interval on a partition boundary.

|GC-1
|A required object stays readable while an entitled reader, an in-flight operation covered by the contract, or an eligible recovery path depends on it.
A shared artefact stays alive under its declared catalog reference rule.
|An admitted read and a concurrent collector satisfy the chosen lifetime contract.
Collecting one of several catalog references leaves the shared object available to surviving members.
The last eligible removal may collect it.

|GC-2
|Deletion is authorized for the intended physical identity and remains consistent across retries, lost replies, and leader turnover.
Catalog publication, recovery roots, deletion notices, and cache invalidation preserve their ordering contracts.
|Pause deletion and change the generation before resuming.
Check that the authorized identity is the only object affected.
After interruption between physical deletion and its notice, retry converges on the same eligible state.

|FTS-1
|Accelerated MATCH yields the reference scan's qualifying rows at the same basis.
Every narrowing decision retains every qualifying visible row.
Required fallback preserves the predicate and score corpus when the underlying data is readable.
|Compare result bags and exposed temporal columns across indexed and scan-only runs, including shared files, erasures, history modes, missing files, and admission-budget fallback.

|FTS-2
|Ranked early termination preserves SQL's top results under the chosen corpus, numerical evaluation order, residual predicates, and tie rules.
|Compare top K with a fully evaluated sort for exact ties, floating-point boundaries, and multiple MATCH predicates.
If SQL defines a total tie-break order, compare the exact ordered rows.
Otherwise compare results using the orderings SQL permits.
|===

=== Progress, conditional guarantees, and contract choices

[cols="1,3,3",options="header"]
|===
|ID |Guarantee or decision |Premises and scope

|LIVE-1
|An eligible accepted request progresses to its documented result in stable service.
|The serving term stabilizes, providers keep the required data available, relevant work is scheduled fairly, and the environment eventually delivers the request and its dependencies.
Each retry policy and configured deadline defines a separate observable outcome.

|LIVE-2
|A retired generation is eventually reclaimable after its last obligation ends, and eligible deletion work eventually completes.
|Reader I/O terminates or can be drained safely, the policy resolves abandoned handles, the collector gets opportunities to run, and provider operations eventually succeed or become conclusively absent.

|OPT-1
|Client retries with the same supported identity resolve to one committed effect or a documented refusal.
A different request using that identity follows the explicit conflict rule.
|An API must define the identity domain, receipt retention, expiry, and recovery across a lost reply first.
Replica duplicate suppression is already covered by TX-1.

|OPT-2
|Physically erased material is removed from the classes of storage named by an erasure contract within its declared conditions and schedule.
|Require an inventory of logs, checkpoints, object versions, caches, replicas, exports, backups, keys, and any separately governed storage.
TIME-2 covers query semantics while this decision remains open.

|OPT-3
|Unauthorized or erased data has the declared effect on observable rows, scores, errors, metadata, or timing.
|Define observers, authorized views, permitted indirect effects, and included channels before comparing executions.
Precise query erasure under TIME-2 is one possible functional projection of this stronger requirement.
|===

Adopting a liveness requirement requires a progress witness in a representative configuration and a mutation that disables the necessary progress step or fairness assumption.
A bound on allowed clock skew, request duration, or retention capacity belongs in the product or deployment contract when a proof relies on it.
An overloaded or permanently inaccessible provider may prevent forward progress.
The safety claim under those failures is preservation of the last valid history and precise refusal or interruption where the API requires it.

== Candidate kernel and comparison

=== Mechanisms

Each mechanism is a rule a design could plausibly weaken independently.
The granularity follows which invariant must change atomically and which user observation could expose a weakening.
One Rust method may implement several mechanisms.
Several API methods may spell the same mechanism.

[cols="1,3,2,2",options="header"]
|===
|ID |Semantic transition |Why it is an independent subject of proof |Weakening or replacement to study

|M1 · Admit and apply
|Admit a record against authoritative order and term, then publish its whole applied batch at one visible boundary.
|Term and order eligibility govern which batch may advance, and the apply boundary determines what a concurrent read can see.
Their independence deserves separate weakenings even if one owner applies both.
|Advance from an unfenced source.
Treat a gap as harmless.
Allow a partial batch to become visible.

|M2 · Resolve against an eligible private view
|Resolve each operation against the chosen committed basis and the ordered private prefix, and ensure its basis remains eligible at publication.
|Two executions can publish whole batches while still resolving incompatible decisions from a stale basis.
|Compare serialized resolution, validation and re-resolution, and blind publication.

|M3 · Capture and evaluate a read
|Admit a read to a stable logical prefix and resolve the ordered facts at its requested valid and system coordinates.
|A fixed order leaves open what a bitemporal read means and how a fresh historical read reacts to ERASE.
|Conflate the admission horizon with requested system time.
Discard same-commit operation order.
Replace intervals with an equivalent persistent representation.

|M4 · Publish a complete representation
|Prepare a complete replacement and expose its covering catalog or recoverable root at the declared publication step.
Preserve the replay suffix needed to recover.
|Representations may change without adding a transaction.
Readers and recovery use distinct completeness premises.
|Expose a partial sibling group.
Publish a root before one dependency completes.
Trim the suffix before recovery can discover a usable root.

|M5 · Hold and discharge representation obligations
|Represent the right to read or recover the required objects and permit reclamation only after the applicable obligations end.
|A fully correct new representation can coexist with an older reader or recovery path that still needs the previous one.
|Compare copied data, validated leases, and coordinated pins.
Try time-based collection alone and deletion after the first shared reference disappears.

|M6 · Refine through optional evidence
|Allow a narrower candidate set or ranked cutoff only when the resulting observation equals the reference query, and apply the declared fallback when needed.
|Search can change how much of the correct underlying representation is visited.
|Omit a qualifying candidate or residual predicate.
Cut off a possible tie.
Disable optional acceleration entirely and measure which requirements remain.
|===

The minimality result is relative to the chosen requirements.
If the requirements permit scan-only MATCH and express no acceleration or cost target, M6 is a contract for an optional optimization.
Its weakening may violate correctness, while removing the optimization entirely may preserve the semantic kernel.
A cache layout, artefact layout, API spelling, worker count, or chosen lease duration requires a separate reason to appear in the minimal mechanism set.
Include a durable request identity rule only for a surface whose retry contract requires it.

=== Independent designs and common tests

Three isolated GPT-6.2 Astra designers received the same requirements brief and produced independent proposals before seeing the production source or each other's reports.
Each arrived at ordered atomic publication, a private resolution prefix, a captured read horizon separate from requested system time, and a representation boundary.
The convergence is design evidence.
Necessity comes from explicit countermodels or required programs that become unwritable.

[cols="1,2,2,2",options="header"]
|===
|Design |Resolve and publish |Read and erase |Study implication

|A
|Publish a resolved batch with a version precondition.
A serialized writer turn is another implementation of the eligibility constraint.
|Retain already-admitted handles under their entitlement.
New read admission follows the current erasure boundary according to its API policy.
|Test whether history reads remain expressible when old admissions and old system coordinates are routed separately.

|B
|Serialize resolution and durable extension.
A private list gives the resolver read-your-writes.
|A fresh old-system-time query uses the current capture.
A copied immutable answer can replace a generation pin if admission and copying establish the required ownership.
|Compare copying, holding a generation, and caching only a subset against A05 and A08.

|C
|Append resolved facts and represent historical answers with persistent interval maps.
|Use separate coordinates for the erase horizon and historical system basis.
|Check that an old root alone lacks the current horizon information needed by a fresh historical query.
|===

Retain one shared model vocabulary and acceptance suite when comparing designs.
Encode serialized, validated, and deliberately blind resolution in the same transition system.
Encode explicit leases, pins, copied ownership, and the age-only comparison against the same reader obligation.
Keep common input restrictions fixed or declare exactly which assumption differs between variants.
If a variant rejects a supported positive acceptance trace, record the expressiveness gap alongside any passing safety results.
Run an independent re-derivation again if a counterexample forces a material change to the requirements.
Give each author the same requirements and acceptance programs, isolate their reports and models until handoff, and independently replay the reported results. link:../../verification/README.adoc[Independent derivations and existing comparisons]

== Assumptions and deployment obligations

Every assumption has an owner, an affected guarantee, and a way to detect or test a violated premise where feasible.
Keep the production premises in the study that consumes them.
An assumption promoted to a kernel rule must have an enforcing transition and an acceptance case.
An environment contract must identify the supported providers and settings.

[cols="1,3,3",options="header"]
|===
|ID |Required premise |Owner and evidence

|E1 · Log order
|Readers of a replica log agree on record identity and position.
A delivery cannot silently skip a retained position.
The meaning of an empty read, prepared delivery, and accepted append is explicit.
An acknowledged record remains available above the declared retention floor under the supported failures.
|The provider and deployment own storage and delivery guarantees.
RTDB owns term admission, gap handling, replay position, and use of the retention floor.
Check each adapter and deployment profile against the durable order contract. link:../../allium/log-processor-lifecycle.allium[Log lifecycle]

|E2 · Object completion
|Successful publication gives the exact immutable bytes at the address expected by consumers.
Partial multipart uploads and pending copies are distinct states.
A lost reply can mean completion, refusal, or unresolved outcome.
|The adapter interprets completion and preserves evidence on ambiguous responses.
The provider and configuration establish visibility, durability, and conditional creation assumptions.
Check put, file upload, copy, direct open, list, and delete individually. link:rtdb-verification.adoc#_provider_contracts[Provider study]

|E3 · Discovery and root closure
|A selected root is complete with respect to every object needed for recovery from it and the replay suffix.
A reader or recovery process either discovers an eligible root under its contract or has another supported recovery path.
|The checkpoint writer orders dependencies and root publication.
Recovery owns root selection and retry behavior.
Maintenance owns retirement and suffix retention.
Provider listing, direct reads, and retention settings are inputs. link:db.allium[Database processing] · link:block-gc.allium[Block collection]

|E4 · Identity and fencing
|An object identity binds to one immutable generation's bytes.
A delayed operation and a newly created generation cannot be confused by reuse of a pathname.
An obsolete worker cannot publish or delete for a new term beyond the authority its issued capability still carries.
|Use disjoint immutable names or a provider condition on the exact object identity where required.
Audit data, metadata, artefact, staging, cache, and recovery keys independently.
Record which effect needs a term fence and how queued operations inherit it. link:trie-cat.allium[Trie catalog]

|E5 · Time
|Temporal row coordinates, monotonic elapsed time, and timestamps used by retention policy have defined domains.
Any clock used for lease entitlement has a stated authority, skew and restart assumptions.
|Coordinate interpretation belongs to the temporal engine and API.
Expiry enforcement belongs to the reader and reclamation protocol.
Time-source and skew assumptions belong to deployment.
Exercise equal boundaries and an elapsed-time advance near expiry.

|E6 · Physical input order and coverage
|The resolver receives the required order for each entity and operation.
An IID path covers its declared key range.
File and memory representations preserve original precedence through filtering and merge.
|Audit the writer, reader, page descriptors, live overlay order, compaction merge, and historical recency layout.
Verify narrow checks and replay across physical layouts. link:compaction.allium[Compaction] · link:../../allium/live-index.allium[Live index]

|E7 · Resource and cancellation behavior
|A successful operation holds the resources it needs until the contract permits release.
Any fallback or refusal stays within the declared memory and cancellation behavior.
Cancellation completion and provider I/O completion can be distinct events.
|Query and maintenance lifecycles own joins, reservations, and guard release.
Use native fault injection to distinguish cancellation requested, cancellation observed, underlying I/O finished, and handle dropped.

|E8 · Progress and fault domain
|For progress, the environment eventually provides a stable term, a reachable provider, sufficient resources for an eligible operation, and fair opportunities to run.
The fault model states which crashes, partitions, retries, and losses can coexist.
|Model scheduling and environment steps explicitly, then qualify claims on supported deployments.
Keep the safety invariant checked on adverse schedules within the fault domain even when the liveness premises fail.
|===

The local storage, S3, Azure, and Kafka claims have separate obligation records.
Use only the assumptions of the deployment named in a result.
For local storage, define what durable write, rename and process restart mean for the required failure class.
A process-interruption replay and a power-loss guarantee require different evidence.
For S3, account for the provider semantics of completed operations and the adapter's conditional creation path.
For Azure, explicitly include pending copy, stable copy identity, terminal status and uncertainty about staging cleanup.
For Kafka, justify ordered delivery, retained suffix, and survival of acknowledgement under the chosen broker configuration. link:rtdb-verification.adoc#_provider_contracts[Sources and adapter notes]

== Reader lifetime and reclamation protocol

The common safety condition is that every entitled read can use every required object in its selected generation, including the storage steps the contract allows to complete.
The common reclamation condition is that all obligations relevant to an object have ended and no new obligation can be created for that retired identity.
The proof distinguishes an optional search artefact with valid scan fallback from required data or metadata.
The shared artefact reference rule also imposes its own obligation even when the file is optional for producing an answer.

=== Candidate policies

[cols="1,3,3,3",options="header"]
|===
|Policy |User-visible promise |Mechanism to prove |Main open premise

|Validated bounded lease
|The admitted handle is usable through its declared deadline, with specified treatment of I/O started before expiry.
New operations after expiry receive the specified refusal or must obtain a fresh admission.
|Bind a lease to an eligible generation through an authoritative check.
Bound the admission against retirement and model any renewal as another checked decision.
Hold the necessary obligation for previously started I/O until completion or confirmed cancellation if the contract allows it to finish.
|Define clock authority, any safety margin, the lease period and renewal bound, and the semantics of a resumed or transferred handle.
Decide whether a stale follower waits, redirects, or refuses when it cannot establish admission.

|Coordinated pin
|The admitted handle can continue until close or another explicit event in its documented lifecycle.
The pin covers the generation and any in-flight reads the contract protects.
|Serialize pin acquisition with retirement and reclamation at a common authority.
Close the acquisition path before deleting a retired generation.
Release only when the handle and its protected operations have discharged their obligations.
|Distinguish a slow live reader from an abandoned owner under the stated failure model.
If pins expire on owner failure, define how the old owner is fenced before collection.

|Owned immutable copy
|The reader continues using a complete captured answer or complete independent inputs for the promised duration.
|Protect copying until all required bytes or observations are transferred, then release original-store responsibility for that reader.
The consumer owns the copy through its lifetime.
|Demonstrate support for streaming, backpressure, large queries, and bounded memory or spill storage.
A partial cache of future inputs needs an independent entitlement for what remains.

=== Proposed transitions and linearization points

The model treats the following events independently wherever the implementation might interleave them.

. *Capture and validate.* Capture the logical basis and physical generation, then establish that admission is still valid at the authority that controls retirement.
Retry capture when the selected generation changes before eligibility is established, or return the declared outcome.
. *Begin use.* Before opening metadata, data, an object-backed mapping, or a required range read, confirm entitlement or ownership of sufficient independent bytes.
Register a protected operation if completion extends beyond handle close or expiry.
. *Publish replacement.* Commit a complete new coverage map.
Retire the old generation for new admissions according to the chosen policy.
A maintenance cycle may now consider its objects, subject to the remaining obligations.
. *End use.* Release the active operation after the documented completion or cancellation boundary.
Release the reader only when its lifetime ends and its outstanding obligations have been transferred or discharged.
. *Authorize deletion.* At the authority that controls acquisition and retirement, confirm the exact immutable identity, absence of protected dependencies, and the required term or epoch condition.
Keep that reasoning valid through the actual provider delete.
. *Delete and publish.* Apply the provider mutation idempotently under the exact identity.
Publish the applicable catalog notice and invalidate cache entries according to their ordered boundaries.
After a lost reply, distinguish a conclusive absence of that identity from an unresolved outcome.

The pure admission and reclamation functions may implement the table of legal decisions.
The owner that serializes acquisition and retirement is what makes their inputs true when a mutation is dispatched.
A capability can carry the outcome of a decision.
An authority or identity constraint must also preserve the outcome across any delay before effect.
The collection study must cover trie data, trie metadata, shared artefacts, cached pathnames, checkpoint roots, table blocks, and log payloads with their own reachability rules.

The retained bounded study compared a validated lease and coordinated pin and exhibited age-only and stale-follower counterexamples.

== Verification methods

=== Design and contracts

. *Allium and acceptance traces.* Keep the human-facing state and API contracts in the owning specifications.
Link each requirement to its owning rule, observable acceptance case, and proof or test.
Give the reference model explicit inputs for environment assumptions.
Review each change to user-visible behavior before rewriting the oracle.
. *Bounded falsification.* In TLC, represent work that can pause as separate transitions.

Use small configurations for each failure family and at least one larger or independent check for important results.

. *Unbounded reference proof.* In Lean, define inductive histories and a simple executable oracle.

Prove composition for each claimed refinement and state the relation between inputs explicitly.

=== Production decisions and bypass checks

A Verus area should use `proof.rs` to include the production files by path, `laws.rs` for independent requirement statements, and `area.json` for the area description, verified obligation floor and controls.
Each law should carry a stable marker identifying its requirement and theorem or model predicate.
Include the same source and machine value types that the production caller uses.
Where necessary, move a pure synchronous decision out of the I/O shell, keeping the production call through it.
Keep proof-only definitions and ghost state distinguishable from executable behavior.
Specify arithmetic domains, vector and map invariants, preconditions, effects on success, and refusal behavior.
Audit external specifications and state where the production shell establishes every premise.
An internal loop invariant may be stronger than the final observation law.

A Verus negative control mutates the executable production decision and names which diagnostic should fail.
A joint control changes the decision and its local contract together and requires the independent law to detect the weakened behavior.
Retain the result of the unchanged baseline, and require the mutant to fail for the expected proof obligation.
Classify a parse failure, wrong error site, missing mutation anchor or unrelated compiler failure as a control harness error.
Require proof code to satisfy the project's no-cheating checks and make the trusted library or tool assumptions reviewable. https://verus-lang.github.io/verus/guide/[Verus tutorial and reference]

A separate compile-fail check verifies call-path enforcement.
Examples include forging a replica admission witness or invoking a protected effect with the unadmitted type.
The mutant must fail at the intended API boundary and the baseline must compile.
Check effect ownership with source inventory too, particularly for public helpers and admin, replay and provider paths.
