= Native RTDB runtime

The Rust implementation is in its source-writing phase.
The commands and interfaces below have implementation and regression-test source, but no native build or execution evidence yet.
Use link:../../rust/implementation-status.json[the implementation status] and link:../../rust/source-review.adoc[the source review] for the remaining work and the compilation gate.
The reviewed link:xtdb-rust-rewrite.md[migration design] remains the cutover contract.

== Server and clients

The `rtdb` binary assembles the native node, configured resource providers, authentication, pgwire, Flight SQL, health checks, metrics and tracing.
`node --file PATH` selects a YAML or data-only EDN configuration.
`--memory-limit` or `RTDB_MEMORY_LIMIT_BYTES` sets the explicit allocation ceiling; the default is one GiB.
Library-internal HTTP, TLS and cloud SDK allocations still require whole-process measurement.
See link:../../rust/crates/server/README.adoc[server configuration and lifecycle] for listener defaults and shutdown behavior.

Pgwire simple and extended queries, prepared statements, COPY, cancellation and session controls use the native session implementation.
Flight SQL uses the same query and transaction services through authenticated sessions, prepared handles and streaming ingest.
The link:../../rust/crates/pgwire/README.adoc[pgwire] and link:../../rust/crates/flight-sql/README.adoc[Flight SQL] references describe their current surfaces and compatibility qualifications.
The link:../../rust/crates/sql/README.adoc[SQL] and link:../../rust/crates/xtql/README.adoc[XTQL] references identify language forms that remain incomplete.

`INSERT` accepts `_valid_from` and `_valid_to` per row, including in a batch of prepared arguments.
The rows apply in input order.
A null start uses the transaction's assigned time, and a null end leaves validity open.

Use `ASSERT CURRENT_TIMESTAMP < TIMESTAMP '2027-01-15T00:00:00Z'` as the first statement of a read-write transaction to require an exclusive deadline.
The assertion uses the assigned system time, including any increase required to advance the previous transaction's time.
The transaction aborts when the assertion fails.
In the same transaction, an expression such as `CURRENT_TIMESTAMP + INTERVAL '1' SECOND` can supply a value, part of an encoded key, or a validity endpoint.

`SET bijection.at = TIMESTAMP '2027-01-15T00:00:00Z'` selects a fixed valid instant and query clock for subsequent reads in the current database.
Set it while the session is idle.
The session is read-only until `SET bijection.at = NULL` restores the live clock.

The embedded library exposes a versioned C ABI with Arrow C Data and C Stream ownership.
The Java foreign-memory adapter implements ADBC and the existing Clojure connection protocols over that library.
Applications depending on concrete JVM `Xtdb.Connection` or `RelationReader` classes need the migration described in link:../../rust/crates/ffi/README.adoc[the embedded binding reference].
Native buffer owners survive statement closure until the foreign consumer releases them.

== Funded DecisionClock receiver

The optional native profile pairs the signed site receiver certificate with a private receiver authority.

[source,yaml]
----
fundedReceiverClock:
  installationFile: /etc/rtdb/site-receiver-clock.json
  domain: 12345678-1234-4234-8234-123456789abc
  placementEpoch: 7
  purpose: bijection.rtdb.durable-acceptance-clock.v4
  transport:
    socket: /run/rtdb-receiver/clock.sock
    verificationKey: "<64 hex digits for the receiver authority's Ed25519 public key>"
    evidenceSha256: "<64 hex digits matching the certificate's evidenceSha256>"
    timeoutMillis: 100
----

The EDN spelling is `:funded-receiver-clock` with `:installation-file`, `:domain`, `:placement-epoch` and `:purpose`.
It accepts `:transport` with `:socket`, `:verification-key`, `:evidence-sha256` and `:timeout-millis`.
Use the commissioned receiver's nonzero domain UUID and the site's original nonzero placement epoch.
The site placement epoch is independent of the receiver publisher epoch and the journal writer epoch.
Use the v4 purpose shown above for the stock transport.

`installationFile` is an absolute path to an operator-controlled JSON object of at most 16 KiB, with the existing site fields `deployment`, `source`, `placement_epoch`, `certificate`, `issuer`, `image`, `cell` and `service_scope`.
Its `deployment` and `source` are UUIDs and `source` is the exact original RTDB incarnation.
Its `issuer` is the independently pinned 32-byte Ed25519 verification key in hex, `service_scope` is the installed 32-byte scope digest in hex, and `cell` and `image` are the commissioned values.
Keep those values and the placement epoch under the host's deployment authority.
Its `certificate` string holds the original signed JSON envelope of at most 4 KiB.
Pass through the envelope bytes exactly so its digest agrees with the original keeper evidence.
The verifier checks the signature and the exact purpose, deployment, source, cell, image and service scope against these installed settings.
The envelope has exactly `statement` and `signature` string fields.
The independent issuer signs the UTF-8 bytes of the decoded `statement` string, and the certificate identity hashes the original envelope bytes.
Use lowercase hex for the certificate signature, evidence digest and service scope, as required by the keeper verifier.

Use an absolute, operator-controlled Unix socket path whose socket grants no permissions to other users.
The receiver authority holds the signing key independently of the certificate issuer, keeper proof signers and TLS credentials.
The timeout of 1 through 1000 milliseconds covers the entire observation, including admission, socket I/O and verification.
Each observation uses a new challenge and returns an unavailable error on exchange failure.
The launcher reads the certificate and trust pins at open, so replacing them requires reopening the node.

The wire is one exchange per Unix stream connection.
The request concatenates ASCII `rtdb/native/receiver-clock/v1` and NUL, ASCII `bijection.rtdb.durable-acceptance-clock.v4` and NUL, the 16-byte source UUID, the 16-byte receiver domain UUID, the 32-byte envelope digest, the 32-byte signed evidence digest and a fresh 32-byte nonce.
UUIDs use standard byte order and digests use raw bytes.
The receiver checks the commissioned binding and samples after receiving the complete request.
It returns four big-endian unsigned 64-bit integers containing the publisher epoch, sequence, sampled Unix nanoseconds and conservative current error in nanoseconds.
It appends the 64-byte Ed25519 signature over the complete request followed by those four integers, then closes its write side.
It withholds a reply whenever it cannot attest the exact binding, current error or durable lineage.

The authority durably advances the sequence before signing, starting with a positive epoch and sequence at least equal to that epoch.
The epoch and conservative sample upper bound are nondecreasing, and the sequence strictly increases across samples, restarts and authority replacement within the same domain.
RTDB verifies that lineage across its successful observations and relies on the authority to maintain it across RTDB restarts.
RTDB rounds the signed sample plus error upward to microseconds in the commissioned scale.
The error must be positive and within the signed certificate limit.
Certificate expiry must follow the conservative upper bound plus the elapsed exchange time.
The keeper's separate post-fsync exchange supplies the original-quorum proof.

The stock Multi launcher selects the configured transport when its StreamJournal has a timed-original writer limit in `RTDB_TIMED_ORIGINAL_TRUST_FILE`.
For Default, use `ServerDriver::open_with_installed_receiver_clock` with `defaultV1Serving: true` and the installed resources, including a provider such as guarded `QuorumLog` that supplies recoverable original-quorum evidence on the same replica path.
The existing certified openers also accept a host-supplied receiver through `NodeConfiguration::certify_receiver_clock`.
Only an authenticated writable attachment with the matching source, live receiver and timed-original provider advertises `transact.decision-clock-offer`.
Missing mounts, stale exchanges and unsupported journals keep the capability closed.
An invalid installed certificate or mismatched trust pin rejects the selected profile at open.
Ordinary Default Local and Kafka and native Multi FileJournal remain outside the funded profile.
CUT and the receiver owner supply the commissioned receiver service and the separate qualified keeper mounts before activation.
See link:rtdb-multi-local-qualification.md[the local qualification checklist] for the paired StreamJournal and receiver cases.

== Expression equality

Strict expression equality (`===`) compares native set-reader identities without reading their elements.
Separate set constructions remain distinct, while an alias of one reader retains its identity.
Ordinary SQL equality continues to reject set/set comparisons at type admission.
Stored Transit values use their registered object semantics, including distinct identity-bearing objects and the emitted representations of supported native scalars.
The link:../../rust/crates/expr/README.adoc[expression reference] records the implemented comparison paths and their regression sources.

== Full-text search

`CREATE SEARCH INDEX docs_text ON docs (title, body)` defines a search index over a table's columns; `DROP SEARCH INDEX docs_text` removes it.
Definitions are documents in `xt.search_indexes`, so they can be queried as of any basis.

`MATCH(body, 'overdue invoice')` holds when the column's text holds every term of the query.
`SEARCH_SCORE(body, 'overdue invoice')` ranks a document by its term frequencies, using BM25 term-frequency saturation with unit weights and unit length normalization.
For corpus-relative BM25, use `SEARCH_SCORE(body, query, document_count, total_stored_length, document_frequencies)`.
Aggregate `SEARCH_LENGTH` and the document frequencies over the rows eligible for your corpus, at the appropriate time bounds.
`SEARCH_LENGTH` returns null for values outside the UTF-8 leg of a column.
`SEARCH_CORPUS_FINGERPRINT(ids, bodies)` returns a SHA-256 digest of the ordered pairs from equally sized text arrays.
Use a stable array order to bind a continuation to an exact corpus.
The frequency array follows the term order returned by `SEARCH_TERMS(query)`.
Queries that used the two-argument form for corpus-relative ranking need to pass those statistics explicitly.
Both see the version of each row visible at the query's valid and system time, whatever `FOR VALID_TIME` and `FOR SYSTEM_TIME` select.
Terms are split on non-alphanumeric characters and lowercased; only string values match.
A phrase in double quotes, `MATCH(body, '"overdue invoice" paid')`, matches only its terms side by side and in order.

Compaction and the background lane build search files for settled tries, with one shared file for an eligible partition group.
A scan with `MATCH` uses those files to narrow the candidates it resolves.
The node option `search: {enabled: false}` turns off the lane and acceleration.
`MATCH` still returns the same rows.
`search: {threads: N}` sizes the lane per database.
`search: {writeFormat: 14}` enables authenticated Arrow search files for newly indexed tries.
`search: {writeFormat: 15}` also enables snapshot-pinned serving postings and packed Arrow visibility for ranked SQL.
`search: {writeFormat: 16}` enables independent Arrow text-revision posting runs, journaled token deltas when admitted, and a table-owned event history for SQL point reads and public history-enabled search indexes.
See link:rtdb-fts-logical-postings.md[RTDB logical full-text postings].
The server defaults to paged Arrow format 13.
During a rolling upgrade from a version without format 13 support, set `search: {writeFormat: 11}` on writers and compaction workers until every reader and maintenance lane sharing the database supports format 13.
Upgraded nodes can read and repair retained formats 11 through 15.
Nodes configured for format 16 can repair logical runs from available original L0 inputs or a complete retained local journal.
The native format 16 writer stores the search lineage in `REPLICA_LOG`, so the journal file carries its identity when moved.
Keep any existing `REPLICA_LOG.lineage` with a populated legacy journal until its first writable upgrade.
The writer preserves the UUID from a valid sidecar when the legacy journal contains records and removes the sidecar after the header is durable.
An empty legacy journal starts with a fresh UUID when opened for logical search.
An upgraded journal requires a native reader that supports the lineage header.
If a follower opened the legacy replica journal read-only, restart it after the writer upgrades the journal to enable repair from native journal history on that follower.
Accelerated queries score against the column values visible at the snapshot.
The search accelerator can prune a ranked limit over the two-argument score and a `MATCH` on the same column.
The five-argument score uses the ordinary SQL sort and limit.
See link:../../rust/crates/search/README.adoc[the search reference] and link:fts.allium[the specification].
See link:rtdb-fts-snapshot-native.md[the format 15 design] for publication, ranking and retention.

== Spatial paths

Owned clear relations can declare a WGS84 XY spatial path with leading equality partition fields.
The maintenance lane builds cell postings over each settled trie.
A held read covers unindexed inputs within its work allowance, resolves candidate history at its system and valid cuts, then evaluates exact topology or distance.
A placed observed read can carry an ordered relation-frontier witness, including when no location matches.
See link:spatial.allium[the spatial path specification] and link:../../rust/crates/flight-sql/README.adoc[the owned Flight SQL actions].

== Operations

Health HTTP exposes the index, metrics, started, alive and ready routes, plus POST `/system/finish-block`.
Prometheus, OTLP tracing and configured Azure Monitor or CloudWatch publishers share native execution observations.
CloudWatch requires the corresponding binary feature.
Exporter compatibility, transport allocations and shutdown budgets remain unmeasured.

`export-snapshot DATABASE` captures the selected block's recoverable files and copies them within the configured storage root.
`reset-compactor DATABASE` requires an exclusive maintenance window with other nodes, clients and upstream writers stopped.
It publishes and adopts a replacement catalog before deleting compacted files.
Both commands have `--dry-run` modes, described in link:../../rust/crates/server/README.adoc[the operational command reference].

`compactor` follows replica progress and publishes compaction results for a separate writer to apply.
Concurrent deployment requires a source-log provider supporting multiple writers; the local log keeps its exclusive writer lock.
The local artifact inspection commands decode Arrow, hash-trie, table-block and block-catalog files without starting a node.
Their output is typed JSON; it differs from the JVM helpers' Clojure pretty-print output.

The paired `rtdb-config` binary qualifies configuration offline against explicit environment and artifact provenance inputs.
Its link:../../rust/crates/config/README.adoc[redacted report] does not authorize cutover.
JVM object-valued configuration hooks require a native replacement.

== Reading after a durable source barrier

Run `SHOW rtdb_source_barrier` outside a transaction before opening a read that must observe transactions already submitted by other clients.
The command reads the current database's durable source position and waits for local apply through that position.
Read on the same connection once the command returns `1`.
The command returns an error on a node without an indexer or a database that ingests transactions through an external source.

Use `SHOW rtdb_hosted_source_owner` in the read transaction used to verify known exact transaction coordinates.
It returns the source history only when the attached hosted holder has recovered the directory's durable checkpoint and a quorum confirms its current epoch.
The confirmation samples no source-log tip and makes no claim about whether a particular transaction is applied.
The caller checks its exact coordinates inside the read snapshot and refuses when the snapshot does not contain them.
