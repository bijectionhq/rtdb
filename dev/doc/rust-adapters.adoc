= Native Rust adapter configuration

The Rust implementation retains the pinned JVM adapter configuration names at its native boundaries.
Source coverage and execution evidence are tracked separately in `rust/conformance/source-completeness.json` and the conformance ledger.
The paths described here have regression sources; platform and service qualification belongs to Phase 2.

== Azure credentials

The Azure storage bridge selects environment credentials, workload identity, managed identity, and developer credentials through `rust/crates/azure/src/credential.rs`.
Environment client secrets take precedence over certificates and username/password credentials.
The username/password path requires `AZURE_CLIENT_ID`, `AZURE_USERNAME`, and `AZURE_PASSWORD` and uses `AZURE_TENANT_ID` when supplied.
Its default tenant is `organizations`.
The public-client authority follows `AZURE_AUTHORITY_HOST`, performs AAD instance discovery, and uses the discovered preferred network host for token exchange.

Managed accounts use the password grant.
Federated accounts follow user-realm discovery, MEX policy selection, WS-Trust, and the resulting SAML bearer exchange.
Token responses, identity metadata, cache refresh, and scopes retain the pinned MSAL behavior.
HTTP and XML work runs on the requesting future with bounded response bodies and deadlines.

Developer selection follows IntelliJ, Visual Studio Code, Azure CLI, PowerShell, Azure Developer CLI, and OS broker order.
The IntelliJ provider reads the Azure Toolkit cache through macOS Keychain, Linux libsecret, or Windows DPAPI and defaults its tenant to `common`.
Native cache work belongs to the database's existing I/O region; closing that region joins admitted work before releasing its resources.
The pinned distribution lacks `azure-identity-broker`, so Visual Studio Code and OS broker providers report unavailable.
`SharedTokenCacheCredential` is outside that distribution's default chain.

`AZURE_TOKEN_CREDENTIALS` accepts `prod`, `dev`, or an individual supported provider name, including `IntelliJCredential` and `VisualStudioCodeCredential`.
Provider cache limits, ownership details, and regression-source coverage are recorded in `rust/crates/azure/README.adoc`.

== Kafka and Schema Registry TLS

Kafka logs, Connect source consumers, and dead-letter producers accept the Java SSL configuration names through the native TLS adapter.
Log administrators, producers, watermark readers, ranges, and tails share the log's prepared TLS configuration.
Source consumers retain the configuration for their assignment.
The server supplies its existing memory budget; admitted TLS material remains owned through the last derived native client's destruction.
Schema Registry HTTPS uses the corresponding `schema.registry.ssl.*` options.
JKS, PKCS12, and PEM stores retain independent store and private-key passwords.
The default trust anchors come from the pinned Temurin resource; explicit trust material overrides them, including an explicitly empty store.

`ssl.keymanager.algorithm` selects `SunX509`, `NewSunX509`, or the latter's `PKIX` alias.
The managers retain their distinct alias ordering and client-certificate preferences.
An explicit `ssl.provider=SunJSSE` selects the built-in native context adapter.
Registry accepts these names through its prefixed properties.
Kafka applies Java ConfigDef trimming; Registry preserves raw provider and algorithm names and treats an empty name as the default.

`rust/crates/kafka/TLS.adoc` records TLS policy coverage, retained-memory ownership, and remaining source and qualification work.

== Dead-letter producer option text

The adapter decodes `buffer.memory`, `batch.size`, `max.request.size`, `max.block.ms`, `linger.ms`, `delivery.timeout.ms`, `request.timeout.ms`, `send.buffer.bytes` and `receive.buffer.bytes` as Java signed decimal text, including BMP digits and `-0`.
For those options and serializer class names, the adapter trims outer code units up to U+0020 before validation.

== Kafka configuration providers

Registry dead-letter producer options can declare Kafka `FileConfigProvider` and `DirectoryConfigProvider` classes through `config.providers` and their alias properties.
A `${provider:path:key}` value is resolved before the producer parses its settings or prepares TLS material.
The file provider decodes UTF-8 Java properties and validates escape syntax throughout the input before projecting the final requested values into native UTF-8 strings.
Regular files use the pinned OpenJDK 25 byte and UTF-16 reader windows.
The logical line reader's refill demand determines whether a decoding failure or an invalid property escape surfaces first.
Supplementary pairs can span character windows, and the line layer carries both units until property decoding completes.
Nonregular streams use the native whole-input reader and still need source channel readiness and close qualification.
Both Properties readers retain the source continuation behavior across CR, LF and CRLF, including a comment after a continuation whose logical line is empty.
The directory provider reads requested regular-file entries as UTF-8 with their original line endings.
An `allowed.paths` provider parameter limits resolution to the listed absolute roots and their descendants after canonicalization.
Missing values preserve their original placeholder and inserted text is resolved once from the original option values.
The lookup stages follow `ConfigTransformer`, `FileConfigProvider`, `DirectoryConfigProvider` and `AllowedPaths` from the Kafka 4.4.0 client sources.
Provider construction follows the Java alias map's iteration order, including duplicate alias declarations.
Provider lookups follow the default Java `HashMap.computeIfAbsent` iteration order for aliases and for paths within each alias.
The resolver includes unregistered aliases and repeated variable references when replaying the map's resize decisions.
It collects variables in the Java string-option map's iteration order using the native option map's key order as the insertion sequence.
Differences in the original JVM map's insertion sequence can still affect collisions during string-option extraction.
The Rust resolver retains configuration text in its UTF-8 representation and uses the requesting configuration's allocation budget.
Kafka Connect source assignments also resolve provider placeholders on their `!Kafka` remote before parsing `max.poll.records` and constructing the native consumer.
The assignment retains admitted expanded configuration through consumer destruction.
Kafka log and Connect client construction admit cluster properties-file reads and merge storage before allocation.
The cluster-level file uses Java Properties' ISO-8859-1 input profile.
Java `fetch.max.wait.ms` is translated to the native client's `fetch.wait.max.ms` after provider resolution.
Other Java client properties take their native equivalents: `send.buffer.bytes`/`receive.buffer.bytes` become the `socket.*` buffer sizes, `buffer.memory` becomes `queue.buffering.max.kbytes`, `max.request.size` becomes `message.max.bytes`, the `compression.*.level` matching `compression.type` becomes `compression.level`, `auto.offset.reset=none` becomes `error`, and the standard Java assignor classes become their native names.
A Java property and its native equivalent that disagree are rejected.
Serializer and deserializer classes are dropped, since XTDB chooses its own.
Java-only properties with no native meaning, such as `max.block.ms`, `max.poll.records` and `default.api.timeout.ms`, are dropped with kafka-clients' "was supplied but isn't a known config" warning on standard error.
Non-empty `interceptor.classes` and SASL login or callback handler classes are rejected, since they would run Java code.
Properties neither client recognises still fail native client construction.

Kafka `EnvVarConfigProvider` captures process environment entries when the provider is constructed and filters their names during configuration.
The allowlist uses the native Java whole-region matcher, with Java's default dot behavior for `.*`.
A request for `${provider:key}` selects an exact name from the resulting snapshot.
The retained snapshot and substitutions use the requesting configuration's budget.
The platform capture uses the Rust standard library's process environment snapshot, whose temporary allocator and encoding behavior still require host qualification.

The Registry dead-letter producer captures one create timestamp before native queue admission and carries it through every enqueue retry.
The source metadata wait and its effect on the append timestamp require the live sender integration.


== PostgreSQL floating-point arrays

The native PostgreSQL server accepts `float4[]` (OID 1021) and `float8[]` (OID 1022) Bind parameters in text and binary format.
Each parameter maps to an Arrow list of 32-bit or 64-bit floats.
Parameters can be SQL NULL, empty arrays, or one-dimensional arrays with NULL elements.
RTDB maps elements by position and emits arrays with one-based bounds.
Bind rejects multidimensional arrays.

A result with a known floating-point list type uses the corresponding PostgreSQL array type in its row description.
Fixed-size lists use the same result mapping as variable-length lists.
A list containing both float widths maps to `float8[]`.
An untyped result can still use the session's configured fallback format.
