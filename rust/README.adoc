= RTDB Rust implementation

This workspace is being implemented against XTDB commit `c84f9334eb060ceb92d28ecdd4a06e6b625932fd`.
The reviewed design is repository commit `c995e6b35b6812aa423c8a158c4e201e27532320`.
The JVM source, tests, fixtures, and external language clients remain the compatibility reference.

Source review and native build verification are separate requirements.
A successful build does not establish compatibility, durability, or performance parity with XTDB.
Workspace editor settings disable automatic Rust checks, build scripts, and procedural macro execution.

== Building

Install Rust 1.94.1 or later, a C/C++ toolchain, CMake, pkg-config, Perl, and the platform's SASL development libraries.
Run these commands from the repository root:

[source,shell]
----
cargo build --manifest-path rust/Cargo.toml --workspace --locked
cargo test --manifest-path rust/Cargo.toml --workspace --locked
----

The server executable is `rust/target/debug/rtdb`.
For a server-only build, use `cargo build --manifest-path rust/Cargo.toml -p rtdb-server --bin rtdb --locked`.
The server's default feature set uses local storage; optional backends are selected through the features in `crates/server/Cargo.toml`.

See link:../dev/doc/rtdb-crates-and-test-parity.md[crate contracts] and link:../dev/doc/xtdb-rust-rewrite.md[migration and rollback contracts].
Implementation status and evidence are tracked in link:implementation-status.json[the status manifest].
The link:source-review.adoc[source review record] identifies concrete paths, source discrepancies, and missing production traces.
The link:../dev/doc/rtdb-native-runtime.adoc[native runtime reference] connects the client, operational, packaging and comparison surfaces to their detailed documentation.

== Local development

Run `rtdb dev --data .rtdb` to start one development process with the normal native node, its local source and replica logs, and its filesystem object store.
The data directory defaults to `.rtdb`.
Restart with the same directory to reuse your data, or choose a fresh directory for an independent instance.

Connect a Bijection Flight SQL client to `grpc://127.0.0.1:3000` or run `psql -h 127.0.0.1 -p 5432 -U xtdb -d xtdb`.
The local `xtdb` user has no password, and both listeners bind to loopback.
Use `--port` and `--flight-sql-port` to run alongside other instances, `0` to choose a free port, or `-1` to disable a listener.
Startup prints the bound addresses.

On a fresh default development directory, the primary database serves `rtdb.v1.Transact` over its local replica log.
Its database incarnation and v1 receipts survive restart in that directory.
Ordinary SQL uses the Classic partition, which has its own history.
An applied Classic transaction makes the v1 branch route unavailable for that database.
Use separate development directories when exercising Classic writes and v1 writes.

Run `rtdb dev --multi --data .rtdb-multi` with a Multi-enabled runtime to develop against the fenced Journal driver.
Multi binds Flight SQL to loopback on port 3000 and accepts writes through `rtdb.v1.Transact`.
The selected directory holds the FileJournal, filesystem objects, database identity and generation keys.
Reuse that directory to recover the same Multi database on restart.

For the loopback TLS profile and Bijection HTTP startup, see link:../dev/doc/rtdb-multi-local-qualification.md[Local Multi qualification].

== Ownership

Semantic types, event headers, temporal ceilings, schemas, immutable tries, metadata, and wire codecs are passive objects.
Temporal calculators and batch builders are single-writer transients that publish only completed values.
An owning batch or cache lease retains the allocation and its memory charge until the last view is released.

Storage adapters are passive I/O objects.
The local log writer owns its ordered input queue and durable file handle; its driver is an active object that selects between queued writes and shutdown.
Log progress and cache fetch completion are separate monitor objects.
Readers own their log cursor, and only a successful read at the durable tip may report an empty poll.

== Verification gate

The Phase 1 source review must trace a client read, a data-dependent write, replica recovery, compaction retry, CDC restart, and database shutdown through concrete production implementations.
Every design surface requires an implementation path before compatibility qualification.
The presence of a package, an interface, or an unexecuted assertion is not completion of that surface.

Verification follows the repository's `xtdb-testing` workflow for Gradle runs and preserves separate reference, native, and comparison receipts.
The historical results recorded in the design are reference results, not a Rust baseline.
