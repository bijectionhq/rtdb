2. The native worker checks the copied inventory, digests, framed log tips and compacted rewrites before opening either node.
Each node recovers at least through the archived replica tip and synchronizes to the exact archived source tip.
Before tick 40, `native/recovered-checkpoint.json` records both recovered positions, adopted blocks and tick-39 transaction keys.
3. The same nodes run the second ingest, compaction, layout checks, internal queries, pgwire, PATCH and Flight SQL.
After shutdown, `native/execution.json` records the recovered prefix, 30 continuation ticks and one PATCH for each node.
The runner's `result.json` records the internal and wire matches for the pinned case.

=== Replay the closed native checkpoint on the JVM

After Phase 2 begins, use clean implementation and pinned reference checkouts, a conformance binary built from that implementation revision, and a new output directory outside the checkouts and retained inputs.
Keep the successful original JVM run's workspace and runtime artifacts available at their recorded paths.

[source,shell]
----
python3 rust/conformance/run_mixed_iid_jvm_replay.py --phase-two \
  --reference /absolute/path/to/pinned-reference \
  --reference-run /absolute/retained/mixed-iid-reference \
  --native /absolute/path/to/rtdb-conformance \
  --output /absolute/new/mixed-iid-jvm-replay
----

1. The runner builds both closed native stores and verifies their execution receipt, physical logs and Arrow file digests.
It makes writable copies for the JVM, preserving the local log names and mapping `storage/v06` to `objects/v06`.
2. The JVM opens both copies and checks their adopted blocks and tick-39 transactions before submitting tick 40.
Each node reaches its exact archived source tip and at least its archived replica tip.
It uses the original C84 helpers for the continuation, internal queries, pgwire, PATCH and Flight SQL.
3. The runner compares the typed observations with the retained original JVM case.
`comparison.json` records the reached predicates and their C84 source lines.
`result.json` gives the scoped match summary, and the original JUnit receipt identifies the independent reference invocation.

== Native corpus

The native corpus runs upstream XTDB's own Clojure test Vars against the native engine through the JVM binding.
`upstream_tests.sh` extracts `src/test/clojure`, `src/test/resources`, `src/testFixtures/clojure` and `src/testFixtures/resources` at the pinned upstream commit (`0b9fa440f23d2165250d215209f7fa9bd7c26a6f`, the upstream `main` this fork last merged) into `<out-dir>/.upstream-tests`, read-only, with a `MANIFEST` of blob ids and a `.commit` marker.
The runners put that tree ahead of this repository's test classpath, so neither the RTDB-edited test files nor the edited `xtdb.test-util` load; the runner refuses a namespace whose source resolves elsewhere and stops if `xtdb.test-util` does.
Its only seams are `with-redefs` in `bindings/jvm/src/test/clojure/xtdb/rust/corpus.clj` that route node construction, `tu/query-ra`, `tu/flush-block!` and the connectables to the native engine.
Set `XTDB_UPSTREAM_COMMIT` to run another upstream commit and `XTDB_UPSTREAM_REPO` to read it from another clone; when the commit is missing, `git fetch --filter=blob:none https://github.com/xtdb/xtdb.git <commit>` first.

[source,shell]
----
cargo +1.95.0 build --release --locked --manifest-path rust/Cargo.toml -p rtdb-ffi
rust/conformance/run_corpus_parallel.sh "$PWD/rust/target/release/librtdb_ffi.dylib" build/conformance/corpus-upstream-001 8
python3 rust/conformance/corpus_summary.py build/conformance/corpus-upstream-001
----

`run_corpus.sh <native-library> <out-dir> [ns...]` runs the same corpus through the Gradle `corpus` task, one Gradle invocation per namespace; the task refuses to start without `-PcorpusSources`.
Each result row records the Var's outcome, its assertion counts, `failures` (every failed or erroring assertion, up to 200, with `failures-truncated` beyond that) and `detail`, the first of them.

`corpus_summary.py` counts a failing Var as `fail` or `error` unless `corpus-exclusions.json` lists it and every recorded failure satisfies the match of the entry's decision.
Each decision names the RTDB feature or decision that justifies it and the outcome it reports (`jvm-api-boundary`, `jvm-internal`, `environment-unavailable` or `jvm-layout`); no pattern excuses a Var the list does not name, and a truncated failure list is never excused.
A Var that passes without reaching a native entry point is `pass-jvm-only`, reported apart from both passes and exclusions.
The summary prints the upstream commit the run loaded, or says the run does not measure upstream conformance, and lists uncovered exclusions (a recorded failure outside the decision), stale ones (the Var no longer fails) and absent ones (the Var is gone from its namespace).
Review and edit the list from those lines after every run; the shipped entries were seeded from a run over the fork's edited tests that kept only first failures, so expect uncovered and stale entries on the first upstream run.

== Corpus-backed assertion ledger

`corpus_ledger.py` derives the assertion ledger, the `--invocations` bindings and the native inventory that `runtime_inventory.py` reconciles, from the source inventory, a recorded reference runtime inventory and a native corpus run.
A reference Clojure test under `src/test/clojure` has the same Var, run through the native corpus, as its counterpart `corpus:<ns>/<var>`.
A Var `corpus-exclusions.json` excuses takes its decision's outcome as its classification and the decision's text as the reason; a `pass-jvm-only` Var is classified `jvm-internal`.
The native inventory records each corpus Var's outcome, the native library configuration that ran it, and the revision of the test sources the corpus ran.
A test the corpus cannot run natively, or one that exercises JVM implementation classes, carries a `classification` in place of counterparts: `engine-internal`, `jvm-api-boundary`, `jvm-internal` or `environment-unavailable`, each with a reason.
Corpus outcomes of the last three kinds become those classifications; JUnit tests and Clojure tests outside the corpus root are `engine-internal`.
A ledger case with neither counterparts nor a classification is an error, and a classified case never names counterparts.
Classified cases are reconciled without a bound invocation and reported apart, as `classified_case_count` and `classified_by_kind`; they are excluded from `assertion_denominator` and never count as passed native assertions.
A counterpart whose corpus outcome is not `pass`, `pass-wire` or `no-assertions` is a reconciliation error, so a failing or unexecuted native Var keeps the inventory incomplete.
Runtime cases bind to candidates through aliases for namespaces declared with metadata, whose candidates the source inventory names `^:meta/...`, and for JUnit methods a subclass inherits, resolved through the superclass declarations in the reference checkout's test sources.
A Var defined twice in one file is one ledger case and one candidate.
Language-client candidates, Vars the corpus no longer contains, and macro-generated Vars without a source candidate stay unmapped.

[source,shell]
----
python3 rust/conformance/corpus_ledger.py --source rust/conformance/source-inventory.json \
  --runtime build/conformance/reference-001 --corpus CORPUS_RESULTS --reference-checkout C84_CHECKOUT \
  --native-configuration NATIVE_CONFIGURATION --corpus-source-revision REVISION --output build/conformance/ledger-001
python3 rust/conformance/runtime_inventory.py --source rust/conformance/source-inventory.json \
  --ledger build/conformance/ledger-001/ledger.json --runtime build/conformance/reference-001 \
  --native build/conformance/ledger-001/native.json --aliases build/conformance/ledger-001/aliases.json \
  --invocations build/conformance/ledger-001/invocations.json --output build/conformance/ledger-001/reconciliation.json
----
