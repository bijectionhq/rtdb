= External runtime inventory evidence

`runtime_inventory.py --external EXTERNAL.json` reconciles original SQL-logic and language-client invocations alongside the JUnit runtime inventory.
It is a passive reader and performs no test discovery, builds or engine execution.
Without this argument, all external source files remain unresolved.
Direct SQL-logic fixtures under `src/test/resources/xtdb/sql/logic_test/` remain external assertions even though the source inventory classifies them as fixtures.

The external document records schema version, pinned reference revision, implementation revision, explicit runs and file bindings.
Each run has an `id`, `kind` (`sql_logic` or `language_client`), a relative `root`, the original `recorded_root`, and an `artifacts` closure of `{path, sha256, bytes}` records beneath that root.
Paths cannot escape the root or traverse symlinks.
Absolute receipt paths can be preserved after archival using explicit `relocations` entries `{original, artifact}`.
Runtime binaries, JVM classpath files, framework reports, source files and lifecycle traces must remain in that closure; a digest pointing at discarded bytes is insufficient.

`sources` binds each original repository path to its retained `artifact` reference.
Its digest must match the pinned source inventory.
Every actual assertion has one exact `bindings` entry containing `runtime_identity`, the complete ledger `identity`, `native_configuration`, and the ledger's explicit `counterparts` array.
Language-client bindings also name `source_candidate`.
Parameter/configuration identities are not inferred from test names, suite exits or neighboring cases.
Bindings omitted from execution, duplicated bindings and unbound runtime invocations fail validation.
Client helper declarations without a reviewed assertion mapping remain unresolved; the validator does not infer that a source candidate is merely a helper.

SQL-logic evidence includes the existing runner's plan, original record streams, both JVM repetitions, native observations, process traces and executed-artifact closure.
SQL-logic execution receipts record the engine's current storage format version as `environment.storage_version` and the configured query timezone as `environment.timezone` (`UTC`).
The external inventory reader accepts receipts that omit `environment.storage_version`.
`native_build` identifies the retained production-artifact manifest, its exact Cargo command/process/messages and copied executable bytes.
`native_binary` names that retained executable, and native configuration additionally binds the build configuration, feature selection and actual SQL-logic options.
The validator reparses retained original source bytes and compares every recorded identity, line, expectation and query-limit counter.
A query passes when both JVM runs and the native run satisfy the source expectation and produce identical formatted result text.
The inventory retains each assertion's three observations in full, including any native schema and query basis.
The binding's configuration is the canonical sorted compact JSON object `{adapter: "sql_logic", selection: ..., options: ...}` using the actual recorded selection/options.
An expected-error assertion only passes when the original statement required an error and each run retained an actual exception.
Matching unexpected failures, query mismatches, skips, suppression, parse failures and query limits remain unverified.
They cannot contribute passing coverage.

== Scoped original SQL assertion receipt

`python3 rust/conformance/emit_sql_logic_case.py --external EXTERNAL.json --run RUN --output CASE` extracts one observation from a retained SQL-logic run using link:configurations/sql-logic-scalar-case.json[the pinned case configuration].
Use an output directory outside the external evidence archive.
Keep the original absolute Linux invocation paths in the archive manifest and use its relocations to locate retained bytes.
The reader checks the complete retained streams, original source, selected local production executable, and the two JVM invocations and native invocation.
It checks the recorded Cargo workspace command, the compiler's source manifest and entry point, and the copied executable's position in the production build.
Each execution must record the configured `UTC` timezone and the specified query clock mode.
The three recorded storage versions must agree.
The selected literal expression reads no table or time value, so its context records `applied_basis`, `valid_time` and `system_time` as JSON `null`.
The pinned `sqlite-test/xtdb.test` record 4 expects T-formatted `NULL` followed by LF.
Engine-specific schema, clock readings and snapshot tokens remain in the original archived evidence.

The command emits a scoped ledger, the paired `CaseReceipt` arrays and their input lineage.
Use `--verify CASE` in place of `--output CASE` to derive the expected bytes from the archive and check the existing receipt files.
The lineage records the original JVM repeat as well as both compared executions.
All retained streams must be structurally complete.
The selected assertion must pass in all three executions.
The scoped ledger records both `inventory_complete` and `runtime_reconciled` as `false`.
The comparator produces its report from that ledger and the paired receipts.

== Client and file evidence

Client evidence includes the actual packaged server identities, copied original client sources, immutable client images, raw JUnit/TRX/ExUnit/libtest reports, container inspection, and drained owner receipts.
The run's `packages` entries name the original reference/native package manifests and their retained source/artifact closure.
The validator reparses the original framework reports and checks that stored cases match them exactly.
Both engines must execute identical framework/suite/name/source identities in the same explicit original lane.
The recorded reference/native configurations must match the ledger binding.
Both original assertions must pass; matching failed or skipped outcomes cannot qualify the file.

Each `files` entry records the original source path/digest and its exact `required_invocations` array of `{run, identity}` values.
Every original source candidate and every recorded parameter/configuration invocation must be accounted for.
A source file with no candidate declarations may be explicitly classified `support_input` only when its exact path is in the reviewed support-role allowlist for the pinned reference revision, with its retained original artifact.
SQL `.test` files cannot use that classification.
Unknown candidate-free code remains unresolved.
Missing files remain in `external_lanes_requiring_receipts`.

`complete` reports exact inventory reconciliation.
`all_assertions_passed` separately requires successful JUnit outcomes and passing original external assertions.
The release matrix requires both fields.
No source-only candidate count, suite process exit code or aggregate comparison flag becomes an assertion denominator by itself.
This validator and its regression sources have not executed during Phase 1.
