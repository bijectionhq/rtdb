= Matched packaged performance evidence

This machinery is written as Phase 2 source and has not executed.
It measures the packaged servers that operators receive through their real pgwire and Flight SQL listeners.
`run_performance.py` owns the Compose projects and subprocess regions; the clients, operation traces, measurements and comparison results are passive values under that lifetime.
All server, client and observer containers must be stopped and removed before a successful receipt is published.
Diagnostic timeouts do not establish clean owner drain.

== Inputs and workloads

link:performance-inputs.adoc[Packaged performance inputs, version 1] defines the complete plan, resource, node, provider, case and operation fields.

`performance_fixture.py --output NEW_FIXTURE.json` writes deterministic source-defined traces without starting a database.
Its eight cases cover all seven required classes: cold/warm ID lookups, a bitemporal range, a mixed-type join, bulk ingest, replicated commit, compaction under ingestion, and restore.
The Flight case queries the same explicit historical prefix through ADBC; setup uses pgwire to supply explicit system-time and valid-time values.
Expected typed rows live in the immutable fixture, separately from either engine's result.
Seed transactions and measured mutations use explicit monotonic system-time sequences, so a future seed cannot make later wall-clock submissions abort.
Before timing, each case captures the actual snapshot token and completed transaction rows, verifies the seeded system time, checks the logical row count/sum, and compares the actual persisted level/row-count catalog layout.
Opaque tokens and physical transaction IDs remain retained; logical system-time prefixes and catalog/query observations are compared across engines.
The benchmark cases are a new common workload and do not replace or count as original benchmark assertions.
Workload size, sample count, concurrency, SQL, row values and query postconditions remain in the retained operation trace.

The execution plan supplies the fixture's artifact reference and digest, its exact cases, explicit pilot budgets, two or more JVM repetitions, two or more native repetitions, and both engine deployments.
Each engine identifies its immutable package receipt and named nodes with configuration artifact, command, data mount, protocol ports, database and user.
The command must consume `/configuration.yaml`.
`credential_files` and `client_password` are optional explicit artifact references; credentials are never generated by the harness.
Keep secret values in mounted files, not the retained plan's `environment` map.
Configure remote object paths with the supplied `RTDB_RUN_ID` namespace and use fresh prefixes for every case.
The follower must read the same actual logs/storage as the writer; a second independent playground is not a replicated node.
Each server's configured allocator/heap budget must be stated in `engine_memory_configuration` alongside the common container limit.

The shared resource contract records container memory/swap limit, CPU count and placement, native architecture, backend placement and host page-cache policy.
The driver checks actual Docker limits and rejects CPU emulation.
`process_cold` means a real server process restart while retaining its volumes; it does not claim a cold host page cache.
Repeated cold samples only perform reads, preserving the restored logical prefix.
Warmup operations execute outside the timed sample interval.
The shared client image is built from the original pinned Python project and lockfile, and both server artifacts use that same image.

Every query compares actual typed values with its immutable expected rows, and schema/results are compared again across JVM repetitions and native runs.
Transactions require a committed `SHOW LATEST_SUBMITTED_TX` receipt.
Replicated commits transfer the actual await token to a second node and verify the acknowledged rows there.
Flush submits the HTTP request and then waits for the same explicit catalog adoption query on both engines; the JVM endpoint's enqueue response alone is not a completion boundary.
Compaction must produce the declared live higher-level trie postcondition while the load runs.
The measurement owner joins a catalog observer with the ingestion workers and retains its monotonic observation time.
The observer captures its baseline before releasing ingestion and requires a new live higher-level trie whose temporal metadata includes a measured write.
An existing higher-level trie or a compaction containing only seed transactions cannot satisfy this requirement.
Qualification requires a committed measured write before that observation and a measured write begun afterward.
An adoption first observed after the fixed load completes fails the case; the harness does not extend the declared sample denominator.
Restore time spans process startup through protocol readiness and the retained data checks.
SQL/codec incompatibilities, unavailable controls and failed postconditions fail the invocation rather than reducing its denominator.

== Measurement boundaries

The client retains per-operation latency, wall elapsed time and exact worker/round/operation identities.
The percentile selection is the pinned benchmark formula `sorted[floor(p * (n - 1))]`.
Throughput includes the client invocation's connection and worker setup; latency samples begin after connection setup.
The process observer joins each server container's PID namespace and reads the actual server PID 1 `VmHWM` and process I/O counters.
Peak RSS is the maximum individual server-process lifetime high-water mark through the sample, not a sampled aggregate peak of all replicas.
The client itself is separately memory-limited and is not included in engine RSS.
Result rows, serialized result bytes, total retained sample bytes, worker count and request bytes have explicit bounds.
These bounds do not prove an exact peak Python allocator accounting limit.

Comparable object-provider measurements use the owner-launched `provider_observer.py` HTTP sidecar.
Set `provider_measurement.kind` to `owned_http_observer`, identify the committed observer source as `observer_artifact`, and supply `configuration` with `upstream`, `port`, `workers`, `request_timeout_seconds`, `max_request_bytes`, and a slash-delimited `request_path_prefix` such as `/bucket/{namespace}/`.
Optional `list_paths` identify the provider's listing route, prefix parameter and required namespace prefix.
Object and listing prefixes contain `{namespace}` as a complete component and end with `/`.
Admission rejects decoded traversal segments and forwards accepted request targets unchanged.
Configure both actual engine object-store endpoints to use `http://object-observer:PORT`; an unused observer cannot qualify the case.
The upstream origin is explicit and must contain no embedded credentials.
HTTPS uses normal certificate/hostname validation or an explicit retained `ca_file`; the harness never disables TLS verification.
Signing, Range, content type and content encoding headers are preserved across the proxy, including the signed Host header.

The boundary is `successful_object_http_payload_and_requests`.
Only fully transferred successful 2xx calls increment successful counters.
Read bytes count GET response payloads; write bytes count PUT/POST/DELETE request payloads; HEAD contributes a successful request with no body bytes.
HTTP framing is excluded; list/API metadata payloads are included.
Failed request count, request bytes and response bytes remain separate.
Counters are isolated to the invocation namespace and taken immediately around the measured load, including background work completing in that interval.
Both counter boundaries require zero admitted in-flight requests; background operations cannot start before one interval and finish after the other without being accounted for.
The bounded worker owner cancels admitted client/upstream sockets on shutdown and whole-request deadline, then joins the workers.
Upstream DNS resolution occurs before listener admission, and TLS still verifies the configured hostname when connecting to the resolved address.
HTTP trailer forms that cannot be preserved by this adapter are rejected and remain unqualified.
The proxy's overhead is part of this explicitly matched measurement path for both engines.

Local filesystem payload/request accounting remains an implementation gap.
Process `/proc/1/io` counters include logs and runtime work and are never substituted for object-provider counters.
The historical correctness runner's JVM BufferPool bytes and native ObjectStore bytes likewise remain incomparable for this purpose.
A missing provider observer or a workload that never uses its claimed provider path cannot qualify packaged performance.

== Results and limits

All JVM baseline repetitions run before the native repetitions.
The report retains baseline variation, throughput, p50/p95/p99, engine peak RSS, provider bytes/requests and restore readiness time.
A repeatable native p95 regression above 10% or throughput loss above 10% opens an investigation; this harness does not auto-approve an explanation.
Each case also requires explicit p95, minimum-throughput and peak-RSS pilot budgets.
Any semantic/schema divergence, missing identity, provider-boundary mismatch or failed drain prevents qualification.
The output retains package and client image identities, input digests, every protocol receipt, actual resource inspection, command logs and lifecycle errors.
Inputs and source revisions are checked again after execution.
Qualification of this workload never grants full test parity or production cutover authority.
