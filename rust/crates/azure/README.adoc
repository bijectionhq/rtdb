= Azure Blob Storage adapter

Configuration and credential aliases are passive values and lookups.
The connection parser produces one immutable account, endpoint, and credential choice.
Inline account keys and node-local alias connection strings retain the JVM precedence rules.
Connection strings support account keys, SAS tokens, explicit Blob endpoints, endpoint suffixes, and Azurite development storage.
The native store creates its container idempotently before returning.
Object keys include the configured prefix and the supplied storage-version and epoch root.
Shared immutable publication retains conditional creation and exact retry comparisons.

The passive default-credential bridge uses official Azure Identity clients alongside native providers for application, workload, and development credentials.
It selects configured environment client secrets, certificates, or username/password credentials, workload federation, managed identity, IntelliJ, or Azure CLI, PowerShell, and Azure Developer CLI credentials.
Credential refresh occurs inside the selected provider on each request; the bridge has no background loop.
Credential commands run in owned process groups with a 30-second deadline, bounded output, and joined output readers.
Command execution occupies the caller's thread until the group exits or is terminated.
`AZURE_TOKEN_CREDENTIALS` restricts production, development, or an individual supported provider; unsupported selections return errors.
A configured service identity failure does not switch to a different principal.
The native managed-identity credential implements the endpoint selection of Azure Identity Java 1.18.7 and its MSAL4J 1.26.0 dependency.
App Service, Service Fabric, Cloud Shell, Azure Arc, and IMDS use their selected endpoint, API version, secret or metadata headers, and supported client-ID selector.
The pinned MSAL selector treats `MSI_ENDPOINT` as Cloud Shell even when the older `MSI_SECRET` variable is present; it has no separate Azure ML protocol branch.
Cloud Shell and Service Fabric report a user-assigned client ID as unavailable during token acquisition, allowing the default chain to try its next provider.
Arc accepts a bounded challenge file in its token directory and requires the response to confirm a requested client ID.
Challenge reads run in the database's existing I/O region; shutdown retains cancelled reads through worker completion and result destruction.
Unix challenge files are opened nonblocking and checked for a regular-file type before reading, including when the challenge names a symbolic link.
HTTP responses are bounded to one MiB, challenge files to 4096 bytes, and requests have connect and total deadlines.
The credential is passive: HTTP attempts, retry delays, and serialized cache refresh run on the caller's future.
The bridge continues after a classified unavailable managed identity, while an authentication failure from a reachable endpoint stops principal selection.
Error-envelope classification preserves null responses, nested errors, field order, duplicate fields, scalar string coercions, and the default JSON reader's token position when a known string field contains a container.
Only fields included in the pinned provider's error message can supply its unavailable marker.
IMDS availability probes precede default-chain calls, including cached-token calls; explicit `ManagedIdentityCredential` selection skips the probe.
Service Fabric requests retain normal HTTPS trust and hostname checks, matching the reachable return path in the pinned `DefaultHttpClientManagedIdentity.openConnection`.
That method returns any `HttpURLConnection`, including its HTTPS subclass, before its thumbprint-specific branch.
The passive IntelliJ credential reads the Azure Toolkit cache from macOS Keychain, Linux libsecret, or the Windows DPAPI-protected cache file.
Each native cache read belongs to the database's existing I/O region; shutdown joins admitted reads even after their callers cancel.
Cache reads and token responses have a one MiB byte limit.
The immutable authority and cache reader belong to the passive credential.
One serialized monitor owns the last account and its access-token, refresh-token, and account-cache values.
The cache limits each collection to 64 entries and retained credential text to eight MiB.
Refresh uses the Azure developer single-sign-on client and the storage scope with the MSAL OpenID scopes.
An expired session with an authenticated account tries its retained refresh token before rereading the Toolkit cache.
Account-free responses reuse only unexpired tokens whose returned scopes include the requested storage scope.
ID-token and client-info payloads are parsed before publishing a session, and blank refresh-token responses retain an existing cached refresh token for that account.
Short-lived silent-refresh results trigger one forced refresh before falling back to the Toolkit cache.
A proactive refresh rejected by the token service preserves a still-usable access token.
The configured tenant and authority host select the token endpoint.
AAD instance discovery validates custom authorities and selects the advertised preferred network host before token exchange.
Authority alias metadata is retained in one process-wide cache with explicit byte and entry limits.
Development fallback follows the pinned order: IntelliJ, Visual Studio Code, Azure CLI, PowerShell, Azure Developer CLI, then OS broker.
The pinned distribution does not include `azure-identity-broker`; Visual Studio Code and OS broker credentials therefore report unavailable, matching their Java classpath checks.
`IntelliJCredential` and `VisualStudioCodeCredential` are valid individual `AZURE_TOKEN_CREDENTIALS` selections.
`SharedTokenCacheCredential` is absent from the pinned default chain and is not an accepted selector.
Native desktop APIs and authority-specific sign-in behavior require Phase 2 qualification on each platform.
The pinned Rust certificate credential reads `AZURE_CLIENT_SEND_CERTIFICATE_CHAIN` and includes the leaf and retained CA chain when requested.
The environment username/password branch requires `AZURE_CLIENT_ID`, `AZURE_USERNAME`, and `AZURE_PASSWORD`, and follows client-secret and certificate selection before workload identity.
Present empty values remain configured values and fail acquisition without selecting a different principal.
Its missing tenant defaults to `organizations`; IntelliJ explicitly defaults to `common`.
The passive password credential owns its application ID and immutable credentials, and uses the same account-aware session monitor as IntelliJ.
AAD password acquisition performs user-realm discovery, then uses a direct password grant for managed accounts or MEX policy discovery and WS-Trust for federated accounts.
WS-Trust 1.3 takes precedence over WS-Trust 2005, and the returned SAML assertion is exchanged with the configured application ID.
ADFS and CIAM authorities skip user-realm discovery.
Federation requests and responses have a one MiB limit; parsed XML has depth, node-count, and eight-MiB retained-data limits and rejects document types and external entities.
XML documents, realm results, binding policies, and assertions are passive values owned by the acquisition call.
The process-wide legacy security-namespace flag retains the pinned MSAL namespace-map mutation.
