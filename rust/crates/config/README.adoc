= Offline configuration qualification

`rtdb-config` is a read-only companion to the native server.
Its report implements the configuration inventory in `dev/doc/xtdb-rust-rewrite.md`, sections 6 and 9.
The release image and extracted artifacts include the binary with the same backend feature selection as the server.
This source has not been compiled or executed during Phase 1.

`rtdb-config --build-info` prints the compiled version, full revision and selected time-zone version/SHA-256 without configuration inputs.
Runtime `XTDB_VERSION` and `GIT_SHA` overrides do not alter this artifact identity.

The qualification command reads three explicitly supplied files and writes JSON to standard output.
Classic S3 key preflight takes one additional explicit inventory file.
It opens no node, log, object store, credential provider, TLS keystore, Kafka properties file, registry, subprocess or network connection.
It creates no configuration or storage files and changes no deployment state.
The supplied environment JSON is the entire environment used by the production decoder; the tool does not inherit deployment credentials or options from its own process environment.
The caller must provide any implicit settings, such as `XTDB_PASSWORD`, `XTDB_SKIP_DBS`, and `XTDB_COMPACTOR_THREADS`, that apply to the deployment.

[source,shell]
----
rtdb-config yaml deployment.yaml environment.json provenance.json
rtdb-config ingest-yaml databases.yaml environment.json provenance.json
rtdb-config edn deployment.edn environment.json provenance.json
----

`environment.json` is an object of unique string keys and string values.
An empty object selects production defaults for implicit environment settings.
`provenance.json` has exactly the following fields; revision values are full 40-digit Git object IDs and artifact values are 64-digit SHA256 digests.
The package manifest contains digests of the extracted server and migrator binaries.

[source,json]
----
{
  "reference_revision": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "implementation_revision": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "server_artifact_sha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
  "migrator_artifact_sha256": "dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd"
}
----

The report retains SHA256 digests of the exact configuration, environment and provenance input bytes.
It includes the declared provenance, compiled backend capabilities, databases, partition counts, auth methods and rules, remote aliases, module registrations, source and replica identities, and storage roots including native storage version and epoch.
PostgreSQL CDC reports its remote, publication and slot; Kafka Connect reports the remote, topic, Docs table and option names.
A persisted PostgreSQL source with an omitted indexer is reported as DirectMirror, matching the runtime default for legacy configurations.
New PostgreSQL source YAML requires an explicit `indexer`.
Passwords, hashes, keys, connection strings, Kafka option values and URL userinfo/query/fragment values are omitted or replaced with `[redacted]`.
Decoder errors use fixed messages because parser diagnostics can contain secret values.
Paths, usernames, database names, hosts and other deployment identifiers remain visible; protect the report as deployment metadata.
Whole-input digests can still reveal equality between secret-bearing files, so retain reports under the deployment's access and retention policy.

`configuration_compatible` means the inspected configuration had no reported static gap.
`cutover_eligible` remains false: neither a parsed configuration nor a supplied artifact digest proves any of the cutover evidence.
A completed report exits with status 2, including when its static configuration is compatible.
Status 1 means an input, allocation or output failure; `--help` exits with status 0.
No report is an authorization to grant writer credentials.

YAML uses the production bounded parser, environment expansion and semantic decoder.
The structural inventory lists unknown fields and provider tags before semantic decoding can reject the first one.
The report retains reservations for its own allocations and derived decoded values; each input is limited to one MiB.
A path beyond the inventory limit or more than 10,000 findings makes the report incomplete and ineligible.
Duplicate environment keys and duplicate YAML keys are rejected.
The CLI accepts regular files and bounds reads; on Unix it opens inputs without blocking on a FIFO.

The data-only production EDN adapter can ignore nested JVM options when projecting recognized fields.
Every EDN report therefore contains a blocking projection qualification finding, even if decoding succeeds.
Convert to explicit YAML and compare every original setting before treating that deployment's configuration as compatible.
Executable reader forms, custom JVM objects, programmatic module factories, custom indexers, unsupported converter classes and credential-provider callbacks require a native adapter, bridge or explicit migration.

== Kafka

Kafka log and remote descriptions require the `kafka` feature.
Kafka Connect external sources also require `kafka-connect`.
With Connect support compiled in, qualification uses the native Connect configuration parser and built-in converter constructors to check portable converter settings.
This includes Confluent Protobuf with dynamic message types, the converter's own `schema.registry.url` list, supported Schema Registry credential sources and subject-name strategies, and the Protobuf projection settings accepted by the native converter.
Supply the Registry URL separately for each Confluent key or value converter.
A remote's `schemaRegistryUrl` is inventory metadata and does not supply a converter's Registry URL.
Unknown converter options and unsupported classes produce blocking findings.
Transforms, predicates, and Registry rule or DLQ settings require separate runtime qualification.
Registry transport setup, TLS material, registered schemas and references, and record conversion are checked when the source uses them.

With Kafka support compiled in, inline broker properties are checked using the native property translator.
This covers supported OAuthBearer client-credentials options, including the built-in Kafka callback, retriever and validator classes used by the native adapter.
Put the comma-separated `RTDB_KAFKA_OAUTHBEARER_ALLOWED_URLS` in the explicit environment JSON for secured broker OAuthBearer.
Include the exact token endpoint, including any query string.
The report records the variable's name and omits its value and the broker and converter option values.
Custom OAuth hooks, file token retrieval, and client assertions require a native adapter.
Broker authentication, token issuance and refresh, TLS material, and librdkafka client construction require deployment-time verification.

== Classic S3 key preflight

Use the `rtdb-config` binary packaged with S3 support to check one configured Classic database per invocation.
Select `xtdb` for ordinary node YAML or the recorded database name in the fixed `ingest-yaml` configuration.

[source,shell]
----
rtdb-config ingest-yaml databases.yaml environment.json provenance.json \
  --classic-s3-key-inventory s3-keys.json
----

The JVM S3 adapter sends literal rooted paths to the SDK.
Legacy RTDB encodes the object path first, which changes the key stored by S3 independently of HTTP escaping.
For example, the JVM's `tables/public$t%3F/data/l00-rc-b00.arrow` and RTDB's encoding of `tables/public$t?/data/l00-rc-b00.arrow` both end up at the same key under a shared root.
RTDB encodes the percent sign in the already literal `public$t%3F` as `public$t%253F`.
The preflight reads explicit logical names and provider keys so it can detect this collision without guessing from a percent sequence.

=== Capture and inspect

. Record the selected database's exact configuration, including the S3 region, endpoint when custom, prefix, and storage epoch.
  The namespace uses the effective endpoint URI, including the bucket host prefix for virtual-hosted custom endpoints, or `null` for standard AWS addressing.
  Declare addressing in YAML and remove deployment endpoint environment overrides before taking the capture.
. Fence publishers and quiesce compaction, GC, multipart activity and lifecycle deletion for the capture.
  Resolve or account for unfinished uploads before declaring the capture complete.
  Record the retained catalog and log basis, then enumerate its recorded logical object paths relative to the storage root.
  Use recorded slugs and locators, including retained historical references, and account for every listed key independently of its provider spelling.
  Mark keys needed by a current read with `requires_current_version: true`.
. From a read-only provider capture at the same cut, supply all pages of data versions and delete markers for both exact storage directory prefixes, including empty listings.
  The roots include the configured prefix and the storage version and epoch, with a trailing slash.
  Supply one prefix if both spellings agree.
  Preserve the raw stored key and opaque version ID as returned by the provider, after removing any listing response encoding.
  Keep `%` sequences in stored keys and version IDs verbatim.
  Set `complete: true` only after confirming the capture's scope, ownership, completeness and stable cut.
. Run the preflight on the files and retain the report alongside the capture and provenance.
  The command reads the supplied files locally, with no S3 connection or deployment mutation.
  Store the output as deployment metadata because it contains exact paths and version IDs.

[source,json]
----
{
  "schema_version": 1,
  "database": "inventory",
  "namespace": {"bucket": "fixture-bucket", "endpoint": null, "region": "us-east-1"},
  "complete": true,
  "listed_prefixes": ["snapshots/v06_e02/"],
  "logical_objects": [
    {"key": "tables/public$t?/data/l00-rc-b00.arrow", "requires_current_version": true}
  ],
  "versions": [
    {
      "key": "snapshots/v06_e02/tables/public$t%3F/data/l00-rc-b00.arrow",
      "version_id": "current+/=",
      "kind": "object",
      "is_latest": true
    }
  ]
}
----

The sample is eligible for `legacy_rtdb` spelling at the captured cut.
`shared` means all recorded paths resolve to the same exact keys in both layouts.
`jvm_literal` and `legacy_rtdb` identify the sole layout covering the capture when at least one recorded spelling differs.
`refused` carries findings for incomplete or mismatched scope, collisions between logical paths, both aliases in use, mixed layouts, missing or unexplained keys, unversioned or inconsistent histories, and missing current objects.
A delete marker still occupies its exact key for collision detection.
The report includes the raw input digest and, for matched scope, each logical path with both candidates and the in-scope version identities.
`eligible` applies to key spelling at the supplied cut only.
The report's separate `cutover_eligible` remains false and a completed report still exits with status 2.
See the link:tests/fixtures/classic-s3-alias-collision.json[collision fixture] for a capture that the preflight refuses.

=== Open a literal-key Classic namespace

Native RTDB accepts the optional `keyLayout: jvm_literal` field on the Classic `!S3` object store.
The default is `legacy_rtdb`.
Specify the region and declare any custom endpoint in the same configuration.

[source,yaml]
----
storage: !Remote
  objectStore: !S3
    bucket: fixture-bucket
    region: us-east-1
    prefix: snapshots
    keyLayout: jvm_literal
----

Use a newly allocated namespace or qualify an existing namespace at a fenced cut.
For an existing namespace, require `jvm_literal` or `shared` from the preflight and verify that every retained version grant names the exact literal key before opening it.
The profile selects a single spelling for all provider operations and isolates its disk cache by provider configuration.
The persisted profile has its own native configuration type.
Every RTDB process that can open the namespace must understand that type and select the same layout, including after restart or replacement.
Keep an existing `legacy_rtdb` namespace on its original profile until an offline migration has reconciled its physical keys and grants.
Multi cell storage uses its own key layout and configuration.

=== Upgrade and rollback

. Keep serving with the current layout while resolving refusals and qualifying a protected shadow restore at the same catalog and log basis.
  Use the report to establish the exact provider identities, and qualify object bytes, storage formats and version-scoped access independently.
. Before any cross-layout upgrade, choose and approve an offline migration or a storage profile with a stable namespace rule.
  An apply plan must reconcile the recorded locators, each `(bucket, endpoint, region, key, version ID)` used by existing grants, and the disk-cache namespace together.
  A copied object has its own destination version identity.
  Keep the original keys, versions, exact grants, catalog and log basis protected through rollback.
. Rehearse restart, historical reads and return to the original protected basis before transferring publisher ownership.
  Rerun the preflight against a fresh final capture if the storage or catalog has moved since qualification.
  Apply, runtime activation and any future default change require separate approval.

== Cutover inventory

Ordinary node YAML names the primary database while attached database configurations live in its durable catalog.
That report explicitly blocks an uninventoried attached-database set.
An operator can supply a separately captured fixed database inventory using the production ingest YAML shape, including each database's exact log, storage and external source description.
The tool does not claim that the supplied list is complete or that it reflects the current durable catalog.
Relative local paths, uninspected Kafka properties files, unknown remote aliases, invalid epoch/root descriptions and missing compiled features are blocking findings.
Absolute local paths are lexical: the tool does not resolve symlinks, read files under those roots or verify permissions and capacity.
Cloud credential chains, endpoint overrides supplied outside the explicit configuration, backend behavior and token rotation require separate qualification.

The report carries the remaining section 9 obligations: deployment inventory, write-pause and recovery targets, protected retention, matched-basis shadow reads, accepted-write drain, publisher fencing, finalized per-partition handoff manifests, restore verification, canary read-back, restart and historical reads, and reverse recovery through acknowledged Rust writes and interrupted compaction uploads.
Mixed JVM/Rust writers require a separate qualification.
Those observations must be retained with their own reproducible inputs and artifact provenance before an operator transfers ownership.

The library's request inputs, parsed document and report are passive values.
A single caller owns the transient inventory builder; the report owns its memory reservations after decoding returns.
The synchronous CLI only reads requested inputs and streams the report to the caller's output; it owns no tasks, monitors or persistent service state.
The server dependency supplies the exact production decoder and feature selection; the CLI calls none of its service-opening functions.
