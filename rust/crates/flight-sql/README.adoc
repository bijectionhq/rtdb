= Native Flight SQL and ADBC transport

`rtdb-flight-sql` serves Arrow Flight SQL through native tonic HTTP/2 and Arrow IPC.
ADBC Flight SQL drivers use the same `rtdb-node` sessions, SQL preparation, query cursors, transaction resolver, and authentication as the PostgreSQL frontend.
The source and regression cases remain uncompiled and unexecuted during Phase 1.
Schema descriptions retain the supplied physical parameter fields, while query execution opens their signed vector view.
Retained parameter IPC remains lossless.
Prepared updates retain uploaded Arrow parameter batches through transaction buffering and encoding when the batch layouts agree.
Separate uploads of the same statement can have different schemas when they are coalesced in a transaction.
The source encoder aligns compatible argument vectors by position in Arrow and preserves the order of the argument rows.
Bulk ingestion retains compatible Arrow document columns during source-log encoding, replay and transaction staging.
This includes lists, fixed-size lists and structs with compatible child fields.
When a struct gains fields between compatible Arrow uploads, source encoding joins those fields in Arrow, including structs inside lists.
Arrow batches targeting the same table can share a source-log document layout when their common columns agree and other columns are absent.
When the same transaction also contains compatible row-backed puts for that table, source encoding builds vectors from those rows and combines them with the uploaded vectors in transaction order.
Columns with compatible union legs share a dense union when their scalar types or nested container kinds differ between batches.
Null and missing values use the union's null leg.
Uploads can gather multiple tags for the same value layout into one Arrow child, including signed execution aliases.
When a union with one value layout is normalized, the typed Arrow array's validity represents null entries.
The typed document writer handles layouts that require cell conversion.

== Composition and ownership

`ServerDriver::bind(FlightConfig, Node, Arc<Authenticator>)` binds an insecure listener and returns its `ServerHandle` and unstarted driver.
The handle exposes the bound address, current status, status subscription, and shutdown request.
The caller owns `run`, requests shutdown, and joins the driver before closing the node.
Dropping a running driver future does not satisfy that join obligation.
`bind_with_clock` injects the lease clock; the ordinary constructor uses the wall clock.

The Active Object is the server driver, which selects listener completion and lease sweeps.
Tonic owns its transport connection tasks and joins their connection watchers during shutdown.
The driver's socket adapter observes cancellation during reads and writes, including a peer that stops consuming responses.
The driver also waits for the admitted-call monitor to reach zero before reporting completion.

Service methods and response streams are passive caller-owned work.
The stream advertises the prepared result schema and conforms runtime pages through the passive `rtdb-columnar::DeclaredBatch` adapter.
Columns that already match their declared field retain their Arrow buffers when the adapter conforms the rest of the page.
Compatible nested field ordering and dense union identifiers can change while retaining the source value buffers.
This follows the pinned Flight producer's ADBC `ArrowReader`, including NULL endpoint vectors under advertised timestamp fields.
The encoder checks the complete declared schema before encoding physical buffers, including signed decimal precision and scale metadata.
Schema and record-node regression sources remain unexecuted.
An admission owner retains its semaphore permit through authentication, execution, and the final response stream.
An acquired-session guard releases its in-use count even when a call is dropped during identity revalidation.
Sessions own their catalog selection and per-database connections.
A transaction handle owns a dedicated connection.
A prepared handle owns SQL, its session/database or transaction scope, and the retained IPC parameter batch.
A connection resource serializes access to its `NativeSession`; expiration cancels borrowed work and releases the connection when its final borrower leaves.
`ServerStatus` is a separate monitor of call counts and live registry sizes.

Session, transaction, and prepared registries retain expired tombstones for one further idle period.
A presented session renews from its initial unclaimed timeout to its normal idle timeout.
A session with an in-flight call cannot expire; releasing the call restarts its idle measurement.
Transaction and prepared handle lookups renew their leases, and an end action claims a handle exactly once.
Session closure leaves dedicated transaction handles independently owned.

== Authentication and sessions

Authentication accepts Basic, Client, Bearer, and anonymous trust calls according to `rtdb-auth` rules.
A placed endpoint uses the `x-xtdb-database` header on the first authenticated call to bind the session to its local deployment.
Use `rtdb-multi gateway --flight-listen ADDR` and the cell secret to route to the local cell's writer over the private network.
Non-loopback Flight SQL gateways require TLS.
The gateway sends proof of the original peer address so the writer applies the same authentication rules to forwarded calls.
After a writer move, establish a new Flight SQL session.
The transport peer address comes from the accepted socket.
Each authenticated session retains a principal and an HMAC of the complete original authorization header, using a fresh service-lifetime secret.
A repeated Basic or Client header must match that MAC.
A cookie and bearer token supplied together must name the same session.
Every presented session revalidates its principal before work begins.

New sessions return the `arrow_flight_session_id` cookie.
Authenticated sessions also return an `authorization: Bearer` header.
Unknown or expired bearer sessions fail as unauthenticated; cookie sessions fail as not found.
The per-call `x-xtdb-database` selector takes precedence over the session catalog, then `xtdb`.
Session options expose catalog and the fixed `public` schema, with per-option invalid-name or invalid-value results.
Playground mode attaches unknown databases locally on first use through the node catalog owner.

The listener is insecure, matching `FlightSql.open` in the pinned implementation.
The node's PostgreSQL TLS configuration does not apply to this endpoint.

== Queries, writes, and metadata

GetFlightInfo captures the query plan, Arrow parameters, catalog and clock behind a bounded opaque `TicketStatementQuery` handle.
Authenticated ticket redemption requires the original session and deployment attachment.
It keeps the connection borrowed through statement classification, basis capture, and schema preparation against that basis.
GetFlightInfo, GetSchema, CreatePreparedStatement and DoPut statement updates use the same selected Direct parser diagnostics for initial preparation.
When the vendor parser rejects a first unquoted ASCII identifier outside both vocabularies, the frontend compares the byte range and accepts a matching extraneous-input or statement-head mismatch report.
The gRPC description carries the report’s line, column and message.
Anomaly metadata includes the message, category `incorrect` and code `xtdb/sql-error` when its encoding fits the 4 KiB limit.
A Direct parser admission failure after eligibility returns its resource error, and other Direct outcomes retain the original preparation error.
Paired Flight SQL diagnostic execution remains pending.
DoGet revalidates the redeeming session, waits its visibility barrier, then opens the captured basis through `NativeSession::query_context_at`.
A ticket remains usable by a different authorized caller.
Flight SQL opens a columnar query cursor where the operators can provide Arrow batches.
An index-covered ordered point read streams typed results from the posting leaves under the ticket's captured basis.
Query streams retain their cursor, connection, session lease, cancellation scope, and Arrow allocation owners through completion or cancellation.

GetFlightInfo issues DML and SET once.
An open write transaction buffers DML for commit.
Their empty ticket sends an empty Arrow schema when redeemed and performs no further effect.
SQL BEGIN, COMMIT, and ROLLBACK use the shared Flight SQL control rejection; transaction actions own those operations.
Prepared handles are re-prepared against the current execution context on each use.
Their parameter metadata uses positional unnamed nullable fields, and the source's field-4 `is_update` extension is retained.
Prepared query binding retains the first Arrow batch.
Flight SQL derives the result schema from the bound Arrow fields and encodes the batch when issuing a query ticket.
Ticket redemption validates the argument batch and reads the first parameter row when opening the query.
A pure projection of compatible bound parameters stays in Arrow.
Compatible nested lists, fixed-size lists, and structs are projected as Arrow columns.
Supported addition, subtraction, and multiplication read integer and floating-point arguments through the query engine's Arrow projection kernel.
Supported division, comparisons, casts, and text functions read their parameters through the vector expression evaluator.
For a batch with multiple rows, it copies the selected first row without retaining the rest of the batch.
It reuses compatible buffers and normalizes Boolean padding and masked cells when copying is needed.
An update submitted through `GetFlightInfo` passes the bound batch to the transaction path as Arrow arguments.
Prepared update binding accumulates all Arrow batches by column position.
Zero columns mean an unbound execution; columns with zero rows preserve an empty execution batch.

Bulk ingestion supports append-on-exists and create-if-missing, a separate schema field, and one native document operation per input record batch.
A transaction handle buffers those operations together; an ordinary auto-commit connection submits each batch separately.

BeginTransaction, EndTransaction, ClosePreparedStatement, GetSessionOptions, SetSessionOptions, CloseSession, and `xtdb.CommitTransaction` are implemented.
The custom commit action sends the last submitted transaction result before a commit error and includes its await token.
Catalogs, schemas, tables with optional IPC schemas, table types, and the five pinned SQL-info values are exposed.
Schema and table patterns use the Arrow LIKE kernel, including escaped wildcard characters.
SQL-info values use the standard dense-union string and int32 legs with child-local offsets.

== Compatibility qualifications and resource accounting

The `FlightSqlTransaction` prose in `dev/doc/tx.allium` describes a handle reachable from any session.
The pinned `XtdbProducer` instead compares caller identity for transaction and prepared handles.
The native implementation preserves authenticated-session ownership and the shared anonymous owner; the specification retains an open question about that distinction.
Query tickets are independently transferable, as in the reference.

Arrow Java 19 advertises eight standard actions through ListActions, including savepoint, Substrait, and CancelQuery actions that XTDB leaves unimplemented.
The native server preserves that advertisement and returns unimplemented for those actions.
Session actions and the custom commit action remain callable despite their absence from that list.
Call or response-stream cancellation releases query work; the source does not implement a CancelQuery or CancelFlightInfo action.

Transport message sizes and concurrent calls are bounded.
Parameter IPC inspection checks metadata, body extents, buffer extents, and declared decompression sizes before Arrow decoding.
Schemas, record batches and retained parameter streams preserve signed 32-bit decimal precision and scale through the shared IPC codec.
External schemas cannot supply the codec's reserved native annotation, and exported schemas contain only the real decimal metadata.
Each output encoder retains its declared native schema and rejects batches whose full-width metadata differs.
Decoded Arrow owners and encoded `Bytes` retain their reservations through clones and transport delivery.
Metadata enumeration reserves borrowed schema bounds before cloning table bindings; returned catalog snapshots retain those reservations.
The schema and codec estimates are conservative allowances, not a demonstrated bound for every possible nested Arrow representation.
During classification of the complete SQL input, Flight SQL charges token array capacity and an estimate for lexer scratch to the node's memory budget.
A classified control command retains an estimated parsing and binding allowance through schema preparation or execution.
Flight SQL reserves a schema allowance before converting Arrow parameter fields to logical types and holds it through result-schema binding or construction of retained SQL arguments.
Typed batches with zero rows still carry their parameter field types.
Without a bound parameter batch, result-schema binding borrows the prepared parameter types.
HTTP/2, prost, TLS-free tonic buffers, ordinary SQL parser scratch, and scalar-expression peak allocations still require end-to-end accounting qualification.
Leases use the shared microsecond clock and have not been compared with the JVM nanosecond clock at submicrosecond timeout boundaries.
Native server-version metadata uses the Rust package version.
Ticket timestamps use chrono's supported calendar range, which is narrower than the JVM Instant range.
Query metrics count pull and Arrow-encoding failures; transport failures after an encoded message has been yielded are owned by tonic and do not currently increment the query consumer-error counter.

== Regression source mapping

Cases cover captured read bases, effect-free empty-ticket redemption, positional and multi-batch parameters, rebind isolation, authenticated handle and ticket ownership, anonymous cross-session transaction completion, immediate lease expiry, bulk ingestion, metadata union offsets, and shutdown while an upload waits for its first message.
Internal cases cover idle leases and tombstones, nested session calls, credential parsing, cookie selection, Kotlin ticket JSON with required nullable fields, retained Arrow ownership, empty argument distinctions, and malformed IPC extents.

These cases map to `core/src/test/kotlin/xtdb/flight_sql/LeaseTest.kt`, `src/test/kotlin/xtdb/FlightSqlAuthnTest.kt`, `src/test/kotlin/xtdb/FlightSqlAdbcTest.kt`, and the Flight SQL/ADBC Clojure tests under `src/test/clojure/xtdb`.

Interop with Java, Go, Python, R, and ADBC drivers, external authentication, flow-control cancellation races, concurrent expiry/claim races, and every test listed here remain unexecuted qualification work.

Ticket `currentTime` retains the query clock's nanoseconds through serialization and later execution.
The captured snapshot-time cap retains its separate microsecond representation.

An existing anomaly with an absent message uses its `xtdb.api.error` category class name as the general Flight status description.
An empty message remains empty.
Bounded anomaly metadata and custom commit-result errors omit an absent message field.

== Native owned relations

`flightSql.ownedNativeActions: true` enables the owned-relation actions for a compatible installation.
Both actions use the authenticated Flight session on an idle autocommit connection and require database write access.
An embedded server enables `FlightConfig::owned_native_actions` and `NodeOptions::owned_relations`.

Send `rtdb.owned.Create.v1`, `rtdb.owned.ReadPoint.v1`, or `rtdb.owned.Commit.v1` as the Flight `Action.type`.
The body contains a big-endian unsigned 16-bit relation-name length, the logical relation name as ASCII bytes, and one terminated Arrow IPC stream containing exactly one nonempty record batch.
The relation name contains 1–96 lowercase ASCII letters, digits, hyphens or underscores.
The create batch contains unique column names, an `_id` column, and the document fields.
Nullable `_valid_from` and `_valid_to` timestamp fields can supply row validity bounds.
The point batch contains just one non-null `_id` cell.
The connection's authenticated principal and attached database select the owned storage namespace.

Success returns one Flight `Result` whose body is a terminated Arrow IPC stream.
Create success contains one row with non-null signed 64-bit `tx_id` and `system_time_micros` fields.
Point success contains the document columns and at most one row.
Every point response Arrow schema contains `rtdb.owned.present_micros` as a signed decimal microsecond timestamp assigned by the store.
A point result with no rows contains the schema and terminator, with zero record batches.
An unknown relation uses a zero-field schema, and a missing entity in an existing relation uses its current schema.
The Flight limit applies to the complete encoded Action and Result protobuf messages, with a default of 64 MiB.
Failures use the Flight gRPC status and the existing anomaly metadata.

Use `x-xtdb-database` for the initial Multi gateway connection and retain the resulting session cookie or bearer token.
The gateway forwards these actions to the session's attached holder and fences that route at holder movement.
A new holder requires a new authenticated session.
A disconnected create has an unknown outcome and is not automatically retried.

`rtdb.owned.Commit.v1` inserts an exclusive signed 64-bit big-endian Unix microsecond deadline between the relation name and Arrow IPC stream.
The batch contains `_id` and a non-null Utf8 `_op` column with `create`, `replace`, `delete`, or `check`.
Create and replace accept document fields.
Delete accepts an identity and optional validity bounds, with null values for other document columns.
Check accepts an identity and an observation, with null mutation bounds and document values.
Create, replace, and delete apply in batch order in one atomic transaction.

A nullable `_read_valid_micros: Int64` specifies the point to revalidate before mutation.
At that instant, two nulls in `_read_system_micros: Int64` and `_read_event_position: Binary` assert absence.
A present point requires both the observed SQL history coordinate and the 16-byte event position.
The event position contains the original signed 64-bit transaction position and unsigned 64-bit event ordinal, in big-endian order.
A mutation without a valid instant carries no observation.
The point reply includes `rtdb.owned.valid_micros` as signed decimal microseconds.
For a present row it also includes `rtdb.owned.revision_micros` as signed decimal microseconds and `rtdb.owned.event_position` as hexadecimal.
A successful commit reply has the same schema as the create reply.
An expired deadline or stale observation aborts the entire transaction before mutations apply.

`rtdb.owned.Commit.v2` applies the same row schema and reply format to multiple relations in one transaction.
Its body starts with one exclusive signed 64-bit big-endian microsecond deadline and an unsigned 16-bit big-endian group count.
Each group is an unsigned 16-bit big-endian relation-name length, the ASCII relation name, an unsigned 32-bit big-endian IPC length, and exactly that many bytes of a terminated IPC stream.
Each group contains one nonempty batch.
Use up to 32 distinct relations and at most 4096 rows across the request.
With zero groups, the action validates only the deadline and returns its ordered transaction key.
The body ends immediately after the declared groups, or after the count when it is zero.
All observations are checked against the same ordered state before any mutation applies.
Mutations apply in group order and then row order, using the authenticated session's principal and database.

Owned events carry their complete typed key. Its IID identifies the physical locality bucket.
The complete key separates identities within a shared bucket and governs lookups, writes and erasure.
A private owned identity can be a variable-length Arrow Binary value with its complete bytes, including zero and high-bit bytes.
Binary identities sort lexicographically by unsigned byte with a prefix before its extension.
See link:../../../dev/doc/rtdb-factstore-binary-identity.adoc[the FactStore caller contract] for the cutover.

=== Declaring a private relation schema

Send `rtdb.owned.DeclareRelation.v1` with the relation prefix followed by a UTF-8 JSON object of at most 64 KiB.
The object has one `fields` array with up to 128 distinct entries and an optional `validity` policy.
Each entry has `name`, `type`, `optional`, and `nullable`, for example `{"name":"amount","type":{"kind":"i64"},"optional":false,"nullable":false}`.
Field names are nonempty UTF-8 strings of at most 128 bytes, without control characters or a leading underscore.
Supported scalar kinds are `bool`, `i8`, `i16`, `i32`, `i64`, `u8`, `u16`, `u32`, `u64`, `f16`, `f32`, `f64`, `utf8`, `binary`, `date_day`, `instant`, `uuid`, and `decimal`.
An `instant` is a zoned microsecond timestamp.
A `decimal` type also declares `precision`, `scale`, and `bitWidth` (128 or 256).
A declaration is accepted before the relation has stored data or another declaration.
The result has the create reply schema.

For a declared relation, create and replace enforce the field types at the ordering cut.
A field may be omitted only when optional, and an explicit null requires nullable.
A nullable Arrow column can carry both states across rows by including optional `_absent: List<Utf8>` with the names of that row's omitted payload cells.
Each listed cell must be null or undefined in the incoming batch.
Unknown payload fields are refused.
The `explicit` validity policy is the default and accepts supported mutation validity metadata.
The `acceptance` policy begins every Root put or delete at its ordered system time with an open valid end and rejects explicit endpoints.
The `bounded_period` policy requires two finite, strictly ordered mutation endpoints on each Root assertion or retraction.
An ordered transaction may affect one period per complete key. Separate ordered replacements may overlap at the same key, with the latest accepted assertion winning at each valid instant.
Use the same complete entity key across periods and pass the requested valid instant to the held point action.
World mutation and acceptance-only unique occupancy remain unavailable for this policy.
Relations without a declaration continue to infer their schema.

Standard owned transaction replies include the ordered transaction ID, its SQL history coordinate, and its recorded decision clock.
A hosted receiver reads the clock from the original installed outcome by transaction ID and history coordinate before releasing it.
An installation without a hosted clock returns a null decision observation.

=== Holding one owned read cut

Use `rtdb.owned.OpenRead.v3` with an empty body to reserve one present and retain its exact applied catalog.
The result has 16 opaque handle bytes followed by three signed big-endian i64 fields for the SQL system time in Unix microseconds, the ordered transaction ID, and the receiver clock observation in Unix microseconds.
`rtdb.owned.OpenAppliedRead.v5` requests an already-applied hosted catalog from the current recovered holder.
Its input is the 16-byte source installation UUID, a one-byte count from one to four, and that many exact transaction keys.
Each key is a signed big-endian i64 transaction ID followed by a signed big-endian i64 ordered microsecond time.
The final field is a big-endian u64 generation. Use zero outside a reserved audience session.
Its result uses the same held handle and cut format.
The selected transaction must equal or advance both coordinates of each supplied transaction in the same history.
The node pins the exact installed storage catalog in the serving residence, confirms the recovered holder's source identity and checks the supplied transactions in that catalog.
An inexact floor, foreign history, or a cut that cannot be retained is refused without waiting for a new log position.
The handle admits held point, historical point and hosted control reads and applied confirmation.
This operation establishes a data cut. Its ordered time does not give the current physical clock or establish live write authority.

On a placed cell, install the same `--flight-audience UUID/TURNS` on every Flight gateway and holder and bind a separate `--flight-audience-listen ADDR` on each.
The authenticated hosted owner sends the installed value as `x-rtdb-audience-flight-v19` on the audience gateway during its handshake.
The handshake also sends `x-rtdb-audience-reader-seat` as `TURN/ALTERNATE/ATTEMPT`, with a zero-based turn, 0 or 1 and a canonical UUID.
The gateway and holder acknowledge the exact reservation and mint attempt. Ordinary and audience routes are accepted on their own listeners.
The dedicated path has its own TCP acceptance, connection limits, calls, backend HTTP/2 connection pool and holder session seats.
Each turn has two seats. An exact retry under the same credential can recover the live session in that seat.
Another mint cannot take the seat until the original session and its retained I/O release it, including when a close reply is lost.
The original audience bearer can close its own session or held read after the writer attachment is displaced.
A handshake authenticated against the current local attachment can start retirement of a prior attachment's session in its own seat. It waits for the same original resource ownership to drain before it can mint.
The connection and call limits set aside two permits per turn plus two for preparation and cleanup.
Before serving, the holder reserves 16 MiB of execution memory and 16 MiB of cache memory per permit. Both reservations are deducted before the ordinary allocation splits between cache and execution. It refuses startup if the node cannot fund both pools.
Each session uses its own buffer pool on the audience cache budget from initial preparation through applied confirmation.
Audience queries use local scans. The holder requires an uncached view of the live writer's exact S3 storage attachment for the installed source.
That view shares the attachment's object mapping, custody and serving key and bypasses the ordinary SSD cache and its fill queue.
Provider object reads use a distinct S3 HTTP client and credential cache, including when retained I/O outlives its caller.
The configured source and its attached archive open that client with their own credential provider. A remote store without the client refuses the scoped read.
Whole objects read into the buffer pool must match the reserved length. The pool funds the retained bytes and the temporary ciphertext and archive buffers before fetching the body.
The reservations remain held while admitted provider work drains after cancellation. The read view requires a whole-object or scan-range reservation for every body.
Native trie data uses 64 KiB plaintext frames. A point scan can read its footer and pages without decrypting the rest of the file. The object header authenticates the length and content identity, and every selected frame authenticates its key, identity and position.
Retained archives bind the encrypted frame header in their manifest and authenticate only the requested frames before resealing them for the serving key. Native trie data and retained archives must be written in this format.
Each audience action has cumulative ceilings of 256 object-store requests, 32 MiB of requested object bodies, 4 MiB of provider metadata envelopes, 65,536 scan items and 64 MiB in decoding bounds.
An applied hold additionally limits the whole turn to 64 Flight actions, 4096 object-store requests, 512 MiB of requested bodies, 64 MiB of provider metadata envelopes, 1,048,576 scan items and 1 GiB in decoding bounds.
Each action spends both allowances, including detached provider work.
Closing the original hold uses cleanup capacity even after the hold exhausts its work allowance.
The object reader reserves a 16 KiB metadata envelope separately from each requested body, including HEAD, and checks complete range responses under the reserved body length.
The holder charges these before the counted work. Admitted provider tasks retain the allowance and the call and session permits until their work drains. Listings, unbounded body reads and the ordinary object transport are unavailable during the action.
Live trie scans locate rows under the audience execution budget without consulting the ordinary leaf caches.
The holder refuses the handshake if the opened residence needs per-read registration for a legacy object reference or serves a retained archive from a local volume. An admitted S3 archive uses the custody hold acquired when the attachment opened.
The installed source holder loads pack locations before accepting a session. Its own block publications register their locations before the catalog can be captured. A scheduled object lookup never searches for more packs or adopts a relocated pack.
Each audience session owns one retained-read slot. A new applied open must advance that session's generation and retires the previous handle before starting the new read.
A delayed open with an earlier or repeated generation cannot displace the replacement. CloseSession and session expiry both retire its current hold. Their budget charges cover native session state, decoded action bodies, pinned query contexts, output encoding and retained replies.
The audience handshake and subsequent actions use the reserved admission.
The holder sets aside 12 MiB per reserved connection outside body accounting, with four HTTP/2 streams, an 8 KiB header-list limit, a 512 KiB request message limit and a 2 MiB reply limit.
The gateway sets aside 2 MiB per reserved peer connection and 2 MiB per forwarded call.
Its audience upstream has bounded HTTP/2 windows and keeps no idle routes.
An audience session can read a forward live Root range of up to five nominations through ReadHeldRange.v2 on its prepared hold.
It can also read that range at a retained system cut less than 60 seconds before the hold through ReadHeldRange.v4, with the valid instant equal to the system cut.
The historical scan verifies relation coverage and spends the original hold's aggregate work allowance.
Its range request permits an exclusive continuation and has a 16 KiB carrier ceiling.
Applied confirmation on the same prepared session can check the exact partition publication marker against both catalogs.
The gateway resolves the placement at handshake, then forwards authenticated session actions to the sealed holder address.
For each audience data action the holder reads the live member and current deployment over a DynamoDB client with its own credential provider.
It checks the writer epoch, recovered checkpoint and exact attached database. A holder whose directory cannot install an audience read transport refuses audience startup.
Applied acquisition and confirmation also check journal leadership on the holder's configured `--audience-journal-port`.
Each logkeeper serves this port with `--audience-authority UUID/TURNS` and `--audience-authority-listen ADDR`.
The connection and frame sizes are bounded. Each success confirms the exact journal, replica stream, active ensemble and durable writer epoch.
A pending fence change refuses immediately until it is durable. Ordinary append and history-read queues do not carry these authority checks.
Closing a local hold or session only releases resources. The directory, journal quorum, network, object storage, and scheduler still have service obligations.

Before its first open, a reserved session must call `rtdb.owned.PrepareAppliedRead.v2`. The body is the same source and exact transaction floor as an applied open, without the generation. After registering the captured catalog in the directory, the action returns one unsigned eight-byte big-endian remaining lifetime in microseconds, bounded by both the catalog pin and the session. Anchor this duration to the start of the preparation request on the caller's monotonic clock to reserve a conservative full observation window. Audience sessions have a nonrenewable 180-second ceiling from the handshake. Retained work keeps its original permits through cancellation and drain.
The registration is session-bound and expires after 180 monotonic seconds. A read or confirmation shares it only for a catalog at or after the registered cut in the same attachment, storage version, storage epoch and replica epoch.
An older registration keeps the retirement floor from passing this cut. In-flight snapshots keep their own references until reads and provider I/O drain.
A changed or expired preparation requires a new session. Opening and confirming a hold never falls back to a new registration on a reserved session.
Holder confirmation, exact transaction checks, and session generations still apply to each acquired cut.

The reservation admits preparation, applied open and confirmation, held point and historical point reads, hosted control reads, and closure of the hold or session.
The gateway routes only action RPCs on a reserved session.

`rtdb.owned.ConfirmAppliedHosted.v6` takes the 16-byte original held handle, the same source and transaction floor input, an exclusive signed big-endian i64 Unix microsecond cutoff, a point option, and the normal hosted control groups.
The point option starts with one byte: zero for a control-only read, one for a raw Utf8 key, and two for a complete typed handle.
For a point, send the ordinary relation prefix, the big-endian u16 key byte length, the key and a signed big-endian i64 valid instant in microseconds.
The Utf8 key is 1 to 4096 bytes.
For a typed point, the length includes the handle tag and may be 2 to 4097 bytes.
A Binary fact handle contains tag byte `04` followed by the raw identity.
An included point ends with a zero byte for absence or one byte of value one followed by its signed big-endian i64 expected revision and the 16-byte original event position.
The original handle must come from `rtdb.owned.OpenAppliedRead.v5`.
Every control must be a check from the placed attachment's installed allowlist.
The point must be an ordinary Root point at the original held valid instant.
The node proves the supplied floor and the original transaction on one newly pinned applied catalog.
It checks the supplied control and point revisions and absences on the original and newly pinned catalogs.
Success returns three signed big-endian i64 values: the captured transaction ID, its SQL system time, and the receiver clock observation that satisfied the cutoff.
A changed control or point returns one zero byte.
The node refuses unproven cuts and checks the physical clock again before returning.
This action appends no transaction and authorizes no write.

Governed data pages carry a complete typed `_entity_key` on put, delete, and erase events. A native point seeks the canonical IID bucket and resolves only its exact key.
Older governed pages without the key require a reset. Compaction resolves each complete key independently inside an IID bucket. Covered search and ordered paths use complete identities.

Send `rtdb.owned.ReadHeldPoint.v1` with those 16 handle bytes followed by the ordinary ReadPoint action body.
The Arrow response uses the held present and valid instant on every call, including missing rows.
`rtdb.owned.ReadHeldPoint.v2` uses the same framing with exactly one Arrow row and two columns, `_id` and `valid_micros: Int64?`.
A null `valid_micros` uses the held default. Otherwise it selects one business-valid microsecond within the original held system cut.
`rtdb.owned.valid_micros` echoes the selected instant even when the row is absent, and `rtdb.owned.present_micros` stays at the held present.

`rtdb.owned.ReadHeldAbsentKeys.v1` takes the held handle, relation prefix and one Arrow batch with 1 to 64 keys and a 96 KiB total request bound.

`rtdb.owned.SearchHeld.v7` takes the 16-byte held handle, a signed big-endian i64 valid instant or `i64::MIN` for the held present, then a big-endian u32 overlay byte length and the optional Arrow overlay bytes.

An overlay requires the configured placed hosted-control owner, the live Root validity and requested evidence. `rtdb.owned.NearestHeld.v4` ranks clear stored vectors by exact cosine distance at a held cut.
It takes the 16-byte held handle, a signed big-endian i64 valid instant or `i64::MIN` for the held present, then a big-endian u32 overlay byte length and the optional Arrow overlay bytes.
Next comes a filter count byte F (0 to 8) and a big-endian u16 partition count (1 to 32).
Each partition is a relation prefix, a vector column prefix and F filter column prefixes, all framed like relation prefixes; relations are distinct.
Each filter then carries a big-endian u16 value count (1 to 64) and that many values, each a big-endian u16 length (at most 1024) and its bytes.
A big-endian u16 k (1 to 256), an evidence flag byte (0 or 1) and a route byte (0 exact, 1 approximate) follow, then a big-endian u16 dimension count D (1 to 4096) and D big-endian IEEE-754 f32 probe components, which must be finite with a nonzero norm.
A vector column holds a list of numbers; a missing cell or a zero-norm vector is not a candidate, and a vector with other than D finite components refuses with `rtdb.owned/nearest-dimension`.
A filter column holds Binary values; a row passes when every filter column is present and byte-equal to one of that filter's values.
The distance is `1 - dot(a, b) / (|a| |b|)` in f64, and the reply keeps the first k candidates by ascending distance, then complete typed identity, then partition ordinal.
The scan admits at most 100,000 candidates and otherwise refuses with `rtdb.owned/nearest-scan-limit`.
The reply has `_id` as in SearchHeld.v7, `distance: Float64` and `partition: UInt64`, with the held present and valid instant, `rtdb.owned.search_total` (the candidates that passed the filters) and `rtdb.owned.search_witnesses` as in SearchHeld.v7.
`rtdb.owned.search_scope` is the lowercase hex SHA-256 of the domain tag `rtdb.owned.nearest.held.v2` and a NUL byte followed by the complete request body.
With the approximate route, a partition whose relation has an approximate vector path over its vector column ranks only the shortlist of that path's published generations and frontier (`vector.allium`), widened until k candidates pass the filters; other partitions, and any partition whose shortlist exceeds its budget, rank exactly.
The distances and order remain exact; the result may omit true neighbours.
`rtdb.owned.nearest_approximate` is `1` when any partition ranked a shortlist and `0` otherwise.

`rtdb.owned.DeclareVectorPath.v1` takes a relation prefix and one Arrow row of `_id` (the path name), `column` (a stored list column), `dimensions` (Int64, 1 to 4096) and `recall` (Float64 in (0, 1]).

`rtdb.owned.HybridHeld.v4` fuses a SearchHeld.v7 text ranking and a NearestHeld.v4 nearest ranking of the same relations at one held cut by reciprocal rank fusion.
It takes the 16-byte held handle, a signed big-endian i64 valid instant or `i64::MIN` for the held present, a big-endian u16 limit, then two overlays, each a big-endian u32 byte length and optional Arrow bytes (the text overlay as in SearchHeld.v7, then the vector overlay as in NearestHeld.v4), then a big-endian u32 byte length and the SearchHeld.v7 request that follows its overlay, and last the NearestHeld.v4 request that follows its overlay.

`rtdb.owned.change_coverage_micros`, `rtdb.owned.change_position` and `rtdb.owned.change_edge_kind` together encode the continuation edge.
Resume from the complete edge to preserve publications that share a system time.
An empty covered page has no rows and carries the already-known held present in `rtdb.owned.present_micros`.

=== Retiring an owned relation

An admitted Root `rtdb.owned.DecideHosted.v4` can retire Root relations together with its catalog changes.
Send one row in the retired relation's fact group with `_op: Utf8` equal to `retire-relation`, `_id: Utf8` equal to the relation name, and `retain_micros: Int64`, the 0 to 100-year history the relation keeps after retirement.
The transaction records the retirement in the principal's retired catalog and deletes the relation's ordered, search and spatial paths from their catalogs.
The declaration stays, so historical reads keep resolving the relation's schema until collection reclaims it.
Any later write, declaration or path naming the relation, and any other operation on it in the same transaction, aborts with `rtdb.owned/relation-retired`.
Retiring a relation again with the same retention changes nothing; another retention conflicts.
Once `retain_micros` has passed and no undropped world forked before the retirement names the relation, trie collection reclaims its data, journal and constraint tables.

=== Declaring owned partition capacity

`rtdb.owned.DeclareCapacity.v2` takes the relation prefix and a terminated Arrow IPC stream with one batch and one row.
Its fields are `column: Utf8`, `prefix_bytes: Int64` (0–4096), `cap: Int64` (positive), and `when: Binary`.
`when` contains zero to four equality predicates in column-name order. Each consists of a one-byte UTF-8 column-name length and the name, followed by a big-endian u16 value length and the exact nonempty Binary value (up to 2052 bytes).
An owned Root relation may declare up to 16 distinct projection and predicate combinations.
A populated relation can declare its first cap when its schema requires validity from acceptance with an open end and has no creation lifetime.
The resolver initializes the new rule's covered counters from the final visible rows at the declaring revision.
If a prefix already exceeds the proposed cap, the transaction aborts with `rtdb.owned/capacity-already-exceeded`.
Redeclaring a projection with the same predicate and prefix width changes its maximum while retaining its counters.
Lowering the maximum checks the relation's final membership at the declaring revision, including any removals in that transaction.
An admitted Root `rtdb.owned.DecideHosted.v4` can co-order capacity declarations with its catalog changes.
Send each declaration in the target relation's fact group with `_op: Utf8` equal to `declare-capacity`, `_id: Utf8` equal to the projection column, and the four fields from DeclareCapacity.v2.
The hosted batch must check the observed `bj_installation` authority row.
The facts, counters and catalog changes commit together after the authority, catalog and capacity conditions all succeed.
Held Original replay reinstalls complete-key capacity declarations at their recorded source transaction.
The resolver checks that the replay reproduces the source relation's write frontier and exact counter effects before accepting the replay receipt.
A held replay receipt carries `commit_positions` from the archived transaction.
When the list is nonempty, the submitted governed events must follow that order, preserving sparse positions left by erased assertions.
The resolver rejects extra or missing governed events before accepting the receipt.
Successful declarations return the same transaction-key Arrow row as Create.
Zero counts complete Binary keys. An empty complete key charges a single relation-wide bucket. Positive widths count prefixes of that length. Keys are limited to 4096 bytes.
Each qualified projection and partition has its own counter. A row charges the rule only while all its predicates match. One shared relation frontier certifies all counters.
Writes to the governed root must start at ordered present and have an unbounded valid end.
The resolver applies same-transaction releases and claims together, then commits the facts and counters atomically.
A capacity conflict or uncovered counter frontier aborts the commit.
World writes to a governed relation refuse until the world can account for inherited occupancy.

=== Holding a historical root publication

`rtdb.owned.OpenReadAsOf.v2` takes the 16-byte fresh held read handle and a signed 64-bit big-endian requested system instant in microseconds.
Next come the publication relation prefix, a big-endian unsigned 16-bit marker byte length followed by that UTF-8 marker, and a big-endian unsigned 16-bit scope count followed by that many relation prefixes.
The scope comprises one to 32 distinct preadmitted root relations, including the publication relation.
Each selected relation needs a covered journal floor and head or a proven empty history.
The marker is read at the requested system cut and business-valid instant.
Its visible row must cover all valid time.
The derived handle uses the marker's original transaction position and history time. The highest eligible position breaks a history-time tie. Every selected relation must cover this exact cut.

The response is one byte zero for a covered absent marker. A successful reply carries the 16-byte handle followed by signed 64-bit big-endian history time, transaction position and query time.
Use the handle with ReadHeldPoint.v1, ReadHeldPoint.v2, ReadHeldValidDuring.v2, ReadHeldVersions.v2, ReadHeldRange.v4, or CountHeldRange.v2 in the declared scope and CloseRead.v1 to release it.
The default business-valid time is the selected marker time.
The derived handle shares the original generation, lease and expiry and may serve requests after the fresh handle is closed.
It carries no commit evidence.

`rtdb.owned.ReadHeldRootCutPoint.v1` takes the held handle, signed 64-bit history time and position, and a side byte (0 before, 1 inclusive). The remaining bytes carry the clear relation and typed point with an explicit business-valid instant. It retains the original catalog, journal floor and purge checks, and narrows the scan by position on both sides. The Flight reply uses the named publication's history time on both sides.

The corresponding Root path touch action `rtdb.owned.ReadHeldPathTouch.v2` places the signed 64-bit transaction position immediately after the handle. It certifies the addressed touch from the selected journal group and checks the path declaration across the two positioned reads.

`rtdb.owned.LookupHeldPublication.v1` takes the original 16-byte handle, relation prefix and a selector byte.
Selector 0 uses the latest publication of the relation in the hold.
Selector 1 carries a relation-local unsigned 64-bit journal sequence.
Selector 2 carries a signed 64-bit transaction position and history time and requires an exact match.
Selector 3 carries a signed 64-bit history cap and selects the last eligible entry in the hold.
All fields are big endian.
The result is empty for a covered absence or carries the unsigned 64-bit sequence, signed 64-bit position and history time.
The journal inventory and read entitlement govern lookup.

`rtdb.owned.OpenReadAtPublication.v1` uses a signed 64-bit position followed by history time in place of the requested time in `OpenReadAsOf.v2`.
The selected marker must exist at exactly the requested position.
The hold and result fields follow `OpenReadAsOf.v2`.

=== Fixed-valid range observations

`rtdb.owned.DeclareFixedRange.v1` takes the relation prefix and one terminated Arrow IPC batch with one row.
The fields are `path: Utf8`, `column: Utf8`, and `valid_micros: Int64`.
Declare the relation's schema first and the fixed range before its first fact event.
This declares one immutable path on the authored Binary column followed by the full native Utf8 or Binary `_id`, and returns the usual transaction-key row.
The maximum timestamp cannot be used as a valid instant.

`rtdb.owned.ReadHeldRange.v3` adds a seventh `valid_micros: Int64` field to v2.
It traverses the covered path at that valid instant on the held system cut and uses the same handle and witness nonce in Commit.v3.
When the declaration and valid instant match and `after` is absent, the exact witness protects the full requested half-open span, including a covered empty result and the unreturned part of a capped page.
The ordered resolver validates both old and new full keys through at most 64 intervening dense journal groups.
A group omits exact sides when its relevant IDs or keys fall outside the supported type or byte limits, or when its evidence could not be captured.

`rtdb.owned.ReadHeldRange.v4` and `rtdb.owned.CountHeldRange.v2` add a `system_micros: Int64` field to v3 and v1 respectively.
The system cut must be covered by the relation history on a fresh hold or equal the selected cut on a derived hold.
Both actions require a covered index revision and return the requested system and valid instants in the reply metadata.
Historical pages require the path to project `_id` for ordered erase validation.
Historical pages and counts carry no commit witness.

Held range and count actions can cover a cut by replaying up to 4096 uncheckpointed events from the captured relation, including up to eight flushed source files.
This also covers relations that have no checkpoint yet when the retained sources supply the complete history.
Before the first fact, the held declaration supplies the path field types and the exact empty result.
An incomplete or over-limit replay yields no rows, count, or witness.
The relation-frontier check still applies to moving-valid reads, continuation reads, and reads whose exact witness or intervening coverage is unavailable.

=== Committing checked hosted control rows with owned facts

`rtdb.owned.DecideHosted.v4` is enabled only for a live placed connection authenticated as `flightSql.hostedControls.owner` with `flightSql.ownedNativeActions` enabled.
The operator's `flightSql.hostedControls.relations` sequence names the admitted ordinary `public.bj_*` tables.
All six hosted publication actions start with the 40-byte installed authority proof.
It contains a signed big-endian Int64 claim revision in microseconds, the 16-byte installation incarnation and the 16-byte writer grant in that order.
The primary controls must include one check-only `public.bj_installation/authority` row with that exact revision.
The resolver compares the proof with the live authority at the ordered predecessor on the authenticated placement.
A refusal alternative shares that check.
With hosted controls installed, generic placed Flight fact writes can address only `fact_layout_readiness`.
The optional sections and the ordering deadline precede the ordered fact and control groups as described below.
Both sections use the Commit.v2 relation-group sequence framing. The control section has at least one group. A check-only transaction may omit fact groups.
Fact groups may repeat a relation to preserve run order. The combined sections admit at most 32 distinct fact and control groups and 4096 total rows.

Each control group contains one terminated Arrow batch with distinct field names.
Every row has `_id: Utf8` and `_expected_micros: Int64?`. Replacement rows supply a complete image in the already installed ordinary column types. A row with `_check_only: Boolean` set to true carries only the ID and expectation and leaves the table unchanged.
A null expectation requires exact absence.
An existing row must contribute one exact valid slice from epoch to infinity at the ordered base.
Control replacements use the same epoch-to-infinity interval.
The resolver checks all control and fact observations before any mutation and aborts both sets of effects on failure.
Use an absent-checked unique receipt key as one of the writes when the host needs to recover an indeterminate response.
The response is the ordinary committed transaction-key row.

`rtdb.owned.ReadHeldHostedControl.v2` uses the same installed placed owner
and ordinary control allowlist as the commit actions. Send the original live,
underived 16-byte held read handle, one ordinary control table prefix, then
one terminated Arrow IPC batch with one row `_id: Utf8`. The ID is complete
and bounded to 4096 bytes. No time override is accepted.

The response is ordinary point IPC, with the original held present and
`valid_micros` equal to zero. A hit is one row with the complete ID,
ordinary control fields, and its original system revision in point metadata.
Native writes to the Root receipt table stamp their local transaction ID.
Reading a stamped receipt also returns `rtdb.owned.receipt_tx_id` as point metadata.
Pair it with the system revision to name the exact transaction in applied confirmation.
An installed table with a covered absent row returns its typed schema without
a revision or rows. Send that revision or null as `_expected_micros` in a
subsequent checked hosted commit. A missing table or a non-epoch valid slice
refuses the read.

After the authority proof, `rtdb.owned.DecideHosted.v4` carries one flags byte.
The low six bits signal final counts, held-world reads, a refusal alternative, a physical journal cutoff, an offered clock slot and a funded mutation clock, in that order.
The optional 16-byte slot handle or length-prefixed funded offer comes first.
The optional refusal comes next as a length-prefixed section containing a length-prefixed fact group stream and the hosted control group stream.
An optional held-world prefix follows, using the original handles and witness nonces.
The optional ordered-present count conditions precede the durable Root range evidence.
Its wire prefix is a big-endian unsigned 16-bit count followed by that many UTF-8 tokens, each preceded by its big-endian unsigned 32-bit byte length.
`rtdb.owned.SealHostedRanges.v1` accepts the original held handles and issued witness nonces and returns the length-prefixed tokens in the same order.
The authenticated token binds the principal, history, original transaction, relation and range, event frontier, and expiry.
Another eligible receiver can validate it after the original Flight session closes.
The deadline follows, with the physical cutoff and receiver clock certificate digest present when requested.
The final streams contain the primary facts and hosted controls.

`rtdb.owned.DecideHostedPacked.v1` uses the `DecideHosted.v4` envelope and controls, including the original refusal groups.
Its primary facts section starts with a big-endian u16 run count and u16 stream count, followed by one u16 stream index per run in original execution order.
Each stream has the ordinary relation and u32 IPC length framing and carries one Arrow batch for each scheduled occurrence of that stream.
The owner expands this schedule before the shared decision path so interleaved operations keep their original ordinals.

`rtdb.owned.DecideHostedImportPage.v1` uses the same authority, deadline, range evidence, and control checks as an ordinary live `DecideHosted.v4` with zero flags.
Its length-prefixed fact stream begins with a big-endian u16 placement count and that many pairs of big-endian u16 values.
Each pair names the number of inline runs preceding it and the number of consecutive page rows it consumes.
The first coordinates strictly increase and the counts together consume the complete page.
The schedule is followed by one usual relation and length-prefixed Arrow batch, then the usual ordered group stream for the inline effects.
The shared batch has up to 64 creates and up to 128 total create and check rows on one Root relation.
The owner restores the original run and row order and field presence before passing the effects and hosted controls to the ordinary decision path.

`rtdb.owned.ValidateFreshHosted.v1` starts with the history UUID and one to four exact transaction positions, followed by the durable Root range prefix, the exclusive deadline and the fact and control group streams.
It accepts only point and control equality checks and issued durable range evidence.
An ordinary fresh Flight receiver acquires and applies a protected journal cut, verifies the supplied evidence and returns the covered transaction and receiver observation, or refuses release.
The receiver can be an enrolled subscriber while the writer grant is vacant.

`rtdb.owned.OfferClockSlot.v2` takes a 16-byte placed Root hold handle and returns the first one-second grid reading at least five hundred milliseconds after the held receiver clock.
The reply contains the signed big-endian microsecond reading and the original 40-byte receiver observation.
An accepted receipt retains that observation alongside the actual receiver observation and the offered through-position.
A successor authenticates continuation of the same clock domain with nondecreasing epoch, sequence, and time.
The reading is a signed big-endian microsecond count.
`rtdb.owned.DecideHosted.v4` and `rtdb.owned.DecideHeldWorlds.v3` can use that reading with the original handle.
The placement and session must still own the hold.
The source append must reach the offered reading. The receiver's sampled clock must be in the half-open second starting there.
A committed receipt keeps the exact reading and original held position alongside the unrounded receiver observation.
Flight waits outside the writer order if the request reaches the server early.
A missed offer returns `rtdb.owned/clock-slot-missed` and orders no application writes.

The refusal alternative uses the original attempt markers, receipt slots and dispatch retirement.
The receiver also binds retained decision and impact rows to the offered decision.

The resolver discards the candidate buffer and orders the alternative under the same transaction key, with the original Root, control and retained-world guards.
A receipt-only request with a final count condition moves the Sync receipt head for either result.

This action supports checked replacement and exact absence insertion for hosted controls.

An installed held restore may combine its exact writer, archive, hold, unsealed state, and predecessor checks with an absent-checked original transaction receipt.

Copied native Root assertions retain their source valid intervals, including the original creation and expiry of a lifetime row.

Generic SQL keeps the existing private relation boundary.

== Catalog publication and watches

The normal owned listener advertises `rtdb.owned.PublishCatalog.v1` and `rtdb.owned.WatchRelation.v1` through ListActions.
It also advertises `rtdb.owned.ScanCatalog.v1`, which accepts a catalog statement with one Arrow argument row and the original SQL snapshot token as its first argument.
It reads through that admitted snapshot under the caller's database authority and streams one result per Arrow IPC message when the request offers `x-rtdb-owned-ipc: stream-v1`.
The existing catalog index stores its original hex keys for mixed client releases.
Both actions use the database of the authenticated Flight session.

For publication, the protobuf body has repeated preceding SQL statements (field 1), the Arrow IPC stream (bytes field 2) and an optional trailing marker statement (field 3).
Each statement carries its SQL text (string field 1) and optional one-row Arrow IPC arguments (bytes field 2), with fields named `_0`, `_1` and so on.
The write stream has one batch with `_id` Utf8, `world` Int64, `key` Binary, `idx` Int64, `op` Dictionary(Int32, Utf8), `value` nullable Binary, `number` nullable Int64, `label` Dictionary(Int32, Utf8), `units` List(Utf8), and `stamp_offsets` List(Int32).

A single result carries transaction ID (int64 field 1), system time in Unix microseconds (int64 field 2), await token (string field 3), committed (bool field 4), error code (string field 5) and error message (string field 6).

For the watch, the protobuf body has a public relation name (string field 1) and an optional previous event count (int64 field 2).

A call with a previous count waits until it differs or until 20 seconds elapse, at which point it returns the previous count.

== RTDB v1 Flight service

The public protobuf descriptors are in link:../../proto/rtdb.v1.proto[rtdb.v1] and link:../../proto/rtdb.admin.v1.proto[rtdb.admin.v1].
Select the database with `x-xtdb-database` and discover the route's features and limits via `DoAction` with type `rtdb.v1.Capabilities`.
Action bodies and replies are serialized protobuf messages.
For `Query` and `Changes`, put the request in a `google.protobuf.Any` and use its serialized bytes as a `DoGet` ticket.
Flight sends the Arrow IPC schema and batches first, then one metadata-only `FlightData` carrying the corresponding protobuf trailer.
A failed call carries a protobuf `Error` in the `rtdb-error-bin` status detail.

`Query` accepts a read-only SQL statement and an optional Arrow IPC stream containing one positional parameter row.
Use a deterministic total `ORDER BY` for queries whose results span pages and repeat the request with the returned continuation and the desired page limit.
The request's basis and query clock are fixed across its pages.
Tracking returns an authenticated claim covering the database at the reported basis.
The current implementation accepts `main` with the merged layer.
Query and Changes tokens are scoped to the serving attachment and process.
The temporal read driver encodes system-time boundaries as positions in the shared basis format.
Claims use the shared claim format with the process's sealing authority.

`RTDB_SEARCH(table, column, query[, analyzer])` returns matching rows with `_score` in descending score order.
`RTDB_NEAREST(table, column, vector, limit)` returns the nearest vectors with `_distance` in ascending cosine-distance order.
`RTDB_HYBRID(table, text_column, query, vector_column, vector, window, limit[, analyzer])` fuses the first `window` rows of the exact RTDB_SEARCH ranking and of the exact RTDB_NEAREST ranking at one snapshot by reciprocal rank fusion with k = 60.
A row's `_score` is the sum of 1 / (60 + rank) over the windows that hold it, text first, with ranks from 1, and the function returns the first `limit` rows by descending `_score`.
These functions break ranking ties by internal row identity.
`MATCH`, `SEARCH_SCORE` and `COSINE_DISTANCE` are also available as SQL expressions.
`MATCH`, `SEARCH_SCORE`, `SEARCH_TERMS` and `SEARCH_LENGTH` take an optional analyzer name as a string literal after their other arguments, `simple` by default.
`CREATE SEARCH INDEX name ON table (columns) WITH (analyzer = 'english', history = false)` indexes under that analyzer, and a search index serves only queries that name its analyzer.
The analyzers are `simple`, `standard`, and `dutch`, `english`, `french`, `german`, `italian`, `portuguese` and `spanish` with their `_stop` forms; dev/doc/fts.allium specifies them.
`CREATE VECTOR INDEX name ON table (column) PARTITION BY (columns) WITH (dimensions = n, method = 'ivf', recall = r)` declares an approximate index; `DROP VECTOR INDEX name` retires it.
A query opts into the approximate route by adding `APPROXIMATE_NEAREST(column, vector, limit)` to the predicates of `ORDER BY COSINE_DISTANCE(column, vector), _iid LIMIT limit`.
The route probes the published generations, ranks the rows above their frontier exactly, and returns exact distances for candidates that may omit true neighbours.
Without an index, or when the filter is selective, the same query ranks exactly.
Use `FOR SYSTEM_TIME` or `FOR ALL SYSTEM_TIME` for transaction-time reads within the query cut.

`Changes` requests a set of tables and reports open and closed system-time history intervals.
Each output row carries a table, a system time, the interval boundary direction, and selected Arrow IPC key or row images.
The limit counts whole system-time groups.
Ascending requests advance `after` to `through`, and descending requests move `until` down to `through` while retaining the original `after`.
A cursor below the retained checkpoint floor returns `rtdb/cursor-expired`.
With the `changes.progress-only` capability, a request can set `progress_only` with `IMAGES_NONE` to receive only the schema and normal coverage trailer.
Progress-only requests use the same table readers, group limits, interval bounds, and wait conditions.

By default, a present `key_ipc`, `before_ipc`, or `after_ipc` cell is a standalone one-row Arrow IPC stream.
When the route advertises `changes.images.stream-v1`, a client that supports shared image streams can send the `x-rtdb-changes-images: stream-v1` metadata header with an image-bearing `Changes` DoGet.
The response echoes that header when it selects the shared carrier.
For an offered carrier without an exact acknowledgement, retry without the request header to obtain the default representation.
In a shared response, read each image column separately for each outer record batch.
If row zero is null, that image is absent throughout the batch.
Otherwise row zero holds an Arrow IPC stream with one single-row record batch per outer row, in the same order, and remaining cells in that column are null.
A shared response can include single-row outer batches, for example when the image schemas or presence differ between adjacent changes.
Both carriers use the same image projections, whole-group limit, and coverage trailer.

Default mode serves the same wire operations on local or shared logs.
The route advertises `query.linearizable` when it can establish a fresh barrier.
Branch selectors, timed writes and administrative actions require their corresponding feature implementations.
