= Native Flight SQL and ADBC transport

`rtdb-flight-sql` serves Arrow Flight SQL through native tonic HTTP/2 and Arrow IPC.
ADBC Flight SQL drivers use the same `rtdb-node` sessions, SQL preparation, query cursors, transaction resolver, and authentication as the PostgreSQL frontend.
The source and regression cases remain uncompiled and unexecuted during Phase 1.
Schema descriptions retain the supplied physical parameter fields, while query execution opens their signed vector view.
Retained parameter IPC remains lossless.
Prepared updates retain uploaded Arrow parameter batches through transaction buffering and encoding when the batch layouts agree.
Separate uploads of the same statement can have different schemas when they are coalesced in a transaction.
The source encoder aligns compatible argument vectors by position in Arrow and preserves the order of the argument rows.
Bulk ingestion retains compatible Arrow document columns during source-log encoding, replay and transaction staging.
This includes lists, fixed-size lists and structs with compatible child fields.
When a struct gains fields between compatible Arrow uploads, source encoding joins those fields in Arrow, including structs inside lists.
Arrow batches targeting the same table can share a source-log document layout when their common columns agree and other columns are absent.
When the same transaction also contains compatible row-backed puts for that table, source encoding builds vectors from those rows and combines them with the uploaded vectors in transaction order.
Columns with compatible union legs share a dense union when their scalar types or nested container kinds differ between batches.
Null and missing values use the union's null leg.
Uploads can gather multiple tags for the same value layout into one Arrow child, including signed execution aliases.
When a union with one value layout is normalized, the typed Arrow array's validity represents null entries.
The typed document writer handles layouts that require cell conversion.

== Composition and ownership

`ServerDriver::bind(FlightConfig, Node, Arc<Authenticator>)` binds an insecure listener and returns its `ServerHandle` and unstarted driver.
The handle exposes the bound address, current status, status subscription, and shutdown request.
The caller owns `run`, requests shutdown, and joins the driver before closing the node.
Dropping a running driver future does not satisfy that join obligation.
`bind_with_clock` injects the lease clock; the ordinary constructor uses the wall clock.

The Active Object is the server driver, which selects listener completion and lease sweeps.
Tonic owns its transport connection tasks and joins their connection watchers during shutdown.
The driver's socket adapter observes cancellation during reads and writes, including a peer that stops consuming responses.
The driver also waits for the admitted-call monitor to reach zero before reporting completion.

Service methods and response streams are passive caller-owned work.
The stream advertises the prepared result schema and conforms runtime pages through the passive `rtdb-columnar::DeclaredBatch` adapter.
Columns that already match their declared field retain their Arrow buffers when the adapter conforms the rest of the page.
Compatible nested field ordering and dense union identifiers can change while retaining the source value buffers.
This follows the pinned Flight producer's ADBC `ArrowReader`, including NULL endpoint vectors under advertised timestamp fields.
The encoder checks the complete declared schema before encoding physical buffers, including signed decimal precision and scale metadata.
Schema and record-node regression sources remain unexecuted.
An admission owner retains its semaphore permit through authentication, execution, and the final response stream.
An acquired-session guard releases its in-use count even when a call is dropped during identity revalidation.
Sessions own their catalog selection and per-database connections.
A transaction handle owns a dedicated connection.
A prepared handle owns SQL, its session/database or transaction scope, and the retained IPC parameter batch.
A connection resource serializes access to its `NativeSession`; expiration cancels borrowed work and releases the connection when its final borrower leaves.
`ServerStatus` is a separate monitor of call counts and live registry sizes.

Session, transaction, and prepared registries retain expired tombstones for one further idle period.
A presented session renews from its initial unclaimed timeout to its normal idle timeout.
A session with an in-flight call cannot expire; releasing the call restarts its idle measurement.
Transaction and prepared handle lookups renew their leases, and an end action claims a handle exactly once.
Session closure leaves dedicated transaction handles independently owned.

== Authentication and sessions

Authentication accepts Basic, Client, Bearer, and anonymous trust calls according to `rtdb-auth` rules.
A placed endpoint uses the `x-xtdb-database` header on the first authenticated call to bind the session to its local deployment.
Use `rtdb-multi gateway --flight-listen ADDR` and the cell secret to route to the local cell's writer over the private network.
Non-loopback Flight SQL gateways require TLS.
The gateway sends proof of the original peer address so the writer applies the same authentication rules to forwarded calls.
After a writer move, establish a new Flight SQL session.
The transport peer address comes from the accepted socket.
Each authenticated session retains a principal and an HMAC of the complete original authorization header, using a fresh service-lifetime secret.
A repeated Basic or Client header must match that MAC.
A cookie and bearer token supplied together must name the same session.
Every presented session revalidates its principal before work begins.

New sessions return the `arrow_flight_session_id` cookie.
Authenticated sessions also return an `authorization: Bearer` header.
Unknown or expired bearer sessions fail as unauthenticated; cookie sessions fail as not found.
The per-call `x-xtdb-database` selector takes precedence over the session catalog, then `xtdb`.
Session options expose catalog and the fixed `public` schema, with per-option invalid-name or invalid-value results.
Playground mode attaches unknown databases locally on first use through the node catalog owner.

The listener is insecure, matching `FlightSql.open` in the pinned implementation.
The node's PostgreSQL TLS configuration does not apply to this endpoint.

== Queries, writes, and metadata

GetFlightInfo captures a query's SQL, database, optional parameter IPC, and explicit read basis into the Kotlin-compatible JSON ticket inside `TicketStatementQuery`.
It keeps the connection borrowed through statement classification, basis capture, and schema preparation against that basis.
GetFlightInfo, GetSchema, CreatePreparedStatement and DoPut statement updates use the same selected Direct parser diagnostics for initial preparation.
When the vendor parser rejects a first unquoted ASCII identifier outside both vocabularies, the frontend compares the byte range and accepts a matching extraneous-input or statement-head mismatch report.
The gRPC description carries the report’s line, column and message.
Anomaly metadata includes the message, category `incorrect` and code `xtdb/sql-error` when its encoding fits the 4 KiB limit.
A Direct parser admission failure after eligibility returns its resource error, and other Direct outcomes retain the original preparation error.
Paired Flight SQL diagnostic execution remains pending.
DoGet revalidates the redeeming session, waits its visibility barrier, then opens the captured basis through `NativeSession::query_context_at`.
A ticket remains usable by a different authorized caller.
Flight SQL opens a columnar query cursor where the operators can provide Arrow batches.
An index-covered ordered point read streams typed results from the posting leaves under the ticket's captured basis.
Query streams retain their cursor, connection, session lease, cancellation scope, and Arrow allocation owners through completion or cancellation.

GetFlightInfo issues DML and SET once.
An open write transaction buffers DML for commit.
Their empty ticket sends an empty Arrow schema when redeemed and performs no further effect.
SQL BEGIN, COMMIT, and ROLLBACK use the shared Flight SQL control rejection; transaction actions own those operations.
Prepared handles are re-prepared against the current execution context on each use.
Their parameter metadata uses positional unnamed nullable fields, and the source's field-4 `is_update` extension is retained.
Prepared query binding retains the first Arrow batch.
Flight SQL derives the result schema from the bound Arrow fields and encodes the batch when issuing a query ticket.
Ticket redemption validates the argument batch and reads the first parameter row when opening the query.
A pure projection of compatible bound parameters stays in Arrow.
Compatible nested lists, fixed-size lists, and structs are projected as Arrow columns.
Supported addition, subtraction, and multiplication read integer and floating-point arguments through the query engine's Arrow projection kernel.
Supported division, comparisons, casts, and text functions read their parameters through the vector expression evaluator.
For a batch with multiple rows, it copies the selected first row without retaining the rest of the batch.
It reuses compatible buffers and normalizes Boolean padding and masked cells when copying is needed.
An update submitted through `GetFlightInfo` passes the bound batch to the transaction path as Arrow arguments.
Prepared update binding accumulates all Arrow batches by column position.
Zero columns mean an unbound execution; columns with zero rows preserve an empty execution batch.

Bulk ingestion supports append-on-exists and create-if-missing, a separate schema field, and one native document operation per input record batch.
A transaction handle buffers those operations together; an ordinary auto-commit connection submits each batch separately.

BeginTransaction, EndTransaction, ClosePreparedStatement, GetSessionOptions, SetSessionOptions, CloseSession, and `xtdb.CommitTransaction` are implemented.
The custom commit action sends the last submitted transaction result before a commit error and includes its await token.
Catalogs, schemas, tables with optional IPC schemas, table types, and the five pinned SQL-info values are exposed.
Schema and table patterns use the Arrow LIKE kernel, including escaped wildcard characters.
SQL-info values use the standard dense-union string and int32 legs with child-local offsets.

== Compatibility qualifications and resource accounting

The `FlightSqlTransaction` prose in `dev/doc/tx.allium` describes a handle reachable from any session.
The pinned `XtdbProducer` instead compares caller identity for transaction and prepared handles.
The native implementation preserves authenticated-session ownership and the shared anonymous owner; the specification retains an open question about that distinction.
Query tickets are independently transferable, as in the reference.

Arrow Java 19 advertises eight standard actions through ListActions, including savepoint, Substrait, and CancelQuery actions that XTDB leaves unimplemented.
The native server preserves that advertisement and returns unimplemented for those actions.
Session actions and the custom commit action remain callable despite their absence from that list.
Call or response-stream cancellation releases query work; the source does not implement a CancelQuery or CancelFlightInfo action.

Transport message sizes and concurrent calls are bounded.
Parameter IPC inspection checks metadata, body extents, buffer extents, and declared decompression sizes before Arrow decoding.
Schemas, record batches and retained parameter streams preserve signed 32-bit decimal precision and scale through the shared IPC codec.
External schemas cannot supply the codec's reserved native annotation, and exported schemas contain only the real decimal metadata.
Each output encoder retains its declared native schema and rejects batches whose full-width metadata differs.
Decoded Arrow owners and encoded `Bytes` retain their reservations through clones and transport delivery.
Metadata enumeration reserves borrowed schema bounds before cloning table bindings; returned catalog snapshots retain those reservations.
The schema and codec estimates are conservative allowances, not a demonstrated bound for every possible nested Arrow representation.
During classification of the complete SQL input, Flight SQL charges token array capacity and an estimate for lexer scratch to the node's memory budget.
A classified control command retains an estimated parsing and binding allowance through schema preparation or execution.
Flight SQL reserves a schema allowance before converting Arrow parameter fields to logical types and holds it through result-schema binding or construction of retained SQL arguments.
Typed batches with zero rows still carry their parameter field types.
Without a bound parameter batch, result-schema binding borrows the prepared parameter types.
HTTP/2, prost, TLS-free tonic buffers, ordinary SQL parser scratch, and scalar-expression peak allocations still require end-to-end accounting qualification.
Leases use the shared microsecond clock and have not been compared with the JVM nanosecond clock at submicrosecond timeout boundaries.
Native server-version metadata uses the Rust package version.
Ticket timestamps use chrono's supported calendar range, which is narrower than the JVM Instant range.
Query metrics count pull and Arrow-encoding failures; transport failures after an encoded message has been yielded are owned by tonic and do not currently increment the query consumer-error counter.

== Regression source mapping

`tests/flight.rs` uses an actual native Node and tonic Flight client in its test source.
Cases cover captured read bases, effect-free empty-ticket redemption, positional and multi-batch parameters, rebind isolation, authenticated handle ownership, transferable tickets, anonymous cross-session transaction completion, immediate lease expiry, bulk ingestion, metadata union offsets, and shutdown while an upload waits for its first message.
Internal cases cover idle leases and tombstones, nested session calls, credential parsing, cookie selection, Kotlin ticket JSON with required nullable fields, retained Arrow ownership, empty argument distinctions, and malformed IPC extents.
The reserved metadata API has a source regression in `rtdb-query` for clone lifetime and reservation failure.

These cases map to `core/src/test/kotlin/xtdb/flight_sql/LeaseTest.kt`, `src/test/kotlin/xtdb/FlightSqlAuthnTest.kt`, `src/test/kotlin/xtdb/FlightSqlAdbcTest.kt`, and the Flight SQL/ADBC Clojure tests under `src/test/clojure/xtdb`.
The protocol references are https://arrow.apache.org/docs/format/FlightSql.html[Flight SQL] and https://github.com/apache/arrow/blob/main/format/Flight.proto[Flight session actions].
The implementation uses https://docs.rs/arrow-flight/58.4.1/arrow_flight/[Arrow Flight 58.4.1] and https://docs.rs/tonic/0.14.5/tonic/[tonic 0.14.5].
Interop with Java, Go, Python, R, and ADBC drivers, external authentication, flow-control cancellation races, concurrent expiry/claim races, and every test listed here remain unexecuted qualification work.

Ticket `currentTime` retains the query clock's nanoseconds through serialization and later execution.
The captured snapshot-time cap retains its separate microsecond representation.

An existing anomaly with an absent message uses its `xtdb.api.error` category class name as the general Flight status description.
An empty message remains empty.
Bounded anomaly metadata and custom commit-result errors omit an absent message field.
Authentication uses its separate policy: faults hide their message, unsupported errors have no description when absent, and other absent messages use `authentication failed`.
Raw host failures still require their source-specific conversion before entering these anomaly adapters.

== Native owned relations

`flightSql.ownedNativeActions: true` enables the owned-relation actions for a compatible installation.
Both actions use the authenticated Flight session on an idle autocommit connection and require database write access.
An embedded server enables `FlightConfig::owned_native_actions` and `NodeOptions::owned_relations`.

Send `rtdb.owned.Create.v1`, `rtdb.owned.ReadPoint.v1`, or `rtdb.owned.Commit.v1` as the Flight `Action.type`.
The body contains a big-endian unsigned 16-bit relation-name length, the logical relation name as ASCII bytes, and one terminated Arrow IPC stream containing exactly one nonempty record batch.
The relation name contains 1–96 lowercase ASCII letters, digits, hyphens or underscores.
The create batch contains unique column names, an `_id` column, and the document fields.
Nullable `_valid_from` and `_valid_to` timestamp fields can supply row validity bounds.
The point batch contains just one non-null `_id` cell.
The connection's authenticated principal and attached database select the owned storage namespace.

Success returns one Flight `Result` whose body is a terminated Arrow IPC stream.
Create success contains one row with non-null signed 64-bit `tx_id` and `system_time_micros` fields.
Point success contains the document columns and at most one row.
Every point response Arrow schema contains `rtdb.owned.present_micros` as a signed decimal microsecond timestamp assigned by the store.
A point result with no rows contains the schema and terminator, with zero record batches.
An unknown relation uses a zero-field schema, and a missing entity in an existing relation uses its current schema.
The Flight limit applies to the complete encoded Action and Result protobuf messages, with a default of 64 MiB.
Failures use the Flight gRPC status and the existing anomaly metadata.

Use `x-xtdb-database` for the initial Multi gateway connection and retain the resulting session cookie or bearer token.
The gateway forwards these actions to the session's attached holder and fences that route at holder movement.
A new holder requires a new authenticated session.
A disconnected create has an unknown outcome and is not automatically retried.

`rtdb.owned.Commit.v1` inserts an exclusive signed 64-bit big-endian Unix microsecond deadline between the relation name and Arrow IPC stream.
The batch contains `_id` and a non-null Utf8 `_op` column with `create`, `replace`, `delete`, or `check`.
Create and replace accept document fields.
Delete accepts an identity and optional validity bounds, with null values for other document columns.
Check accepts an identity and an observation, with null mutation bounds and document values.
Create, replace, and delete apply in batch order in one atomic transaction.

A nullable `_read_valid_micros: Int64` specifies the point to revalidate before mutation.
A null `_read_system_micros: Int64` at that point asserts absence, and a non-null value asserts the exact previously observed winning revision.
A mutation without a valid instant carries no observation.
The point reply includes `rtdb.owned.valid_micros` for the observed instant and includes `rtdb.owned.revision_micros` when a row is present.
These metadata values are signed decimal microseconds.
A successful commit reply has the same schema as the create reply.
An expired deadline or stale observation aborts the entire transaction before mutations apply.

`rtdb.owned.Commit.v2` applies the same row schema and reply format to multiple relations in one transaction.
Its body starts with one exclusive signed 64-bit big-endian microsecond deadline and an unsigned 16-bit big-endian group count.
Each group is an unsigned 16-bit big-endian relation-name length, the ASCII relation name, an unsigned 32-bit big-endian IPC length, and exactly that many bytes of a terminated IPC stream.
Each group contains one nonempty batch.
Use up to 32 distinct relations and at most 4096 rows across the request.
With zero groups, the action validates only the deadline and returns its ordered transaction key.
The body ends immediately after the declared groups, or after the count when it is zero.
All observations are checked against the same ordered state before any mutation applies.
Mutations apply in group order and then row order, using the authenticated session's principal and database.

Owned lookups compare the complete stored `_id` before releasing data or accepting a point observation.
A private registry assigns each identity a permanent primary-index locator at transaction ordering.
Colliding identities probe alternate locators and stay independently addressable over time.
A legacy nonempty relation without a complete registry refuses owned reads and writes.

=== Declaring a private relation schema

Send `rtdb.owned.DeclareRelation.v1` with the relation prefix followed by a UTF-8 JSON object of at most 64 KiB.
The object has one `fields` array with up to 128 distinct entries and an optional `validity` policy.
Each entry has `name`, `type`, `optional`, and `nullable`, for example `{"name":"amount","type":{"kind":"i64"},"optional":false,"nullable":false}`.
Field names are nonempty UTF-8 strings of at most 128 bytes, without control characters or a leading underscore.
Supported scalar kinds are `bool`, `i8`, `i16`, `i32`, `i64`, `u8`, `u16`, `u32`, `u64`, `f16`, `f32`, `f64`, `utf8`, `binary`, `date_day`, `instant`, `uuid`, and `decimal`.
An `instant` is a zoned microsecond timestamp.
A `decimal` type also declares `precision`, `scale`, and `bitWidth` (128 or 256).
A declaration is accepted before the relation has stored data or another declaration.
The result has the create reply schema.

For a declared relation, create and replace enforce the field types at the ordering cut.
A field may be omitted only when optional, and an explicit null requires nullable.
A nullable Arrow column can carry both states across rows by including optional `_absent: List<Utf8>` with the names of that row's omitted payload cells.
Each listed cell must be null or undefined in the incoming batch.
Unknown payload fields are refused.
The `explicit` validity policy is the default and accepts supported mutation validity metadata.
The `acceptance` policy begins every Root put or delete at its ordered system time with an open valid end and rejects explicit endpoints.
Relations without a declaration continue to infer their schema.

=== Holding one owned read cut

Use `rtdb.owned.OpenRead.v2` with an empty body to reserve one present and retain its exact applied catalog.
The one result body contains 16 opaque handle bytes, the signed big-endian i64 Unix microsecond present, and the signed big-endian i64 ordered transaction id.
Send `rtdb.owned.ReadHeldPoint.v1` with those 16 handle bytes followed by the ordinary ReadPoint action body.
The Arrow response uses the held present and valid instant on every call, including missing rows.
`rtdb.owned.ReadHeldPoint.v2` uses the same framing with exactly one Arrow row and two columns, `_id` and `valid_micros: Int64?`.
A null `valid_micros` uses the held default. Otherwise it selects one business-valid microsecond within the original held system cut.
`rtdb.owned.valid_micros` echoes the selected instant even when the row is absent, and `rtdb.owned.present_micros` stays at the held present.

`rtdb.owned.ReadHeldHistoricalPoint.v1` inserts an eight-byte big-endian signed system time in microseconds immediately after the held handle, before the relation prefix.
It uses the same point key, with null `valid_micros` selecting the requested system time on the valid axis.
The relation's journal must cover the system time at or before the held cut.
The point reply carries that requested system time in `rtdb.owned.present_micros`.

Send `rtdb.owned.CloseRead.v1` with only the 16 handle bytes to release it.
Close success has zero Flight results.

Handles bind to their authenticated Flight session and database attachment.
Each node holds at most 64 handles.
A handle expires after at most 60 seconds or if its storage lease or holder is lost.
A concurrent commit that prevents capture of the exact reserved head refuses the open with `rtdb.owned/capture-raced`.
After holder movement or lease loss, open a new authenticated session and start a new attempt.
The held read uses the serving node's retained catalog and does not survive a process restart.

`rtdb.owned.DeclarePath.v1` uses the relation prefix and a terminated Arrow IPC stream with exactly one row.
Its two columns are `_id: Utf8` for the path name and `columns: List<Utf8>` for the ordered key columns.
The key consists of distinct stored columns and ends with `_id`.
The relation must already exist in the authenticated owner's namespace.
A successful declaration returns the same transaction-key Arrow row as Create.
Ordered and search path declarations can be repeated with the same complete name, owner relation and columns.
The declaration is immutable and private to the owner's index catalog.
Index maintenance builds the generation after declaration.

`rtdb.owned.ReadHeldRange.v1` uses the 16-byte held handle, a relation prefix, and a terminated Arrow IPC stream with one row.
The row contains `path: Utf8`, the nullable typed `lower` and `upper` key cells, and `limit: Int64` between 1 and 128.
Bounds address the leading path key, with an inclusive lower endpoint and an exclusive upper endpoint.
A null endpoint leaves that side open.
Results contain the covered path columns in ascending path order at the held present and valid instant.
A missing declaration, missing generation, uncovered source frontier, unflushed data, or unsupported covering projection returns an explicit refusal.
The service does not fall back to a primary or SQL scan.

`rtdb.owned.ReadHeldRange.v2` uses the same handle and relation framing with one Arrow batch containing one row.
Its fields are `path: Utf8`, `lower: Struct?`, `upper: Struct?`, `after: Struct?`, `descending: Bool`, and `limit: Int64` between 1 and 128.
Each non-null endpoint contains every declared path column by name, including the full `_id` value.
A null endpoint is open. Lower is inclusive and upper is exclusive in ascending path order for either direction.
The exclusive `after` endpoint advances in the requested direction.
For the next page, use the last returned row as `after` with the same held handle, path, bounds, and direction.
The response uses the same covering schema and held time metadata as v1, with no record batch when the page is empty.

A covered v2 page on a placed attachment with a live catalogue lease also returns `rtdb.owned.range_witness`, an opaque 32-digit hexadecimal nonce in the response schema.
A covered empty page can carry a witness.
Each held handle issues one nonce per observed relation, up to 32 relations.
`rtdb.owned.Commit.v3` prefixes an unchanged Commit.v2 body with an unsigned 16-bit big-endian witness count (1–32), then that many pairs of 16 raw held-handle bytes and 16 raw nonce bytes.
The commit reply is unchanged.
`rtdb.owned.Commit.v4` uses the same framing and accepts zero through 32 witnesses.
It adds the `erase` mutation for a permanently assigned root identity.
An erase row accepts the typed `_id` and an optional point observation, with no validity endpoints or non-null payload values.
The resolver refuses erase on a relation with a governed ordered, search, or unique path or a prefix-capacity rule and refuses any other mutation of the same identity in the same commit.
Erase adds an all-history event and a distinct `erase` change entry at the ordered cut.
It revokes reads at older cuts for the erased relation and refuses historical point and archived fallback reads preceding the identity's erase.
Each identity's historical floor is keyed by its full typed handle inside an independently covered purge bucket.
Colliding locators cannot advance each other's floors.
Installations with owner-wide markers or per-relation erase markers without complete floor coverage require a reset before historical point reads or another erase in the affected scope.
The receipt acknowledges ordered erasure. Disposal of backing objects and keys has its own lifecycle.
Both values belong to the same authenticated session, database, and placed writer epoch.
The handle must still admit reads when submitted, and the witness's exclusive ordering deadline may be earlier than the request deadline.
The resolver compares the witnessed relation's complete event frontier at ordering before applying any mutations.
Any intervening event on that owner relation invalidates the witness, including events outside the observed key span or valid instant.
Events on other relations or owners do not invalidate it.
Count replies carry no range witness.

`rtdb.owned.CommitOrdered.v1` uses the same witness prefix with zero through 32 witnesses and the same deadline and Arrow entry framing.
It preserves the order of relation runs, and the same relation may appear in multiple runs.
The commit admits up to 4096 entries across at most 32 distinct relations.
A check-only request can have zero groups, and this action accepts point and range checks with the ordinary root mutations.

`rtdb.owned.CountHeldRange.v1` uses the same handle and relation framing with one terminated Arrow IPC batch containing one row.
Its fields are `path: Utf8`, `lower: Struct?`, `upper: Struct?`, and `valid_micros: Int64`.
Bounds are complete path keys with an inclusive lower endpoint, an exclusive upper endpoint and null for an open side.
The result contains one non-null `count: UInt64` at the held system present and the requested signed microsecond business-valid instant.
The result schema carries `rtdb.owned.present_micros` and `rtdb.owned.valid_micros`.
The count requires the same complete generation as a covered range and uses subtree cardinalities without a scan fallback.

`rtdb.owned.DeclareSearchPath.v1` uses the relation prefix and a terminated Arrow IPC stream with one batch and one row.
Its fields are `_id: Utf8` for the path name and `column: Utf8` for the stored clear-text column.
The relation must already exist in the authenticated owner's namespace, and the column must contain only text or null.
The FTS maintenance lane uses the private declaration to build the relation's search files.
A successful declaration returns the same transaction-key Arrow row as Create.

`rtdb.owned.SearchHeld.v4` takes the 16-byte held handle, a big-endian u16 partition count (1 to 32), then a relation prefix and a path prefix per partition.
A big-endian u32 offset (0 to 4096), u16 limit (1 to 128), and evidence flag byte (0 or 1) follow, then the UTF-8 query (up to 4096 bytes).
The reply contains `_id` as a typed union of string, keyword, signed Int64 and UUID, `score: Float64`, and `partition: UInt64` as the zero-based request ordinal.
Results sort by descending BM25 score across the full selected corpus, then by complete typed identity and partition ordinal.
The held present and valid instant are in schema metadata, alongside `rtdb.owned.search_total` (the decimal count of all verified matches before slicing) and `rtdb.owned.search_scope` (the lowercase hex SHA-256 of the held handle, ordered relation/path frame, and query under the v4 domain tag). The scope binds pages only within the same hold. An empty result has a schema and no record batch.
Every selected partition must have complete search artefacts at the held cut. Each matched posting is verified against the full identity and winning revision.
A placed read with evidence requested publishes `rtdb.owned.search_witnesses` as the concatenated lowercase hex of one 16-byte range nonce per partition in request order. This also covers a successful empty result.

`rtdb.owned.DeclareUniquePath.v1` uses the relation prefix and a terminated Arrow IPC stream with one batch and one row.
Its fields are `_id: Utf8` for the path name and `column: Utf8` for the canonical Binary key column.
Declare one immutable unique path per owned relation before writing relation data. An exact retry of the declaration keeps its original definition. An existing empty typed relation must declare the key as Binary.
On this relation the final state of each owned commit must give each live row a nonempty Binary key of at most 4096 bytes.
Mutations use validity from their ordered present to infinity.
The ordered resolver applies releases and claims as a group, so a commit may swap keys. Conflicts do not return the occupant or the key.
A successful declaration returns the same transaction-key Arrow row as Create.

`rtdb.owned.ReadHeldUnique.v1` takes the original 16-byte held read handle,
the owned relation prefix, the declared unique path prefix, and one terminated
Arrow IPC batch with exactly one row `key: Binary`, `valid_micros: Int64`.
The valid instant must equal the held system instant because unique occupancy
covers ordered-present membership. The relation's private declaration records
its covered event frontier with the occupancy changes in the same transaction.
A missing declaration or a frontier mismatch refuses the lookup.

A successful reply begins with one 16-byte range witness nonce followed by the
ordinary point IPC response. There is one full fact row for a unique hit,
or no rows for a covered absence. The resolver revalidates this relation
witness in the same way as other held range evidence. The complete occupancy
identity, holder identity, and holder's declared key must all agree.

=== Reading valid history at a held cut

`rtdb.owned.ReadHeldValidDuring.v2` takes a 16-byte held handle, the relation prefix, and one terminated Arrow IPC stream.
The stream contains one batch with one row and fields `_id`, `system_micros: Int64`, `valid_from_micros: Int64`, and `valid_to_micros: Int64`.
The system cut and both valid endpoints must be non-null, with the valid start strictly before the valid end.
One result contains a schema and zero or more record batches of the winning facts in ascending valid-time order.
The `_valid_from` and `_valid_to` timestamps clip each slice to the request. A null `_valid_to` represents an unbounded end.
Each row includes `_system_from`, the winning revision. Gaps and tombstones have no row.
Schema metadata reports `rtdb.owned.present_micros`, `rtdb.owned.valid_from_micros`, and `rtdb.owned.valid_to_micros`.
The returned present metadata identifies the system cut used for the read. A fresh hold can use its own cut or an earlier certified cut. A derived hold uses its selected cut and declared relations. Reads refuse more than 4096 slices or an oversized Flight result.

On placed writer sessions with retained leases, a fully completed valid window at the held head carries the same optional `rtdb.owned.range_witness` nonce as covered ranges, including a proven empty window.
A fully covered held count also carries that nonce, including zero counts.
The nonce depends on the entire relation's frontier at the held cut and retains the original session, placement and expiry.

`rtdb.owned.ReadHeldVersions.v2` uses the held handle and relation prefix followed by one Arrow batch and one row.
The request fields are `_id`, `system_from_micros: Int64`, `system_to_micros: Int64`, `after_revision: Int64`, `scan_limit: Int64`, `result_limit: Int64`, and `descending: Boolean`.
Use a half-open system window at or before the held cut and zero for the initial journal revision. A derived hold admits only its declared relations and ends at its selected cut.
The scan limit is 1–128 source groups. The result limit is 1 to the scan limit.
The first result contains the last scanned revision as big-endian u64, a completion byte of 0 or 1, the floor in signed big-endian Unix microseconds, and the scanned group count as big-endian u16.
The floor is the minimum i64 when coverage starts with an empty relation or the requested interval is empty.
A placed head read may append a 16-byte relation witness after the full response renders.
An incomplete page may have no matching versions. Continue from its last scanned revision with the same handle, window and direction.
Each additional result is one Arrow stream containing the full winning valid timeline for one source group that touched the complete typed identity.
A complete deletion still returns a version stream with schema and no record batch. Clients fill gaps from the explicit valid boundaries.
Schema metadata includes `rtdb.owned.version_revision` and `rtdb.owned.version_micros` alongside the held present and full valid window.
Requests before the certified floor refuse and report `history-floor-micros` in the anomaly context.
Coverage or response-size failures refuse the page.

`rtdb.owned.ReadHeldIdentityPage.v1` takes the 16-byte held handle, the relation prefix, and one terminated Arrow stream with one row.
The fields are `system_micros: Int64`, `valid_micros: Int64`, `after: Utf8`, and `limit: Int64`. A null bound starts at the first key.
The response echoes both time coordinates and carries visible UTF-8 identities from the admitted relation in strictly ascending order.
The limit is 1–128. Schema metadata `rtdb.owned.identity_more` is 1 when the next page can resume after the last returned identity, including when the response reaches its byte bound.
Historical cuts require certified coverage and honor ordered erasure floors.

=== Working in a hosted checkpoint world

The placed Multi host enables world actions on a listener configured for owned native actions.
An authenticated, idle autocommit session must remain bound to its writer placement and epoch.
The host resolves deployment and archive authority from the authenticated placement and the world record.

`rtdb.owned.ReadWorldPoint.v1` takes a 16-byte world UUID, the relation prefix, and a terminated Arrow IPC stream containing one batch and one row.
The row has `_id` of a supported identity type and a non-null `valid_micros: Int64`.
The read resolves the local world shadow at one reserved present, including tombstones, then uses the retained archived cut if there is no shadow.
The IPC metadata reports the live world present as `rtdb.owned.present_micros` and the selected instant as `rtdb.owned.valid_micros`.
A found row includes the winning local or archived `rtdb.owned.revision_micros`. An absent row has no record batch.

`rtdb.owned.OpenWorldRead.v3` takes the world UUID and admits one live cut and its verified archived parent.
The 48-byte result contains the opaque handle, the live present, archived parent transaction ID and system time, and the last application clock. Int64 minimum identifies a world with no local application publication. Each coordinate is a signed big-endian 64-bit integer. Times are Unix microseconds.
`rtdb.owned.ReadHeldWorldPoint.v2` takes the 16-byte held handle, one observation flag byte (0 for read-only or 1 to request a witness), then the same relation and Arrow fields as the one-shot read.
The point response schema includes `rtdb.owned.world_shadowed` (0 or 1). A local tombstone counts as a shadow.
Every call reads the same live cut and archive root. The held handle stays bound to the original authenticated session and attachment.
Use `rtdb.owned.CloseWorldRead.v1` with the 16-byte handle to cancel the read. Success has zero Flight results. The archive lease releases after in-flight I/O drains.
A held read expires no later than 60 seconds or the world's own expiration. A drop fences new opens. Earlier admitted handles can read only while their original cut and archive lease still admit them.

`rtdb.owned.ReadHeldWorldValidDuring.v1` takes the 16-byte held world handle, a relation prefix and one Arrow row with `_id`, `valid_from_micros: Int64` and `valid_to_micros: Int64`.
The reply carries the held present and resolved window in schema metadata. Each row carries `valid_from_micros`, `valid_to_micros` and the winning `system_from_micros` as signed Int64 values.
Local tombstones leave gaps. Gaps carry no rows, and the response issues no write condition.
History refuses a cut lacking custody coverage or requiring more than 128 candidate slices.

`rtdb.owned.ReadHeldWorldIdentityPage.v1` takes the 16-byte held world handle, a relation prefix and one Arrow request row.
Supply `valid_micros: Int64`, `after: Utf8?` (an exclusive bound), and `limit: Int64` (1 through 128).
The reply contains sorted `_id: Utf8` keys, the held world present and valid instant, and `rtdb.owned.identity_more`.
Resume after the last visible identity when that flag is set.
The page merges exact archived and local shadow candidates. A winning local tombstone hides the identity.
Missing coverage, an archive purge floor after the parent cut, or excessive work refuses the page.

`rtdb.owned.DropWorld.v1` takes exactly the 16-byte world UUID.
The ordered terminal record fences subsequent world operations before the host releases its archive pin.
Success has zero Flight results.

`rtdb.owned.ForkWorld.v1` takes a registered 16-byte capture UUID followed by a signed big-endian 64-bit expiration time in Unix microseconds.
The host resolves the live deployment's capture receipt and reopens its verified archive root to obtain the parent transaction key.
Success returns one Flight result containing the new world UUID as 16 bytes.
`rtdb.owned.ForkWorld.v2` takes a registered 16-byte capture UUID, the 16-byte lease UUID of a published replica suffix for that capture, and the same 64-bit expiration.
The host authenticates the archived suffix and applies its inline resolved transactions in a private recovered partition at the exact accepted transaction key.
The world retains that suffix with its parent capture and reopens the same replay cut for held and one-shot reads.
The reply and subsequent world read and write actions use the same wire shapes.

`rtdb.owned.CommitWorld.v1` takes a 16-byte world UUID, then the Commit.v2 relation grouping without a deadline.
The group count is a big-endian u16 from 1 to 32.
Each group consists of a relation prefix, its big-endian u32 Arrow length, and one terminated IPC stream with a nonempty batch.
The request admits up to 4096 rows across all groups.
Each row has exactly `_id`, `_op: Utf8`, `_valid_from_micros: Int64`, `_valid_to_micros: Int64`, and `fact: Struct?`.
Both signed endpoints are required and specify a nonempty half-open interval. Use Int64 minimum and maximum for unbounded endpoints.
A `replace` carries the complete fact fields in its struct. The struct may include `_absent: List<Utf8>` to omit named null cells.
A `delete` carries a null struct and writes a world tombstone over the interval.
The resolver validates replacements against the schema inherited from the archived cut and orders all groups atomically at the live world deadline.
Success returns the standard transaction-key Arrow row.

=== Reading owned relation changes

`rtdb.owned.ReadHeldChanges.v2` takes the 16 raw held-handle bytes, a relation prefix, a signed 64-bit big-endian exclusive system time in microseconds, and an unsigned 16-bit big-endian maximum of 1–128 groups.
The first tracked mutation installs a feed floor and its first group in the same ordered transaction.
A relation with zero events is covered through the held present.
A request that crosses untracked relation events or encounters a missing journal group is refused.

The reply is a terminated Arrow stream with `revision: UInt64`, `system_time_micros: Int64` and `touches: List<Struct>`.
Each touch contains the full native `_id`, `op: Utf8` (`put` or `delete`), `valid_from_micros: Int64`, and `valid_to_micros: Int64?`.
The exclusive upper endpoint is null for an unbounded interval.
A group records the relation's committed mutations in their original order.
Writes exceeding the 1 MiB retained-value budget for a relation's group abort.
A page stops before its next whole group if that group would exceed the 8 MiB retained-value budget.
The `rtdb.owned.present_micros` schema metadata identifies the held cut.
The `rtdb.owned.change_coverage_micros` metadata is the last returned group time if the page stopped early, or the held present when the relation is covered through the cut.
Use the coverage time as the next exclusive system time.
An empty page carries only the response schema and terminator.
Revisions are dense within the authenticated owner's relation, and each returned system time belongs to a commit with a change on that relation.

`rtdb.owned.ReadHeldWorldPoint.v2` with flag 1 may include `rtdb.owned.world_point_witness`, an opaque 32-digit hexadecimal nonce.
The witness exists only under an authenticated placed read with a retained lease. It may accompany an absent result or an archived winner.
`rtdb.owned.CommitWorld.v2` takes the 16-byte world UUID, the 16-byte held world handle, a big-endian u16 witness count from 1 to 128, and that many distinct raw 16-byte nonces.
The remaining bytes are the same relation groups as `CommitWorld.v1`.
The original session and placement must still own the held world read.
Before applying any write, the ordered resolver checks the placement and earliest lease deadline, then the local shadow observations.
A local tombstone has its own observed revision. An archived winner certifies local absence. The parent cut itself is fixed by the world registration.
The response has the same transaction-key row as `CommitWorld.v1`.

`rtdb.owned.CommitWorld.v3` validates an admitted world condition without writing any fact or publishing a clock.
It takes the world UUID, one signed big-endian 64-bit exclusive deadline in Unix microseconds, the held handle, a big-endian u16 witness count from 1 to 128, and the distinct 16-byte nonces.
The remaining bytes are the existing hosted control groups. Only check rows from the placed allowlist are admitted.
The ordered transaction checks the world registration, placement, deadline, local point revisions, root erasure frontiers, and hosted ownership before issuing the transaction-key receipt.

`rtdb.owned.CommitWorld.v4` publishes an admitted single-world overlay and application clock atomically.
`rtdb.owned.CommitWorldClock.v1` publishes a clock alone using the same held conditions, deadline, hosted ownership checks, and immutable attempt marker.
Its body shares the v4 prefix through the expected clock, followed by the target clock as a big-endian i64 and the check-only hosted control groups.
The target must strictly exceed the held clock and be at or before the ordered commit time.
`rtdb.owned.CommitWorldDrop.v1` orders a terminal marker and the immutable attempt marker using the same held conditions, deadline and hosted ownership checks.
Its body shares the v4 prefix through the expected clock and then contains only the check-only hosted control groups.
The placed archive owner retires the matching Directory pin after the ordered result; the response identifies the terminal transaction.
The prefix through the witness list matches v3, followed by 22 lowercase hexadecimal attempt ID bytes, a 32-byte request fingerprint, and the expected application clock as signed Int64 (minimum for no local publication).
A big-endian u32 length frames the existing overlay relation groups, followed by the check-only hosted control groups.
The ordered resolver validates the original witnesses and advances the expected clock by one microsecond from the prior local clock or archived parent basis.
It creates the immutable root attempt marker with the same transaction key as the overlay and clock. Administrative overlay operations retain their existing semantics.

=== Reading a merged held change feed

`rtdb.owned.ReadHeldMergedChanges.v1` takes the 16-byte held handle, an exclusive signed Int64 ordered system time in big-endian microseconds, a big-endian unsigned 16-bit commit limit, and a big-endian unsigned 16-bit relation count followed by that many relation prefixes.
Supply one to 32 distinct preadmitted owner root relation names and a limit of one to 128 commits.

The touch fields match ReadHeldChanges.v2.

A capped page stops before a whole commit if it would exceed the 8 MiB retained-value budget.

`rtdb.owned.change_coverage_micros` identifies the last returned revision of a partial page and the held present of an exhausted page.
Resume from that coverage time.
An empty covered page has no rows and carries the already-known held present in `rtdb.owned.present_micros`.

=== Declaring owned prefix capacity

`rtdb.owned.DeclareCapacity.v1` takes the relation prefix and a terminated Arrow IPC stream with one batch and one row.
Its fields are `column: Utf8`, `prefix_bytes: Int64` (1–4096), and `cap: Int64` (positive).
The immutable rule applies before the relation's first fact event and returns the same transaction-key Arrow row as Create.

=== Fixed-valid range observations

`rtdb.owned.DeclareFixedRange.v1` takes the relation prefix and one terminated Arrow IPC batch with one row.
The fields are `path: Utf8`, `column: Utf8`, and `valid_micros: Int64`.

`rtdb.owned.ReadHeldRange.v3` adds a seventh `valid_micros: Int64` field to v2.

=== Committing checked hosted control rows with owned facts

`rtdb.owned.CommitHosted.v1` is enabled only for a live placed connection authenticated as `flightSql.hostedControls.owner` with `flightSql.ownedNativeActions` enabled.
The operator's `flightSql.hostedControls.relations` sequence names the admitted ordinary `public.bj_*` tables.
The body begins with the Commit.v3 unsigned Int16 big-endian witness count (zero to 32) and its 16-byte held handle plus 16-byte nonce pairs.
Then come the signed Int64 big-endian exclusive deadline, an unsigned Int32 big-endian byte length, that many bytes of ordered fact groups, then the hosted control groups.
Both sections use the Commit.v2 relation-group sequence framing. The control section has at least one group. A check-only transaction may omit fact groups.
Fact groups may repeat a relation to preserve run order. The combined sections admit at most 32 distinct fact and control groups and 4096 total rows.

Each control group contains one terminated Arrow batch with distinct field names.
Every row has `_id: Utf8` and `_expected_micros: Int64?`. Replacement rows supply a complete image in the already installed ordinary column types. A row with `_check_only: Boolean` set to true carries only the ID and expectation and leaves the table unchanged.
A null expectation requires exact absence.
An existing row must contribute one exact valid slice from epoch to infinity at the ordered base.
Control replacements use the same epoch-to-infinity interval.
The resolver checks all control and fact observations before any mutation and aborts both sets of effects on failure.
Use an absent-checked unique receipt key as one of the writes when the host needs to recover an indeterminate response.
The response is the ordinary committed transaction-key row.

`rtdb.owned.ReadHeldHostedControl.v1` uses the same installed placed owner
and ordinary control allowlist as the commit actions. Send the original live,
underived 16-byte held read handle, one ordinary control table prefix, then
one terminated Arrow IPC batch with one row `_id: Utf8`. The ID is complete
and bounded to 4096 bytes. No time override is accepted.

The response is ordinary point IPC, with the original held present and
`valid_micros` equal to zero. A hit is one row with the complete ID,
ordinary control fields, and its original system revision in point metadata.
An installed table with a covered absent row returns its typed schema without
a revision or rows. Send that revision or null as `_expected_micros` in a
subsequent checked hosted commit. A missing table or a non-epoch valid slice
refuses the read.

`rtdb.owned.CommitHostedCounted.v1` prefixes this action with the ordered-present count condition from Commit.v6.
The resolver checks both the ordinary control observations and the final owned count in the same transaction.

This action supports checked replacement and exact absence insertion for hosted controls.
Other control effects, including arbitrary SQL, computed values, deletes, relabeling and temporal splits, are outside this action.
Generic SQL keeps the existing private relation boundary.
