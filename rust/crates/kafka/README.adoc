= Kafka log adapter

`KafkaLog` is a passive append/read capability.
`KafkaLogDriver` is the active owner of producer submission, callback polling, and shutdown.
Capacity semaphores and per-append completion channels are monitors shared with callers.
`KafkaTail` is a passive cursor with caller-controlled polling and an explicitly assigned partition.
The native client owns transport threads; no Rust producer task is detached.
The owner runs the returned driver and cancels and joins it before releasing writable-log resources.
Read-only opening returns no producer or driver.

`enqueue` returns after the native producer accepts the record and fixes its submission order.
The receipt completes after the delivery callback reports the broker acknowledgement.
`acks=all` is mandatory.
Disabling idempotence also limits outstanding broker requests to one so retries cannot reorder appends.
This last override is stricter than the JVM producer configuration, which leaves that property overridable.
An error after submission can leave an unknown broker outcome; replication reconciles its term and sequence through read-back.
The supplied local timestamp is unused, as in the JVM Kafka transport; Kafka record timestamps have millisecond precision.

Each log requires one partition.
Topic creation uses one replica and `LogAppendTime` timestamps.
Existing replicated topics report weak minimum-ISR or unclean-election configuration through the required observer.
Denied configuration inspection is advisory.
Automatic consumer metadata requests cannot create topics.
The source and replica topic names and storage epoch use the existing protobuf schema.

Configuration properties merge bootstrap servers, the property map, then the ISO-8859-1 Java properties file.
The documented PLAIN JAAS configuration and SCRAM username/password configuration translate to native SASL properties.
JAAS lexical rules follow the pinned Java tokenizer: slash comments, Java control whitespace, quoted octal escapes and word/number boundaries.
Quote numeric values and credentials containing punctuation outside Java word characters.
Both modules accept `required`, `requisite`, `sufficient`, and `optional` with Java's locale-independent uppercase matching; later duplicate options replace earlier values.
PLAIN ignores additional login options.
SCRAM ignores additional options except `tokenauth`, whose case-insensitive `true` value selects delegation-token authentication.
The adapter maps that option to `sasl.scram.tokenauth` and includes `tokenauth=true` in the client-first message and authenticated transcript.
Explicit native and JAAS token-authentication settings must agree.
The built-in Kerberos login adapter translates the principal and keytab, and accepts a pre-acquired ticket cache.
The built-in unsecured OAuthBearer JAAS options enable librdkafka's unsecured token generator for development and tests.
Secured broker OAuthBearer uses the HTTP(S) client-credentials grant for Kafka log producers, consumers and administrators, Connect source consumers, and dead-letter producers.
Use `sasl.mechanism=OAUTHBEARER` with `SASL_SSL` or `SASL_PLAINTEXT` and the Kafka `OAuthBearerLoginCallbackHandler`.
The corresponding native `sasl.oauthbearer.method=oidc` and `sasl.oauthbearer.client.id` / `sasl.oauthbearer.client.secret` properties are also accepted.
Set `sasl.oauthbearer.token.endpoint.url` and allow the exact URL in the process environment variable `RTDB_KAFKA_OAUTHBEARER_ALLOWED_URLS`.
This comma-separated allowlist defaults to empty and requires the final endpoint URL when a provider advertises a redirect.
Kafka 4.4 `sasl.oauthbearer.client.credentials.client.id`, `sasl.oauthbearer.client.credentials.client.secret`, and `sasl.oauthbearer.scope` take precedence over `clientId`, `clientSecret`, and `scope` in `OAuthBearerLoginModule`.
The adapter applies `sasl.oauthbearer.header.urlencode`, JAAS `extension_*` and endpoint `ssl.*` options, and the configured subject and scope claim names.
Kafka broker TLS and token endpoint TLS use their respective settings.
A failed initial login fails client construction.
Librdkafka handles subsequent refreshes on its background queue, keeping the previous credential until expiry and retrying refresh failures after ten seconds.
Kafka's `sasl.login.refresh.*` and `sasl.login.retry.backoff.*` properties configure scheduled refresh and HTTP retry backoff respectively.
Token endpoint connect and read timeouts default to 60 seconds each, including a configured zero, to bound native client shutdown.
Custom Java login callbacks, token providers, client assertions and file URL token sources require a native adapter and return a configuration error.
Kafka log clients and Connect source consumers accept Java TLS properties through the shared native TLS adapter.
Each log prepares one retained client configuration for its topic administrator, producer, watermark readers, ranges, and tails.
Each source assignment prepares one configuration for its consumer.
Derived native clients retain the admitted TLS material even after the originating configuration or log is released.
Regular native CA, CRL, certificate, key and native PKCS12 files use admitted immutable raw snapshots at their original native loading sites.
Each native client reserves a separate file-decoding allowance before native construction and retains it through native teardown.
link:src/client/material/README.adoc[Native material ownership] records snapshot lifetimes, deferred I/O failures and the separate hashed-directory/native-allocation qualification gaps.
`KafkaLog::open` and the node's Kafka resource registration receive the existing node memory budget; TLS material remains charged until the last native client releases it.
The adapter consumes its supported Java TLS properties and preserves other native TLS and SASL properties for librdkafka validation.
Java and native identity settings, or Java and native trust settings, cannot both supply the same client.
Producer acknowledgement, idempotence, compression, queue and message-size overrides apply after preparation without replacing its TLS owner.
The schema registry URL is retained for source configuration; the log transports envelope bytes without a registry lookup.

Fresh broker watermarks determine the durable tip.
Retention, withdrawn observed offsets, unexpected gaps, tombstones, and fetch timeout before a known tip return errors.
Empty polling means the cursor reached the observed tip.
The transport does not open Kafka transactions; externally written transaction/control records that introduce offset gaps are rejected.
Poll batches and range reads have explicit limits; a range exceeding its limits fails instead of truncating silently.
Replication prepares the next Kafka record by retaining one fetched native event on the tail.
Preparation leaves the delivered offset unchanged.
The selected read copies the payload after caller admission and releases the native event on delivery.
A refused or cancelled selected read keeps the pending record at its original offset.
Direct polling drains a pending record before polling for another one.
Native client contexts, prefetch and decompression allocations still require qualification against the process-wide memory contract.

Source references are `modules/kafka/src/main/kotlin/xtdb/api/log/KafkaCluster.kt`, `KafkaClusterTest.kt`, `KafkaLogFactoryTest.kt`, `KafkaDurabilityTest.kt`, and `allium/log-processor-lifecycle.allium`.
The Rust test sources cover configuration precedence, JAAS credentials, acknowledgements, topic partition validation, read-back, read-only handles, and cancellation while admission is backpressured.
TLS assembly regressions cover admission before connection setup, failed-setup release, retained configuration and native-client clones, source-consumer options, and producer defaults.
They have not been compiled or executed during Phase 1.
Real broker failover, retained-range truncation, authentication, and native shutdown qualification remain required before backend compatibility can be claimed.

The standalone replay qualification example requires explicitly supplied broker access and a preprovisioned disposable topic named with the `rtdb-replay-` prefix.
The delivery check requires an unused topic whose first append receives offset zero.
Run `cargo run -p rtdb-kafka --example qualify_log_replay -- BROKER TOPIC` from the `rust/` directory.
Pass `--properties-file FILE` for client properties that preserve the supplied broker endpoint.
Pass `--first-retained OFFSET` for a read-only check after the fixture owner advances the broker's retained boundary.
The offset must be positive and the topic must retain a record at that offset.

== Kafka Connect ingestion

`connect::SourceDriver` owns one explicit partition assignment and its consumer, converters, transform chain, indexer, and cancellation choice.
`SourceConfig`, `ConnectConfig`, schema/value descriptions, and resume tokens are immutable values.
Converters, predicates, transforms, and record indexers are passive capabilities opened for that assignment.
The status channel is a monitor with one writer.
The node registers `KafkaConnectSourceFactory` under the existing external-source protobuf type.
The durable configuration stores a Kafka remote alias, topic, Connect plugin options, and an indexer `Any`.
Node-local native plugin and indexer registries provide extension points.
Converter options are retained in the durable source configuration.

A first assignment seeks to the first retained Kafka offset.
A resumed assignment seeks immediately after the last admitted XTDB transaction token.
No consumer offsets are committed to Kafka.
The driver converts and transforms an entire bounded fetched batch before submitting any record from that batch.
Filtered records create no transaction; an entirely filtered tail is replayed after reassignment.
The document indexer obtains `_id` from the key, unwraps a single-field Connect Struct key, overwrites any document `_id`, and writes a delete for tombstones.
Document valid time defaults to the smoothed transaction system time through the end of time.
Decoder, transform, or indexer errors stop the assignment without an aborted placeholder transaction.
The current submission adapter waits for admitted read-back per record; the reference document indexer hands off after resolution and can pipeline read-back.

Native converters cover String, ByteArray, numeric, Boolean, schema-bearing or schemaless JSON, and the core Confluent Avro and JSON Schema wire paths.
The pinned JVM node ships only the String, JSON and Confluent Avro converters.
The ByteArray, numeric and Boolean converters and the Confluent JSON Schema converter are native extensions: a JVM node rejects those classes as not found.
The String converter selects the key or value deserializer encoding before decoding, with `converter.encoding` supplying the fallback to both serializer and deserializer configuration.
Selected serializer encodings are validated during opening even for ingestion.
All nine Java25 standard charsets and their aliases are supported: UTF8, ASCII, ISO-8859-1, UTF16, UTF16BE, UTF16LE, UTF32, UTF32BE, and UTF32LE.
BOM-sensitive little-endian UTF16 and both BOM-suffixed UTF32 variants are also supported.
CESU-8 supports the `CESU8` and `csCESU-8` aliases, retains byte-order marks as text, and replaces each byte of a four-byte UTF8 sequence separately.
Its two- and three-byte malformed groups follow Java's replacement boundaries; decoded surrogate pairs combine into Unicode scalars, while isolated surrogate units become replacements in native UTF8 values.
UTF8 and UTF16 replacement consumes malformed byte groups at the Java decoder boundary; fixed-endian UTF16 preserves its initial byte-order mark as text.
UTF32 consumes a matching initial byte-order mark, including in fixed-endian modes, and defaults to big-endian order when no order is specified.
Its malformed four-byte words and final one-to-three-byte fragment each produce one replacement; adjacent surrogate units emitted by Java's decoder combine into one Unicode scalar, while isolated units become replacements in native UTF8 values.
The 102 Java25 built-in `SingleByte.Decoder` charsets and their 589 distinct canonical names and aliases are supported, including ISO-8859 variants, Windows code pages, IBM DOS and EBCDIC pages, KOI8, Macintosh encodings, JIS X0201, and Thai encodings.
Their pinned mappings preserve control characters and non-round-trip decoding entries, and each unmappable byte produces one replacement.
The link:src/connect/converter/charset/single_byte/README.adoc[single-byte mapping reference] records the complete inventory, provider aliases, source hashes, and derivation.
Shift_JIS and Windows-31J support all ten distinct registered names, including `SJIS`, `MS932`, and `windows-932`.
Their mappings retain Japanese symbols, halfwidth katakana, Windows extensions and private-use characters, with Java's one- or two-byte replacement boundaries for malformed and unmappable input.
The same decoder also supports Big5, GB2312, GBK, EUC-KR, Johab, PCK, IBM1381/942/943/948/949/950, the IBM942C/943C/949C variants, and Windows936/949/950, for 20 double-byte charsets and 100 registered names in total.
IBM control remappings, yen/overline/won signs, Windows extensions, and private-use mappings follow their individual Java tables.
Big5-Solaris adds the `x-Big5-Solaris` and `Big5_Solaris` names, bringing this family to 21 charsets and 102 registered names.
Its first admitted nonempty record updates seven Big5 mappings process-wide, including converters opened earlier; configuration, null records, and empty records leave those mappings unchanged.
The link:src/connect/converter/charset/double_byte/README.adoc[double-byte mapping reference] records the source-derived tables, aliases, and replacement rules.
Big5-HKSCS, Big5-HKSCS-2001, MS950-HKSCS, and MS950-HKSCS-XP add four charsets with 14 registered names, including the Java `x-` prefixes where required.
Their overlays preserve BMP and supplementary mappings, XP private-use characters, and Big5 or MS950 fallback; each complete unmappable pair consumes both bytes, including an ASCII or zero trail.
HKSCS decoding does not activate Big5-Solaris, and its existing seven overlay mappings remain unchanged by Solaris activation.
The link:src/connect/converter/charset/double_byte/hkscs/README.adoc[HKSCS reference] records their source provenance, aliases, and replacement behavior.
The DBCS-only JIS0208, JIS0212, IBM300, and IBM834 decoders map raw pairs with no ASCII or shift-mode bypass; each unmappable pair and unmatched final byte produces a replacement.
The simple EUC IBM1383 and IBM970 decoders preserve ASCII and C1 controls, retry the byte after an unmappable SS2/SS3 prefix, and consume other unmappable pairs together.
These six charsets have 36 registered names documented in the link:src/connect/converter/charset/double_byte/subclasses/README.adoc[DBCS-only and simple EUC reference].
The mixed EBCDIC IBM1364/930/933/935/937/939 charsets support all 30 registered names and begin every record in single-byte mode.
SO and SI switch modes; invalid repeated shifts produce a replacement, and controls consumed as double-byte trails remain part of the replaced pair.
Their EBCDIC controls, symbols, text mappings, and record-local shift behavior are documented in the link:src/connect/converter/charset/double_byte/ebcdic/README.adoc[mixed EBCDIC reference].
EUC-JP, x-euc-jp-linux, and x-eucJP-Open support all 14 registered names with ASCII, halfwidth JIS0201, and JIS0208 mappings.
The Linux variant rejects JIS0212 triples; the Solaris variant adds its JIS0208 mappings and uses the full Solaris JIS0212 table.
Their complete-group replacements and terminal truncation behavior are documented in the link:src/connect/converter/charset/double_byte/euc_jp/README.adoc[EUC-JP reference].
The IBM29626C and IBM33722 Japanese EUC charsets support all 13 registered names with C1 controls, extra SS2 symbols, and separate G1/G3 private-use ranges.
Their symbol differences, IBM943-filtered JIS0212 mappings, and variant-specific malformed-input lengths are documented in the link:src/connect/converter/charset/double_byte/ibm_euc/README.adoc[IBM Japanese EUC reference].
EUC-TW and IBM964 support all 11 registered names through separate plane-selection and replacement rules.
The standard decoder includes supplementary CNS planes, while IBM964 preserves C1 controls and its private-use planes, as described in the link:src/connect/converter/charset/double_byte/euc_tw/README.adoc[EUC-TW and IBM964 reference].
ISO-2022-JP, ISO-2022-JP-2, x-windows-50220, x-windows-50221, and x-windows-iso2022jp support all 17 registered names with record-local designation and shift state.
Their JIS mapping differences, Roman/Kana modes, optional JIS0212 designation, and replacement boundaries are documented in the link:src/connect/converter/charset/double_byte/iso2022jp/README.adoc[ISO-2022-JP reference].
ISO-2022-CN, its CNS/GB variants, and ISO-2022-KR support all 12 registered names with record-local shift and designation state.
Their GB2312/KSC5601 and CNS mappings, high-byte interpretation, BMP-only CNS single shifts, and distinct escape-error lengths are documented in the link:src/connect/converter/charset/double_byte/iso2022cnkr/README.adoc[ISO-2022-CN/KR reference].
ISCII91 supports all six registered names with delayed Nukta compositions, Halant joiners, and record-local pending-character state.
Its signed-byte indexing, attribute handling, retained error context, and terminal flush behavior are documented in the link:src/connect/converter/charset/iscii91/README.adoc[ISCII91 reference].
GB18030 and its `gb18030-2022` alias use the pinned default Java 25 mappings, including supplementary scalars and the provider's four-byte replacement boundaries.
The conditional `gb18030-2000` alias is outside the default-provider configuration, as described in the link:src/connect/converter/charset/double_byte/gb18030/README.adoc[GB18030 reference].
x-SJIS_0213 and x-MS932_0213 support all 13 registered names, including the `sjis:2004` and `windows-932:2004` aliases.
Their MS932 BMP precedence, supplementary scalars, combining sequences, and replacement boundaries are documented in the link:src/connect/converter/charset/double_byte/jis0213/README.adoc[JIS0213 reference].
Extended-provider names accept Java's four Unicode case equivalents through their own canonical-name and alias inventory, as described in the link:src/connect/converter/charset/extended/README.adoc[extended name lookup reference].

x-JISAutoDetect and JISAutoDetect select ISO-2022-JP, EUC-JP, or Shift_JIS under the pinned Linux provider profile.
Their probe priority, consumed-input comparison, Japanese-text heuristic, suffix replay, and record reset are documented in the link:src/connect/converter/charset/double_byte/jis_auto_detect/README.adoc[JIS auto-detection reference].

Avro reader resolution is an immutable action graph over the writer and reader schemas.
It applies named and field aliases, record projection and defaults, ordered reader-union selection, numeric and string/bytes promotions, enum defaults, and recursive schema pairs using Avro 1.11.4 `Resolver` rules.
Incompatible writer-union branches fail when selected; selected reader defaults use the first union branch.
Binary reader resolution skips projected-away fields directly from the wire and reserves space for selected values and defaults.
Binary datum readers consume one value and ignore its suffix; the Confluent root-bytes path retains the complete payload.
Selected collection blocks consume their item counts; projected negative-count blocks skip their declared byte lengths.
Malformed skipped byte lengths may rewind within the datum slice and the pinned decoder's first-compaction window, with cumulative rewind distance limited to one datum length per decoding pass.
Rewinds before that window, Java cursor integer wrapping, and rewinds into the Confluent framing prefix remain compatibility boundaries.
The pinned byte-array decoder can expose that prefix for payloads of at least 16 bytes before its first compaction; the native decoder owns only the datum slice.
Schema-only datum plans defer Connect graph construction until the output schema is selected.
Reader output retains the writer Registry version and the converter's nonrecord writer-schema behavior.
The physical decoder leaves logical values as their integer or byte representation until Connect conversion.
Local raw JSON default descriptors retain oversized integer spelling and floating exponents without changing other JSON consumers.

The Avro migration codec follows `AvroSchemaUtils.toJson` and Avro 1.11.4 `JsonDecoder`: nested union labels, ISO-8859-1 binary strings, record field reordering and aliases, and required JSON fields remain distinct from binary reader-default resolution.
`AvroDatum` couples the physical datum with its actual schema; each passive `AvroMap` retains its raw keys, insertion history, and reader key class.
Its caller-owned map replay follows OpenJDK 21 `HashMap` bucket order, resizing, collision trees, and duplicate replacement at every map depth.
Collision trees use ordered lookup and linked iteration to preserve replacement and root movement without scanning entire buckets.
Malformed binary strings retain their original bytes through string/bytes promotions and use Java UTF-8 replacement at text conversion.
Distinct malformed `Utf8` map keys retain byte identity through reader selection; String reader keys, migration JSON properties, and Connect String keys collapse duplicates at their respective conversion boundaries.
Resolution, selected Connect graphs, JSON expansion, and detached conversion results retain their admitted memory charges through their owners.
The resolver, migration, output-selection, default-number, malformed UTF-8, and map-order regression sources have not been executed.
Registry HTTP and dead-letter producer clients accept empty Java identity and trust stores; server identity admission still requires a usable key.
Explicit empty trust stores retain no default roots and fail untrusted handshakes.
