= Native Kafka producer TLS

Registry dead-letter action options use Kafka's Java configuration names.
An explicit `ssl.engine.factory.class=org.apache.kafka.common.security.ssl.DefaultSslEngineFactory` selects the same native Java-configuration adapter as the omitted default.
Other factory classes require a native adapter.
`ssl.provider=SunJSSE` and `schema.registry.ssl.provider=SunJSSE` select the built-in native context adapter used by the omitted default.
Provider names are case-sensitive.
Kafka trims Java configuration strings through U+0020; Registry preserves provider strings and treats an empty value as the omitted default.
Other Java context providers require their own native adapter.
`ssl.keystore.location` accepts JKS or PKCS12 private-key stores and PEM files; PEM material also accepts `ssl.keystore.key` and `ssl.keystore.certificate.chain`.
Store and private-key passwords are independent.
`ssl.truststore.location` accepts the same store formats, and PEM roots also accept `ssl.truststore.certificates`.
A store file is limited to 4 MiB.
Java and librdkafka-native identity or trust inputs cannot both supply the same role.
The Kafka log and Connect source consumer continue to accept librdkafka-native properties, including OpenSSL cipher expressions.
They do not invoke the Java TLS configuration decoder.

The producer retains every decoded private-key entry.
An empty Java identity store supplies no client certificate.
An empty explicit Java truststore replaces default roots with an empty trust set; certificate acceptance is decided during the handshake.
Absent Java and native CA configuration uses the pinned Temurin 25.0.1+8 `cacerts` resource, retained with its provenance and license files in `src/tls/cacerts`.
The native client receives a fresh trust store containing exactly those decoded anchors.
Clients with retained Java or pinned trust material skip native platform-root discovery before installing that trust store.
Explicit native CA, CRL and identity settings retain their own loading and validation.
Registry HTTPS clients decode the same pinned resource into their native trust store, with the client retaining its admitted allocation.
They retain an explicitly empty Java truststore as empty.
Registry HTTPS constructs the pinned SSL context defaults, including Java-enabled TLS 1.2 CBC suites.
Registry's `cipher.suites` and `enabled.protocols` options are unused by the pinned `SslFactory` and socket consumer; their values do not change negotiation.
Registry treats password, inline-key and inline-certificate strings containing only characters through U+0020 as absent while preserving the bytes of other values.
An empty JKS or PKCS12 path supplies no store, while an explicitly empty PEM key path is opened and fails as a file.
The Registry hostname override disables name checks for an absent, empty or exact `none` endpoint-identification option; other values retain HTTPS name checks.
OAuth HTTPS retains its default hostname verification.
The link:src/connect/registry/http/README.adoc[Registry HTTP connector] retains caller-driven connection ownership and Java redirect, timeout and response-header behavior.
Explicit `ssl.ca.location` or `ssl.ca.pem` retains native CA loading; an explicit Java truststore, including an empty store, replaces the pinned anchors.
A per-connection certificate callback selects client identities using the configured Java key manager.
The eager `SunX509` path additionally checks native usability through OpenSSL's https://docs.openssl.org/3.0/man3/SSL_check_chain/[SSL_check_chain].
`ssl.keymanager.algorithm` selects `SunX509` by default; `NewSunX509` and its `PKIX` alias select the alternative built-in manager.
Registry HTTPS accepts the same names through `schema.registry.ssl.keymanager.algorithm`.
Algorithm names are case-insensitive.
Kafka applies Java ConfigDef trimming to algorithm names; Registry HTTPS preserves supplied whitespace and treats an empty name as the default.
`SunX509` chooses by requested key-type priority, then Java `HashMap` alias iteration order.
`NewSunX509` scans the Java store's alias enumeration, preferring a valid client certificate for the first requested key type.
It otherwise chooses the first valid certificate, then an expired certificate before one with incompatible client key usage or extended key usage.
Fallback ties use requested key-type priority, then store enumeration.
`NewSunX509` also applies the pinned Java algorithm constraints to every certificate in each candidate chain.
Java JKS and PKCS12 stores under `NewSunX509` retain encrypted private keys and select using certificate metadata before recovering the chosen entry.
An unavailable key password or malformed protected key on an unselected entry does not fail configuration.
Ordinary recovery failure on the selected entry supplies no client certificate and does not select another alias; memory-admission failures fail the callback.
The retained effective key password has its own admitted, zeroized buffer, with the store password used when no key password was supplied.
Recovered native keys retain independent reservations and both random-provider contexts on their SSL connection until native key cleanup completes.
PEM keys and `SunX509` Java keys remain eager.
Both transports keep the peer's certificate signature preferences separate from its CertificateVerify schemes.
TLS 1.3 uses `signature_algorithms_cert` when present, with the unfiltered `signature_algorithms` list as its fallback.
Certificate preferences set key-type priority, while the signing list must permit a CertificateVerify signature and TLS 1.2 certificate types restrict eligible key families.
`NewSunX509` checks every candidate certificate's signature algorithm against those certificate preferences, including the final supplied certificate.
Its peer check follows Java's JCA algorithm names, so the RSA-PSS wire schemes share one algorithm name even when their digest identifiers differ.
The native message callback retains the admitted certificate-request allocation on its SSL connection until replacement or connection destruction.
Registry HTTPS uses the same native certificate-request callback and TLS owners as the producer.
The selected entry supplies its key and certificate chain.
A request with no compatible entry sends no client certificate.
`ssl.trustmanager.algorithm` and `schema.registry.ssl.trustmanager.algorithm` default to `PKIX`, with the aliases `SunPKIX`, `X509` and `X.509`.
`SunX509` selects the built-in simple validator: it follows the supplied certificate order, replaces matching reissued trust anchors, and appends a trusted issuer when needed.
Reissued-anchor matching compares encoded public-key parameters with Java's NULL-parameter normalization, retaining distinctions such as RSA-PSS restrictions on the same modulus and exponent.
Its validation covers certificate signatures, validity, issuer chaining, CA path lengths, key usage, Netscape certificate types and unsupported critical extensions.
Simple validation and client authority hints compare distinguished names using Java X500Principal canonicalization, including Unicode case conversion and NFKD normalization.
Intermediate extended key usage does not constrain the simple validator.
A directly trusted leaf bypasses certificate validity and usage checks while retaining explicit certificate distrust checks.
`PKIX` follows Java's ordered-chain validation shortcut and otherwise builds a path from the supplied certificates.

* *Candidate search follows Java preference and branch rules.*
  Candidate preference follows AKI/SKID, trusted-issuer and common non-geographical ancestor rules through HashSet and TreeMap insertion and traversal.
** Repeated DER or repeated subject/public-key/parsed-SAN values are excluded.
   Successive self-issued candidates stop a search branch after anchor completion has been considered.
** The builder retries candidates rejected by path signatures, algorithms, constraints or certificate policy and limits paths to five non-self-issued intermediate certificates.
   Ordered validation has no builder depth limit.

* *Search allocations are admitted against the connection's memory budget.*
  Admission failures stop the search.
  Failed attempts and backtracked candidate frames release their reservations before later work.

* *Post-selection policy failures do not retry another anchor.*
  An exactly trusted leaf takes Java's PKIX early return.
  Other paths require a version-3 anchor to assert CA basic constraints and, when present, certificate-signing key usage.
** Anchor CA/key-usage checks and TLS end-entity/distrust policy run after path selection.

The native verifier accepts the exact selected chain and call-local Java self-issued classifications, with issuer names compared through Java X500Principal canonicalization.
Original certificates supply every signature check, callback certificate and returned chain; original anchors supply Java's anchor policy checks.
Anchor path lengths, name constraints, critical extensions, dates and self-signatures remain outside native path validation.
Temporary non-anchor metadata copies exclude noncritical AKI and SKID only after the shared Java identifier parser accepts their criticality, duplicate and malformed-extension rules.
These copies supply extension checks and are never used for signature verification or transmitted.
Ordered validation screens candidate anchors using canonical AKI key identifiers against original SKID extension bytes and signed serial numbers; absent SKID and pre-version-3 anchor serials follow Java's compatibility rules.
Builder anchor screening uses its distinct legacy-certificate validity-period rule.
Java self-issued intermediates retain the path-length and name-constraint exceptions, including version-1/version-2 key rollover immediately below an anchor in ordered validation.
Certificate validity is checked on every non-anchor member, while intermediate extended key usage does not restrict the path.
Leaf usage checks follow the Java TLS-server rules after path validation has consumed critical extensions.
Critical ordinary-policy qualifiers are rejected while Java's policy tree remains live; an absent or exhausted policy tree leaves later qualifiers unchecked, and anyPolicy qualifiers do not trigger rejection.
Policy processing starts with Java's default anyPolicy set and enforces explicit-policy, mapping and anyPolicy-inhibition counters, including the self-issued and final-certificate rules.
The four policy extensions use Java's BER parsing and duplicate handling: malformed noncritical extensions are absent, malformed critical extensions fail, and two successfully parsed copies of one extension fail.
The default Java PKIX critical-extension set is enforced independently of OpenSSL's larger supported-extension list; native signature verification uses the original certificates.
The selected path is checked against the pinned blocked-certificate list, digest and key-size constraints, JDK-root SHA-1 restriction, and Symantec, Entrust and Camerfirma distrust cutoffs.
Registry uses the same native PKIX path verifier and handshake signature implementation.
Native handshake security uses OpenSSL level 1 with Java certificate key limits, the EC-224 minimum, and compression disabled.
Certificate SHA-1 remains subject to the pinned path policy; SHA-1 handshake signatures remain disabled.
Trusted certificates follow Java HashSet bucket and tree ordering; ties between distinct certificates with the same hash use native object identity and are specific to the process.
The native simple validator checks the connection's configured DNS name or IP address and retains its peer-chain reservation until the connection is destroyed.
`SunX509` uses the pinned roots or Java-style trust material; native `ssl.ca.location` and `ssl.ca.pem` overrides remain available with `PKIX`.
Parsed store metadata, eager keys, chains, roots and their memory reservations belong to one immutable TLS value retained by the native client.
Native client destruction joins librdkafka's activity and destroys its OpenSSL objects before releasing that value.
Configuration duplication retains the same value, and creation failures release both the native configuration and its TLS ownership.
The vendored callback contract is documented in link:../../vendor/rdkafka/XTDB.adoc[the rdkafka fork].

`ssl.secure.random.implementation` selects the pinned built-in secure-random algorithms documented in link:src/tls/random/README.adoc[the random-provider adapter].
Kafka applies Java ConfigDef trimming; an empty supplied algorithm is invalid.
Registry uses the same algorithms through `schema.registry.ssl.secure.random.implementation`, preserving supplied whitespace and rejecting an empty algorithm.
Each TLS owner retains separate library contexts for selected protocol randomness and default signature randomness.
Private keys are destroyed before their library context, and native SSL objects are destroyed before their retained TLS owner.
Context reservations and shared native-device reservations remain admitted through their final owner.

`ssl.enabled.protocols` restricts negotiation to the configured protocols.
TLS 1.2 and TLS 1.3 are usable under the pinned OpenJDK 25.0.1 defaults; SSLv3, TLSv1 and TLSv1.1 remain disabled.
An empty protocol list uses the SSL context's default protocols, as in Kafka's https://github.com/apache/kafka/blob/4.4.0/clients/src/main/java/org/apache/kafka/common/security/ssl/DefaultSslEngineFactory.java[DefaultSslEngineFactory].
`ssl.protocol` selects SSL context defaults.
For `TLSv1.2`, the default cipher set contains TLS 1.2 suites; explicit enabled protocols and cipher suites can still select TLS 1.3 because https://github.com/openjdk/jdk25u/blob/jdk-25.0.1%2B8/src/java.base/share/classes/sun/security/ssl/SSLContextImpl.java[the Java context supports it].

`ssl.cipher.suites` accepts comma-separated Java names and their IANA aliases.
Each configured name is validated, including entries following a valid name.
TLS 1.2 and TLS 1.3 cipher sets are installed independently because https://docs.openssl.org/3.0/man3/SSL_CTX_set_cipher_list/[OpenSSL configures them separately].
Selecting only TLS 1.3 suites also prevents TLS 1.2 fallback.
The supported names and default preference order come from https://github.com/openjdk/jdk25u/blob/jdk-25.0.1%2B8/src/java.base/share/classes/sun/security/ssl/CipherSuite.java[OpenJDK 25.0.1 CipherSuite].
The adapter filters the disabled cipher families named by that release's https://github.com/openjdk/jdk25u/blob/jdk-25.0.1%2B8/src/java.base/share/conf/security/java.security[java.security].
A list containing only disabled suites or protocols produces no usable handshake.

== Open parity gaps

The eager `SunX509` store decoder still differs from Java provider alias lookup for raw mixed-case JKS aliases and some PKCS12 alias and issuer-chain cases.
Its JKS path recovers a private key before discarding an empty chain, while PKCS12 currently skips keys without a matched certificate before recovery; Java `SunX509KeyManagerImpl` recovers those keys first.
PKIX trust-anchor identity hashes and non-Comparable collision ties use native process identity; they do not reproduce a particular JVM run's `System.identityHashCode` inputs.
Public-key comparisons normalize encoded `X509Key` framing, including BER parameters, OIDs and unaligned bit strings.
Both known DH OIDs use SunJCE signed numeric `y`/`p`/`g` equality after validating the DH fields; optional private-value length does not affect equality.
Other AlgorithmParameters/KeyFactory acceptance and custom provider equality remain open.
Native name-constraint matching beyond Java self-issued exceptions and native algorithm availability still require qualification against Java's validator.
The builder's Java BasicConstraints/KeyUsage selectors accept parsed extensions alongside malformed noncritical copies, but native path metadata still needs the same parsing boundary to admit those complete paths.
JVM truststore system-property overrides and a separately provisioned `jssecacerts` file require an explicit native or Java-style truststore configuration.
These are open standard-configuration gaps.
Additional Java providers and credential extensions require native implementations.
The conservative material reservation bound still requires allocator measurement with large stores and concurrent handshakes.

== Regression sources

`tests/connect_registry_tls.rs` exercises public converter construction, Registry rule failure, the native dead-letter producer and an authenticated TLS listener.
It covers nonfirst issuer selection, EC signature selection, Java TLS 1.2 and TLS 1.3 cipher names, explicit overrides of context defaults, rejected protocol fallback, unmatched issuers and converter cleanup.
`tests/native_tls_ownership.rs` covers native configuration duplication, producer/consumer/admin retention, pre-TLS errors and setup callback errors or panics.
Unit sources cover admission before material loading, independent JKS passwords, mixed invalid cipher lists, both key-manager selection strategies, certificate usage and validity ranking, and native TLS 1.2/TLS 1.3 alias selection.
These sources have not been compiled or executed during the source-only phase.
