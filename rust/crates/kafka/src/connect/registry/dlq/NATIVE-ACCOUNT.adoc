= DLQ native byte account

The actual DlqProducer constructor attaches a NativeByteAccount to its ClientConfig before creating the native producer.
The existing checked capacity policy is three buffer.memory lengths plus 8MiB.
The same capacity reservation is shared with the producer's charge region and the account guard; shared handles do not reserve that capacity twice.
Native TLS configuration and captured material retain their existing earlier construction/error order.

DlqProducer and Settings remain passive values with their existing stored shape.
The account retains its existing Monitor Object role, with a re-evaluable drain condition over attached clients and charged native allocations.
Configuration clones and native clients keep that account alive through their existing ownership rules.
Metadata results also retain it, including when they outlive both DlqProducer and its originating context.
The final account release drains native owners before releasing its Rust capacity guard.

The selected ceiling covers native receive-frame storage and the implemented accounted request, completion and queue-owner classes.
It also admits decoded ApiVersions range arrays and stored legacy fallback copies before allocation for attached producers.
The old and candidate arrays keep separate charges until the broker installs the replacement and frees the old array.
Parser failure and downgrade discard their ranges through the same release path, and the broker releases its final stored ranges during teardown.
Admission denial leaves an existing array intact and ends the current connection setup with the native resource error.
Initial and downgraded ApiVersions requests admit their contiguous frame and buffer owner before entering the broker's outbound queue.
Their charge persists to final buffer release, including overlap with an earlier request during a downgrade.
It does not establish a complete producer allocation bound.
Ordinary Metadata responses admit a root arena and any additional storage segments as the parser reaches them.
The final native or Rust result owner retains all of these allocations.
Retained ordinary Metadata cache arenas admit their complete root, copied payloads, padding and reliable-merge slack on that same account before allocation.
Replacement admits the new arena while the old one remains charged, and common final destruction frees each arena before releasing its charge.
A denied cache replacement preserves its old entry and propagates the native resource error after any broker and live-topic updates already completed.
Ordinary Metadata rack computation admits one temporary matching-rack pointer buffer before allocation and retains its charge until the buffer is freed.
That scratch overlaps any additional parsed output segment on the same account and borrows rack strings owned by the parsed root and segments.
Scratch denial returns the native resource error before the current topic's live/cache update, preserving broker and earlier-topic effects and the existing failed-request hint cleanup.
Independent topic-info projection arenas have an internal fallible admission path retaining the actual client account through their final free.
Their classic consumer-group callers can use the explicit consumer-enabled SDK account profile; the DLQ constructor retains its existing producer-only attachment.
Client and broker construction, overlapping broker threads and stacks, live-topic storage, other independent clones and their rack scratch, admin and member-metadata output copies, native sort internals, consumer error owners, TLS/SASL storage, ordinary outbound requests, allocator overhead and the monitor itself still require separate admission bounds.
The Settings method names the native byte capacity rather than claiming that the formula bounds those excluded owners.
Java partitioner class validation and actual partition-selection integration retain their existing boundaries.

== Delivery event ownership

The SDK retains a native delivery event through all its Rust delivery callbacks.
Destroying that event subsequently frees its native messages, keys and headers.
DeliveryContext owns each pre-admitted Delivery receipt before enqueue, while the SDK opaque value carries only its live object identity.
A call-scoped registration guard removes an unaccepted receipt on errors or cancellation; successful enqueue consumes that guard.
Receipt reporting marks the already-owned receipt as reported and links its existing completion field without allocating or releasing the original record reservation.
It publishes that state before diagnostic output.
SDK diagnostic formatting retains its existing String allocation; only receipt reporting is allocation-free.
Diagnostic I/O errors cannot unwind the delivery callback.

DeliveryContext is a passive region owning the receipt objects and completion head as one mutex-protected value, with a retained header allowance.
It introduces no waiter, task, native callback or thread.
The private DlqProducer remains its sole polling owner and releases completed receipts only after the SDK poll or flush has returned.
That return follows native delivery-event destruction and pointer-array release.
Pending receipts remain owned until later reporting or client teardown.
The SDK's finite shutdown flush need not deliver every report, so no Rust Box is owned exclusively by an opaque native pointer.
Client teardown destroys its native field before its context; final context teardown removes every remaining pending or reported receipt after native destruction.
Both cleanup routes free each removed receipt Box before dropping its moved reservation fields.

An additional checked receipt allowance precedes header/Box creation and native enqueue.
Per-record receipt storage includes sixteen target receipt/pointer slots plus 4096 bytes for its Box, map-node growth and SDK delivery pointer-array storage.
The context has a separate checked sixteen-header-slots-plus 4096 allowance retained through its private client ownership, including the region's empty-root minimum.
These allowances concern receipt/event bookkeeping and record lease lifetime; they do not establish bounds for encoded/compressed requests or all native outbound owners.
