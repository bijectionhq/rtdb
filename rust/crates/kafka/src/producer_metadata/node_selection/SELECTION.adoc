= NetworkClient least-loaded node selection

The selector borrows the retained shuffled `Cluster.nodes()` list and reads the serialized network owner's live observations.
The returned borrow identifies the original node, including its address, and can be used by the network owner to acquire a request slot or start a connection.
The selector itself only reads the network state and consumes an offset observation.

`Snapshot::select_node` ranks the retained Cluster node list without copying it or replacing bootstrap Node objects with entries from the broker map.
An unqualified snapshot fails before the first random draw or connection observation.

`NetworkClient.leastLoadedNode` makes one bounded `Random.nextInt` call for a nonempty list and scans from that offset in Java integer order.
It returns immediately for a sendable node with zero in-flight requests.
Otherwise the first sendable minimum wins, followed by the last preparing node, then the first connectable node whose last attempt is oldest.
`ClusterConnectionStates.lastConnectAttemptMs` reports zero for a node it has never seen.
The connecting class includes a connection awaiting its API versions.

The independent ready flag follows the connection's READY state, throttle deadline and active channel readiness.
A request also needs capacity and a completed last send when the queue is nonempty.
The Java scan makes separate short-circuit reads for the ready flag and the send check until the ready flag becomes true.
A saturated ready connection can prevent rebootstrap even when there is no selected destination.
An empty list consults the source bootstrap configuration and current updater status without drawing an offset.

The borrow-only implementation has no retained allocation or timer.
The network owner supplies observations from the same connection inventory during the call.
An unavailable or invalid observation ends selection with a native failure at its demand point.
The signed Java list length and wraparound index are checked before accessing a native slice.
Transport targeting, native connection observations, production cluster-list ownership and request scheduling remain separate prerequisites for activation.
