= Native PostgreSQL frontend

`rtdb-pgwire` implements a PostgreSQL v3 frontend over native Rust sockets and `rtdb-node` sessions.
It uses native SQL preparation, query cursors, transaction resolution, authentication, Arrow IPC, and Transit codecs.
It starts no JVM process and delegates no application operation to a JVM server.
Arrow COPY admits unsigned integer cells at the corresponding signed width before submitting logical documents.
The retained input file preserves the original Arrow bytes.
The implementation and its regression test sources have not been compiled or executed during Phase 1.

== Composition and ownership

`ServerDriver::bind` opens the listener and returns a passive `ServerHandle` plus an unstarted driver.
The caller owns `ServerDriver::run`, requests shutdown through the handle, and awaits that run through every child join.
The driver bounds active connections and pending accepted sockets separately.
At capacity it closes the newly accepted socket without writing an unsolicited protocol response.
Shutdown closes admission, drains connections through the configured deadline, then cancels and joins the remaining connection regions.

The server and each connection are Active Objects.
Each authenticated connection owns one bounded reader child that detects peer termination while query execution is suspended.
The connection cancels and joins that reader before releasing the socket and session.
Its passive protocol transient owns prepared registrations, portals, the implicit-transaction marker, protocol mode, and optional COPY input.
Each portal owns its query cursor, current Arrow batch, row offset, cumulative row count, argument reservations, and cancellation token.
Prepared statements are immutable shared values; named registrations own their name/map charge.
The cancellation registry contains weak capabilities to connection-owned cancellation slots.
`ServerStatus` is a separate watch-channel monitor containing immutable observations.

The node must remain available until the server run has joined.
Dropping the run future is not a shutdown operation.
The handle exposes the bound address, current status, and a watch receiver for node telemetry composition.

== Authentication and protocol

The startup deadline covers the initial packet, SSL negotiation, TLS handshake, password exchange, and external authentication.
Startup and pre-authentication packets use the pinned 10,000-byte body limit; authenticated packets use the configured limit below one GiB.
An authenticated connection may remain idle indefinitely.
TLS uses the caller's native rustls server configuration; Java keystores are not consumed by this crate.
Trust, password, client-credentials, and device authentication delegate to `rtdb-auth`.
Device authentication sends the pinned authentication-success and URL notice before polling for the principal.
GSS negotiation is unsupported, matching the reference.

Simple Query supports multiple statements, implicit transaction completion, explicit transaction controls, empty statements, session parameters, SHOW, SQL PREPARE/EXECUTE, and COPY IN.
Simple Query preserves the parser's distinction between an initial statement mismatch and an unwanted first token for selected unquoted ASCII identifiers.
The error message uses the normalized statement batch, and the structured detail retains the original SQL message.
Shared control parsing and execution live in `rtdb-sql` and `rtdb-node`.
Parse/Bind/Describe/Execute/Close/Flush/Sync retain named prepared statements and portals across protocol messages.
Extended Parse validates the grammar of every SQL `PREPARE` body before sending ParseComplete.
Extended Parse charges any increase in the temporary syntax estimate between the complete Parse SQL input and the DBeaver namespace replacement.
The original input classification and any supplemental syntax charge stay reserved through ordinary SQL preparation.
Prepared statements admit their projected parameter OID capacity before expanding it.
A Bind admits its typed argument slots, reservation handles and retained portal name before creating the argument vectors.
The portal carries the charge through argument and cursor release.
During extended Parse, the node's memory budget covers the temporary tokens used to identify a control statement.
A directly prepared control retains its estimated parsing and binding allowance while a statement registration or bound portal holds it.
A bound portal retains the body selected at Bind when a later Parse replaces the statement name.
Executing the wrapper prepares its immediate child in the current session context.
Planning warnings use severity `WARNING` and SQLSTATE `01000` and are sent in occurrence order before ParseComplete, simple-query results, or SQL `PREPARE` completion.
A nested SQL `PREPARE` emits its terminal child's planning warnings when execution reaches that child.
Planning warnings are sent once per preparation.
Interactive DML warning planning is best-effort and is skipped when the client supplied parameter OIDs.
DML and unprepared control parameter descriptions retain the supplied OID list.
Query and EXECUTE descriptions use their planned placeholder count, padding missing OIDs with the fallback type and truncating excess OIDs.
Direct DML Bind requires matching argument and OID counts and a declared type for each non-null value.
SQL EXECUTE derives its DML argument types from expressions; SQL argument-width validation occurs during submission and transaction resolution.
Bind captures the query context and opens the cursor.
An extended-protocol error skips messages until Sync.
Sync completes an implicit transaction and leaves an explicit transaction open.
Execute limits suspend the portal even when the limit exactly matches the remaining rows; a subsequent Execute observes exhaustion and reports the cumulative count.
Statement close releases its associated portals, and transaction completion releases transaction-scoped portals.

The frontend preserves the reference's JDBC type-lookup exception inside a write transaction and its DBeaver projection rewrite from issue 4528.
It also preserves the canned keyword response.
SQL `PREPARE` bodies use ordinary SQL preparation for both queries.
The server read-only flag applies to DML; COPY independently enforces the connection's read-only transaction state.
`SET ROLE` follows the pinned no-response visitor.
CancelRequest uses the connection identifier and ignores the supplied secret; BackendKeyData sends zero as the secret.
These protocol choices are compatibility behavior, and the read-only/COPY and cancellation policies are recorded as open questions in `dev/doc/tx.allium`.

== Hosted capacity publication

The configured writer on an ordered placement may include
`INSERT INTO xt.hosted_capacity_declarations` in its catalog transaction.
The typed fields are `_id`, `relation`, `column`, `cap`, `predicate`, and
`writer_micros`. The ID equals the complete-key projection column. The
predicate is the Binary equality encoding from DeclareCapacity.v2 and
`writer_micros` is the observed revision of the installation's authority.
The statement stages an engine effect and leaves no row in the reserved target.
Capacity validation and the catalog writes share one ordered outcome.

== COPY and memory

A history reader can offer `/* rtdb-history-label-dictionary-v1 */` immediately inside the opening query parenthesis of `COPY (query) TO STDOUT WITH (FORMAT 'arrow-stream')`.
An owner that accepts the offer writes the Utf8 `label` projection as `Dictionary<Int32, Struct<id: FixedSizeBinary(16), canonical: Utf8>>`.
Older owners ignore the comment and return the ordinary Arrow schema.
Each replacement dictionary carries the exact stored spelling and the first 16 SHA-256 bytes of the Bijection native Root catalog label preimage.
The preimage concatenates `bijection.native-root-catalog.v1`, the big-endian 64-bit length of `label`, the bytes of `label`, the big-endian 64-bit length of the spelling, and the spelling's UTF-8 bytes.
The owner bounds each dictionary to 4,096 entries, 4,096 bytes per spelling and 1 MiB of distinct spelling bytes.
Dictionary rows use the same query basis and delivery grants as ordinary COPY.

The protocol state opens a temporary file at COPY admission and checks the configured disk-byte limit on every input frame.
Arrow streams up to 8 KiB can remain in the existing COPY scratch reservation with an empty temporary file.
If retention is unavailable or the stream grows past 8 KiB, COPY writes the retained prefix to the temporary file and spools the rest there.
Arrow files and Transit inputs use the temporary file throughout, and Arrow files seek to the footer during preflight.
CopyFail, disconnect, shutdown, and completion release the COPY input and its temporary file.
Transit JSON and MessagePack accept multiple top-level documents, resetting the Transit cache for each value.
Transit COPY commits one batch when no transaction is open.
Arrow file and stream COPY preserve record-batch boundaries and commit one transaction per batch outside an explicit transaction.
Inside an explicit transaction, all batches remain buffered until the user's commit or rollback.
Keyword document keys use the source normalization, including `:xt/id` to `_id`; the literal string `xt/id` remains a different key.

Frame, parameter, environment, prepared-registration, portal-descriptor, decoded-row, and encoded-value owners retain memory reservations.
Simple Query recognizes empty, line-comment-only, leading-semicolon and locale-independent keyword probe markers on the whole message before tokenization.
The marker check left-trims Java whitespace and removes one semicolon at the end or before the final line terminator, allowing ASCII regex whitespace after the semicolon.
A leading semicolon that survives that check returns NoData and a zero-row command tag.
The empty marker returns EmptyQueryResponse.
A normalized message selects the keyword marker when its prefix lowercases to `select string_agg(word, ',') from pg_catalog.pg_get_keywords()` under every Java default locale.
It ignores the rest of the message and returns NoData, one text row containing `xtdb`, and the `SELECT 1` command tag.
When the normalized whole-message prefix is locale-dependent, Simple Query validates the full message lexically and recognizes keyword probes per range using ASCII case-insensitive prefix matching.
A matching range bypasses SQL grammar checks and returns RowDescription, one text row containing `xtdb`, and the `SELECT 1` command tag.
Every other range must pass grammar validation before any statement runs.
On success the markers preserve an existing explicit transaction's status and settle an implicit transaction through the normal Simple Query path.
The DBeaver namespace query rewrite matches the complete normalized Simple message before tokenization.
The namespace query keeps its original projection when it appears in a multi-statement message.
Ordinary Simple Query retains the batch's parsed syntax before any statement can change the session.
The grammar validates nested PREPARE statements and requires a statement between separators.
The tokenizer charges the located-token array as it grows and releases it after syntax construction.
The input frame retains the source bytes for the duration of the message.
Nested SQL `PREPARE` statements reached in a Simple Query share a retained copy of the normalized message for later source positions.
A borrowed syntax reservation ends when preparation consumes the tree.
A retained syntax reservation follows its registered wrappers and bound portals.
Each statement resolves its parameters, embedded XTQL and control expressions against the context reached during execution.
A reached planning or execution error is reported in statement order, with subsequent statements subject to normal transaction status.
After CopyDone, Arrow COPY completes framing and allocation preflight before the first batch submission.
It checks metadata and compressed buffer lengths and holds the decoding reservation through the reader and each selected-value conversion.
In autocommit, the retained-stream reader borrows message metadata and suitably aligned bodies from the admitted bytes.
Unaligned bodies and explicit transactions on the retained path use independent body buffers.
The large-stream reader reuses bounded cached framing and reads the rest from the spool.
Transit COPY reserves the bounded file's decoding allowance before reading it into memory.
Temporary-file reads and writes run synchronously on the owning future; cancellation is observed between those operations and during asynchronous transaction work.
TLS internals, compiler scratch, and worst-case nested codec amplification still need complete retained-allocation qualification.

== Source regression coverage

`tests/protocol.rs` starts the native Node and server within each test source and speaks protocol frames directly.
It covers password authentication, simple transaction visibility and rollback, binary parameters/results, exact-limit portal suspension, extended-error recovery, fragmented Transit COPY, Arrow file/stream batch boundaries, COPY rollback/failure, pre-authentication limits, SSL refusal and upgrade with the pinned test certificate, and joined shutdown.
Internal cases cover frame reservation lifetime, malformed payloads, temporary-file cleanup, disk limits, cancellation registration, and peer-disconnect cancellation.
These cases map to `src/test/clojure/xtdb/pgwire_protocol_test.clj`, `src/test/clojure/xtdb/pgwire/copy_test.clj`, and the pinned `pgwire.clj`/`pgwire/io.clj` lifecycle.

Protocol references are https://www.postgresql.org/docs/17/protocol-message-formats.html[message formats] and https://www.postgresql.org/docs/17/protocol-flow.html[protocol flow].
TLS uses https://docs.rs/tokio-rustls/0.26.6/tokio_rustls/[tokio-rustls 0.26.6].
Interop with PostgreSQL clients, successful TLS handshakes, external authentication, connection-saturation fault injection, client-disconnect write races, and full resource accounting remain unexecuted qualification work.

An absent anomaly message becomes an empty primary `M` field; structured detail retains its JSON, JSON-LD or Transit presence rules.
Incomparable MIN/MAX inputs include the input vector type in structured detail.
Plain JSON renders it as EDN text, JSON-LD carries `xt:type`, and Transit carries the native type tag.
An unsupported MIN/MAX input reports its column type form.
Bind argument reclassification preserves the native decoder message, including absence.
The pinned raw-Throwable fallback for a message-less decoding failure requires the original throwable class and display; the passive anomaly does not retain that origin.
Production routing of raw host failures through this boundary still requires that conversion.
