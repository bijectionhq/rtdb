= Query execution source checkpoint

Scalar waits remain inside the cursor's active pull or opening future.
Query and database cancellation each interrupt SLEEP; dropping a pull releases its timer without cancelling sibling cursors.
Projection, filters, scan bounds, ordering, aggregates, correlated arguments and UNNEST use the same asynchronous evaluator.
`tests/volatile.rs` retains current-thread cancellation, scope-release and sibling-cursor assertions as source only.
Optimizer expression-count equivalence remains unqualified: the pinned selection rewrites do not declare a general volatility barrier.

This crate is Phase 1 implementation source.
It has not been compiled or executed, and the tests below are test source rather than passing parity evidence.
The crate does not establish that the complete RTDB implementation or its required production traces exist.

Physical unsigned scan cells and external query parameters enter execution as signed integers of the same width.
Runtime fields carry the corresponding recursive signed types, including typed nulls and empty lists, while advertised fields retain the prepared declaration.
Aggregate factories retain their declared setter target separately from their opened output-vector type.
This preserves declared MIN/MAX setter failures while SUM, AVG, percentiles, grouping, comparisons, and string conversion consume the admitted values.
Physical unsigned metadata bounds retain pages conservatively because signed reinterpretation does not preserve unsigned interval order.

== Ownership and calls

`CatalogSnapshot` is a passive immutable value containing the database names, table OIDs, schemas, partition snapshots, and storage handles used by a preparation or execution.
A transaction catalog accepts exactly one database and exactly its resolving partition, following `core/src/main/kotlin/xtdb/api/tx/OpenTx.kt`.
Normal query catalogs may contain several databases and partitions.
The caller must complete its basis barrier before constructing these snapshots.
Each retained snapshot keeps its captured transaction head separately from the requested system-time cap.

`QueryContext` is a passive execution region containing the query clock, timezone, memory budget, spill quota, and parent cancellation token.
`PreparedQuery::execute` makes a child cancellation token for that cursor, so dropping or cancelling one cursor does not cancel its siblings.
Executions made from the same context share its memory budget and spill quota.
`QueryCursor` owns the operator tree and advances it on the caller's coroutine.
Dropping a cursor releases its operator state and spill files.
A context over a store under local erasure custody encrypts each spill file under a key made for that file and held only in memory; other contexts spill as written.
The spill quota is unlimited by default, as XTDB has none; a node may configure one (`QueryOptions::spill_limit_bytes`), and zero is a quota like any other, refusing the first spilled byte.
A spill a configured quota refuses fails with `rtdb.query/spill-limit`, of kind `ConfigurationLimitExceeded`, reported as SQLSTATE `53400` as PostgreSQL reports an exceeded `temp_file_limit`.
For eligible Arrow queries, UNION ALL forwards its inputs' batches, preserving duplicates and input order.
A sort over input columns retains the batches and orders their row positions using the SQL key comparator.
Compatible signed integers, UTF-8 strings and UTC microsecond timestamps compare directly from Arrow buffers.
Other key layouts use the scalar SQL comparator.
The sort gathers payload columns in the new order and preserves input order for ties.
When a sort spills, its runs and merge output use Arrow IPC under the query's spill quota.
The passive Mark cursor completes its shared candidate build in memory or under the query spill quota before producing a nullable Boolean result.
An uncorrelated build precedes input evaluation and is shared across input rows; correlated builds retain their input row only while constructing and comparing that row's candidates.
Uncorrelated comparisons stop at true, while correlated VALUES comparisons demand the complete candidate batch.
Uncorrelated scalar equality keys select candidates by vector hash and retain whole-build null facts; Listy and struct candidate types compare every row.
Scalar keyed spills follow the ordinary hash join partition schedule after fully consuming the probe input.
Keyless and nested-key spills retain one probe page and visit every build partition, skipping rows already marked true.
Candidate files and temporary rows are released with the cursor or the current correlated evaluation, including failure and cancellation.
Returned `OwnedBatch` values and cloned Arrow arrays retain their own allocation reservations after the cursor has gone away.

`QueryCursor::schema` retains the advertised result fields.
Each passive immutable `EmittedRelation` owns its exact logical relation, resolved batch fields, typed children and aggregate factories.
Operator opening consumes this artifact; deferred inputs and correlated cursors retain the emitted subtree they will open.
The tree and any cursor retaining a subtree share the schema allocation reservation.
`QueryCursor::from_rows` retains a charged `RuntimeSchema` for its fixed output fields.
The recursive derivation reserves its transient schema work before construction and uses the execution's pinned `CatalogSnapshot`, after dependency validation.
Exact virtual-table definitions supply NULL types for absent scan columns; ordinary tables retain their validated scan types, including `xt.txs` and persisted tables in the `xt` schema.
Projection, correlation, joins, grouping keys, sets, and windows propagate these runtime fields without inspecting observed row values.
Each aggregate node owns passive `AggregateTypes` descriptors shared by its output schema and executor.
The descriptor keeps the actual input type for vector dispatch and the emitted factory type for numeric output; array elements retain their emitted types with runtime nullability promotion.
Physical data pages can have narrower fields than the snapshot schema; this derivation retains the snapshot's declared union legs for those scans.
`BoundParameters` retains parameter cells and their complete declared vector types as one immutable charged value.
An untyped manual query infers Null when its raw null argument cannot inhabit the annotated nonnullable field.
Apply and Mark derive capture types from the runtime independent schema before evaluating the selected row, preserving unselected union legs through nested dependent queries.
The dependent runtime schema and scalar evaluator consume that same type vector; a stale preparation annotation does not narrow a capture.

The prepared/runtime distinction follows `scan-vec-types`, `with-absent-cols`, `ProjectionSpec.Identity`, and `expression/->expression-projection-spec` in the pinned implementation.
Virtual temporal endpoints prepare as timestamp fields and produce NULL vectors; periods built from two absent endpoints produce the unbounded range.
`rtdb-sql/tests/periods.rs` retains direct, correlated, nested, outer-join, and ordinary-table counterexamples as unexecuted source assertions.

`PreparedQuery` contains an immutable relation, query settings and captured table dependencies.
Execution rejects changed table OIDs or column types with `rtdb.query/stale-plan`.
A caller must bind and prepare again against the new snapshot rather than reusing a schema that lacks newly introduced union legs.
Parameters are positional `Value` values and remain charged while their execution retains them.
SQL callers construct it with `from_prepared` to retain query-level `SETTING` metadata.
The passive `ReadBasis` value retains the effective per-partition basis, encoded snapshot token, independent API snapshot-time cap, exact engine-clock fallback and allocation reservation.
`QueryContext.current_time` retains seconds and nanoseconds through scalar execution.
Default valid-time points and null AT fallbacks convert it to microseconds only when the scan requests that boundary.
Opening a query resolves literal/parameter settings, validates requested times against captured heads, then caps visibility within those same snapshots.
An unevaluated setting form reaches query opening without a scalar result type; opening rejects it only when the setting is consumed.
`SNAPSHOT_TOKEN` reads the effective basis, preserving nanoseconds and unrecognized database entries from supplied tokens.
The source intentionally retains `query.clj`'s ignored planned `SNAPSHOT_TIME`; the API cap remains effective after a SQL token override.
No setting opens a newer catalog or changes a sibling execution's clock or basis.
Correlated apply holds the independent row while its dependent cursor executes and restores the previous parameter scope on the next independent row.

The operator states are passive, single-writer transients.
No operator starts a detached task or owns a transaction, ingestion, replication, or node lifecycle loop.
Spill files are scoped temporary resources with a retained-byte quota.

== Query tracing

Operator evidence is attached to the producing cursor's span as numeric attributes with fixed keys.
A traced operator boundary collects its own attributes, including those of its internal cursor adapters.
`cursor.predicate.scalar_fallbacks` and `cursor.projection.scalar_fallbacks` count nonempty batch evaluations that enter the scalar evaluator.
An expression evaluated across several rows contributes one fallback for that batch.
The count includes a reached fallback that discards the entire input batch or encounters a scalar error.
Operators sample their existing batch boundaries when query tracing is enabled.

`cursor.peak_memory_bytes` reports the peak reservation in the operator's memory scope.
`query.spill_region_peak_bytes` reports the existing high-water mark for bytes reserved by all spill files in the query context.
Multiple executions opened from one context can share that spill region.
The public `EXPLAIN ANALYZE` report uses its existing schema.

== Implemented source paths

* Visibility resolution merges each common trie task in IID order and descending system time, with newer segments first at equal system times.
  Emitted rows are grouped by contributing source page, with persisted pages before live pages.
* Persisted scans open the Arrow footer and request the pages that survive pruning.
  Compatible uncompressed columns can keep their source buffers through IPC decoding and through contiguous scan selections.
  Compatible lists and structs stay columnar through scan projection.
  Projected columns use Arrow nulls for pages where the field is absent when the other pages share a layout or form a scalar union.
  A dense union with compatible children stays columnar through sparse projection and keeps its Arrow array when it matches the result layout.
  The query cursor also adapts compatible Arrow layouts to the declared result, including mixed unions and newly nullable struct fields.
  Scan columns that need layout alignment keep source vectors and row positions through identity projection and filtering.
  Evaluation reads each selected cell under its source layout, so earlier struct versions keep their original keys.
  The cursor aligns compatible selected layouts and emits sparse fixed-size list selections using Arrow buffers.
  The same selection works on maps from the live index.
  The buffer pool can retain decoded pages and parsed footers independently of the file's encoded payload.
* The temporal resolver sees puts, deletes, and erases before a projected document reaches a value predicate.
* Temporal file selection includes live candidates before dropping persisted files.
* Page selection uses temporal summaries, recency ceilings, and IID ranges, with a bypass option for comparison tests.
  Trie recency dates retain the Java calendar range; UTC midnight scan ceilings require a representable signed 64-bit microsecond value.
  `xt.trie_stats.recency` narrows the epoch day to its stored Date32 value at the system-table boundary.
* A persisted page with a known zero non-null count cannot supply a matching row for a scan with one direct `IS NOT NULL` predicate on that document column.
  Missing or ambiguous counts leave the page eligible under this check.
  Page selection retains pages whose events can constrain or erase matching history.
* Metadata IID paths begin at the metadata root; a trie key's partition is a coarse file filter rather than an additional root prefix.
* Projection, filters, offset/fetch, union-all, and unnest advance incrementally.
* Inner, outer, semi, and anti joins accumulate complete build pages and use in-memory hashing or shuffled spill partitions.
* Cross joins retain left pages and publish each left/right page product in right-page, left-page order.
* DISTINCT holds every key it has seen in memory, as XTDB's `DistinctRelationMap` does, and fails rather than spills when the memory budget cannot hold them.
* Set operations use exact equality checks against spill files, including occurrence tracking for INTERSECT ALL and EXCEPT ALL.
* Sort preserves complete input-page accumulation, applies the configured stable object sorter within each run, and merges four adjacent runs per pass.
* Grouping assigns first-seen group IDs across complete input pages, then updates each aggregate column in specification order.
  Count, sum, average, min/max, boolean, variance, standard deviation, ordered array aggregates, and `vec-agg` share that page schedule.
  Groups and their per-group state stay in memory until the input ends, as in XTDB's group-by, and an ordered `ARRAY_AGG` sorts its rows in memory as XTDB's does; a query whose groups the memory budget cannot hold fails with a memory error rather than spilling.
  Percentiles are the exception: XTDB sorts their values with its external sorter, and so they spill as a sort does.
* Window execution assigns first-seen partition IDs and completes each ROW_NUMBER, LEAD, and LAG output column over the retained ordered relation.
A partitioned window can reuse a stable input sort when the bound key prefix, window directions and null placement, and the observed key layouts and batch boundaries agree.
Other inputs use the shared window sort path.
* Apply implements inner, left, scalar, exists, pull, and pull-many results, including cardinality errors and empty dependent relations.

Default valid time is the query clock.
Default system time is the partition snapshot basis.
Explicit all-system-time scans retain their lower bound and are capped at the basis's next representable microsecond.
Unconstrained relational algebra must request `TemporalFilter::All` explicitly.
An AT null expression uses the query clock, while null range endpoints use the unbounded endpoints.
A maximum-integer point is empty because no later microsecond is representable.

== Reference-sensitive behavior

The grouping comparator follows `core/src/main/clojure/xtdb/expression/map.clj`, `core/src/main/clojure/xtdb/expression/comparator.clj`, and the exact-one comparator check in `core/src/main/kotlin/xtdb/trie/MutableMemoryHashTrie.kt`.
Top-level null keys match for grouping and general DISTINCT, while nested nulls and NaNs can make compound keys nonreflexive.
Assigned group IDs keep each accepted input row in its own group even when its key would not compare equal to itself.

`wrap-distinct` in `core/src/main/clojure/xtdb/operator/group_by.clj` does not request the grouping comparator's null-key equality.
Aggregate DISTINCT therefore uses ordinary SQL equality and retains repeated null arguments in ARRAY_AGG.
The current source contains no planner override for that comparator choice; execution parity for this behavior remains pending.

`vec-agg` shares array accumulation and preserves null input cells.
An empty global input produces an empty vector, while an empty grouped input produces no rows.
Both families retain allocation reservations for collected cells in memory and release them when the cursor ends or is dropped.

Integer SUM follows the wrapping accumulation in `IntVector.kt` and `LongVector.kt` at the declared accumulator width.
Integer input narrows through the vector getter before addition, and floating accumulation rounds at the output vector width.
The reference has no byte or short accumulator implementation, and this executor reports that unsupported case.
SUM admits every input vector leg before reading a page's selection mask, including on empty callbacks and when every row is excluded.
Run-end input has no SUM or square-vector implementation in the reference factories.
Nullable decimal SUM follows `DecimalVector.sumInto`, where a null cell contributes scale-zero zero; a separate null union leg leaves the accumulator unchanged.
An actual `NullVector` input also leaves nullable decimal output null, including a decimal cast of an absent virtual temporal endpoint.
`DecimalVector.increment` adds at the operands' preferred scale and stores the resulting coefficient under the output vector's existing metadata.
SUM can exceed declared precision, while signed coefficient byte-width overflow fails.
The width check follows https://github.com/apache/arrow-java/blob/v19.0.0/vector/src/main/java/org/apache/arrow/vector/util/DecimalUtility.java[Arrow Java 19 DecimalUtility].
Decimal output does not accept integer input vectors, including an inactive integer union leg when its input batch is processed.
Query output reconstructs typed cells through `copy_array`, preserving exact decimal metadata and coefficients without ordinary-write precision checks.
Computed projections validate the selected result before that copy, including nested decimal cells; identity columns and canonical INSERT/UPDATE row packing retain raw cells.
Default and explicit same-type decimal casts therefore reject an overprecision result when projected, while boolean or text results may consume the same scalar intermediate without writing it as a decimal.
AVG completes the page's SUM pass before its COUNT pass.
Numeric average uses a double accumulator, preserving a first negative zero; duration average retains the duration unit, wrapping unit conversion and integer division.
With the reference's default null checks, SUM and AVG fail when a selected null slot belongs to a nullable Duration vector.
A separate null union leg or NullVector contributes nothing, and FILTER can exclude the null slot.
Variance and standard deviation first square the complete input vector, then run masked SUM, square-SUM and COUNT passes in that order.
Their square factory accepts nullable or nonnullable IntVector, LongVector and DoubleVector inputs; FloatVector, decimal, union, NullVector and run-end inputs fail on an actual callback.
The result uses the reference `Variance.kt` formula, including its floating-point cancellation behavior.
EVERY and ANY admit the reducing expression's emitted setter types before masked payload updates.
A first selected nonnull value must fit the boolean accumulator; subsequent values use the expression's boolean coercion.
MIN/MAX reducing aggregates reject decimal, byte, short, unsigned, half-float, and time output setters when input reaches the aggregate, following the available `set-value-code` methods in `expression.clj`.
Empty input does not invoke those setters and retains the nullable factory output.

The reference resolves vector null checks once from `XTDB_VECTOR_NULL_CHECKS`, then the `xtdb.vector.null-checks` JVM property, then `true`.
The explicit disabled-check configuration remains required native work.
It needs a captured configuration owner and access to null cells' physical backing values at Arrow input and primitive-reader boundaries; materialized `Value::Null` alone does not retain that payload.

ARRAY_AGG includes null arguments and returns null for an empty global group or a group excluded entirely by FILTER.
`ArrayAggAggregateSpec` opens its accumulator from emitted input metadata and copies actual vectors into it; an absent timestamp endpoint therefore produces a nullable timestamp element, including inside nested lists.
Filtered ARRAY_AGG and `vec-agg` groups can promote the list itself to nullable.
PULL and scalar apply return null for zero rows and reject multiple rows.
PULL-many returns null for zero rows and a one-element list for a single empty document, following `src/test/clojure/xtdb/xtql/plan_test.clj`'s `test-pull`.

== Remaining execution and resource work

The executor is row-oriented and does not establish vectorized execution or expected production throughput.
Keyless joins, anti-join candidate scans, spill-backed membership checks, and repeated group scans can be quadratic or worse across several grouping and aggregate operations.
Sort spills its record backing when its block and the scratch to order it reach `sort_memory_bytes`; semantic run and output-page boundaries remain determined by complete input callbacks.
Spill decisions read only the operator's configured share in `QueryOptions` (`sort_memory_bytes`, `materialized_memory_bytes`, `materialized_spill_rows`, `join_build_rows`, `top_k_rows`), never the budget's free bytes.
Grouping, aggregates and DISTINCT never spill, as in XTDB.
A refused allocation fails the query, as an Arrow allocation failure does in XTDB, rather than choosing another strategy; the exceptions are cache admissions (a compiled plan the keeper refuses runs unkept) and the search accelerators, which leave the query to the plain scan XTDB runs.
There is no parallel partition scheduling or coordinated scan-page spilling.
A single large output row, aggregate array, or set of overlapping active pages can exhaust the configured memory budget and return an error.

The scan accepts uncompressed, LZ4 and Zstandard Arrow trie data and metadata.
Scan initialization borrows live segments and visits their trie leaves using stack space bounded by trie depth.
The scan reserves query memory for the persisted candidate list before allocating space for references to trie catalog entries in the `Live` state.
It releases the reservation before planning scan tasks.
The scan reserves the candidate summary vector and selector worklists before allocation and releases them before reading file metadata.
It reserves the selected file indexes once their count is known and keeps that charge through the metadata visits.
It reserves inspected dictionary, row-descriptor and decoded-buffer bounds before opening the corresponding data.
Persisted metadata traversal reserves stack capacity before growth and stores each IID path inline.
The stack reservation is released after traversing each metadata file.
Live and persisted scan page descriptors reserve capacity from the query budget before growth, and the reservation stays with the scan partition.
The scan reserves capacity for selected persisted data-file descriptors from the query budget before allocating the descriptor vector, and releases the reservation when the descriptors are dropped.
The scan keeps the current entity's temporal ceiling charged within the scan task and reads each event's polygon through borrowed ranges.
The scan reserves result capacity before appending history fragments for an event and releases that reservation after projecting those fragments.

Memory reservations cover retained rows, output Arrow buffers, staged parameter values, decoded page bounds, and scoped spill work.
Several bounds are conservative estimates rather than proven physical-allocation limits.
Expression evaluation and some row cloning allocate before the resulting value is charged.
Arrow footer inspection, schema metadata, operator descriptors, temporary container capacities, and allocator bookkeeping are not comprehensively measured.
The object cache has a separate byte budget and retains encoded file leases independently of the query budget.
Strict peak-allocation guarantees remain unproved.

Cancellation checks occur between operations and rows, but CPU loops do not yet have a validated cooperative scheduling bound.
Spill file access uses synchronous filesystem calls on the caller's coroutine; cancellation does not interrupt an in-flight filesystem call.
No claim is made about cancellation latency.

External table providers, transaction-result shaping, network output, query preparation caches, and the required production traces are outside this source checkpoint.
The declared aggregate IR includes ordered-set continuous and discrete percentiles.
Their immutable passive descriptors carry the fraction and sort direction; the passive aggregate cursor resolves fraction parameters when it opens, including for empty input.
The caller-owned percentile input cursor excludes nulls and retains the complete group in an indexed record store before sorting its indices.
The configured memory threshold switches record backing to spill files without performing comparisons or splitting the group into sort runs.
The selected object sorter runs once over the complete group, then the cursor selects one rank or interpolates two ranks.
Descending percentile comparison swaps operands through the reference `Comparator.reversed()` contract; ordinary ORDER BY keeps its separate result-negation rule.
Empty groups emit NULL and remain present in the result.
Percentiles construct the ordered-vector comparator after consuming input, so unsupported list, struct, or mixed type legs fail even on empty input.
Ordinary sorting constructs that comparator for each nonempty run and skips it for empty input.
Numeric vector ordering preserves signed integer comparisons and otherwise uses Java Double.compare, including decimal values.
Within-run and percentile ties retain input order; ordinary sort ties across runs follow the reference priority queue.
Scalar predicates and MIN/MAX retain their separate comparison rules.
`tests/percentiles.rs` maps `group_by_test.clj`'s trailing empty-group regression and adds spill, cancellation, quota, and plan-validation source assertions.
The formulas, parameter coercion, and output types follow `operator/group_by.clj`'s percentile factories; numeric rank errors currently use a native anomaly code rather than the JVM exception diagnostic.
Compilation, execution, differential checks, fixture validation, resource measurements, and the required complete-workspace checks remain deferred until the user's full-implementation gate is satisfied.

`Snapshot::with_system_time_cap` gives each partition an independent query basis without changing its durable transaction key.
It retains the captured catalog and live generations, rejects a basis beyond that captured head, and leaves system time unconstrained for `None`.
Missing and null partition entries in a snapshot token use that unconstrained dimension; explicit temporal filters still apply.
An empty token can therefore expose several historical versions, and a transaction pinned before a database's first write can observe a later applied generation while retaining its null token entry.
This follows the pinned query implementation; `tx.allium` records the unresolved isolation contract for that case.
The source regressions in `tests/scan.rs` retain a capped live view across block adoption and exercise distinct caps in one multi-partition database snapshot.

== System catalog source

Virtual `information_schema` and `pg_catalog` relations resolve from declared schemas and execute through passive `SystemCursor` instances.
Their rows derive from the captured table registry, column types, database names, and shared PostgreSQL descriptors.
The column ordinals in `information_schema.columns` and `pg_attribute` assign names beginning with an underscore first, then sort names within each group in UTF-16 code unit order.
`pg_roles` emits login names before grant-only roles and orders names within each group the same way.
The native float array types `_float4` (OID 1021) and `_float8` (OID 1022) are discoverable through `pg_type`, including the links from their element types.
The declared empty constraint, dependency, extension, and index relations follow the pinned JVM information-schema producers.
`xt.live_tables`, `xt.live_columns`, and `xt.trie_stats` read retained partition generations.
`xt.live_trie_artefacts` reports one row per recorded object reachable from a live trie, including partition group objects shared by multiple tries.
Its rows identify the table, object, definition version, and current or historical family.
`file_size` is the published object's recorded size in bytes, or null when the record has no size.
`SystemCursor` computes its allocation bound by borrowing live segments and counting trie catalog entries in place.
`xt.live_tables` and `xt.live_columns` borrow the same segments to produce rows.
Runtime user, role, and metric relations require an explicit `CatalogRuntime`; an absent provider reports an unavailable anomaly when that relation is scanned.
`CatalogRows` retains each provider result's allocation lease while catalog conversion reserves its own rows.
Primary role membership uses the runtime's current primary watermark independently of the outer query basis.
The native node source tests retain the upstream catalog fixture identities.
Catalog schema enumeration and parser metadata allocations remain within the resource qualifications above.

== Bounded inspection sources

Inspection scans extract literal or positional-parameter bounds from conjunctions of comparisons and retain the ordinary row filter.
Direct-column projections translate bound column identities through aliases.
Log tables require both `msg_id` bounds, `xt.block_files` requires both `block_idx` bounds, and table-block tables require equality predicates on `table_name` and `block_idx`.
The runtime supplies passive finite cursors; each returned page owns its reservation, and projection acquires its own reservation before cloning selected values.
`QueryCursor::from_rows` adopts pre-reserved scalar rows for shared SHOW execution and validates the complete retained row capacity before publishing the cursor.

== Query observation

Contexts may carry a passive `ExecutionObserver` for public connection queries.
Each successfully opened cursor owns one duration sample through cancellation or drop, including time between client pulls.
Failed pulls record query errors; frontends report failures while consuming a returned batch through `record_consumer_error`.
Unobserved contexts keep internal transaction-result and role-membership queries outside connection metrics.

== Explain and materialized queries

`PreparedQuery::from_prepared` reserves retained preparation metadata from the supplied budget.
Its passive preparation pass prunes unused scan columns, applies single-column predicates after temporal resolution, and combines compatible ordering and row bounds into a production sort cursor.
`execute`, `execute_with_text`, and the node's shared prepared-query opening path are asynchronous.
Referenced materialized relations open before they return; `EXPLAIN ANALYZE` also consumes and closes the underlying query before returning its result cursor.
Materialized replay retains every bound input page, including empty pages, in one framed spill value shared by independent reference cursors.
Each reference reconstructs the original page boundaries before the client batch size is applied.

`EXPLAIN` returns typed `depth`, `op`, and `explain` columns derived from the production relation tree.
`EXPLAIN ANALYZE` returns the reference's eleven-column schema, actual produced-page and row counts, operator durations, direct-child time subtraction, scan counters, and both operator and query allocation peaks.
`EXPLAIN` describes each join condition as a list of equi-key maps and residual predicates.
An unadvanced branch has zero counts and a null first-page duration.
The production page boundary applies to ordinary execution as well as analysis.
Values, Scan, Project and Sort expose their own input-derived pages; standalone filters skip empty selections and coalesce small pages after the first 100 rows.
An empty Values row table produces no callback; a unit table produces one zero-column row.
Actual empty callbacks supplied by other cursors retain each operator's preparation and forwarding contract.
Limit slices complete child pages, while Union, Distinct, Intersect and Except preserve each nonempty source-page selection.
SortLimit preserves the source sort accumulation and limited-output page boundaries before applying its offset.
Project evaluates one complete expression column before beginning the next column, retaining the unpublished output rows until every column succeeds.
Project and Filter prepare expression metadata once for each input page, including empty pages; an exhausted input does not trigger preparation.
Apply completes every dependent invocation for one independent input page before publishing its output, including an empty result page.
Unnest prepares its collection expression once per input page, expands every row in order, and skips empty expansions.
The per-column and per-page preparation scopes retain compiled expression metadata through all corresponding row evaluations.
Computed sort keys use the same complete column-major page projection before rows enter the sort accumulator.
Mark produces a complete probe-page result; a correlated mark consumes every comparison in its current dependent page and stops before later pages once that page contains a true result.
Correlated marks retain empty independent pages, while shared-build marks skip empty outputs.
Aggregate and Window finish their entire result before publishing one nonempty page; an empty global aggregate retains its normal single row.
Window partition mapping preserves semantic input pages, including empty pages, through computed sort-key preparation.
