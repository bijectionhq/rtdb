= Replication

This crate contains source for term admission, the partition driver, source resolution dispatch, ordered replica append, block production and adoption, recovery, and applied-progress waits.
It remains in Phase 1: no Rust build, test, server, or runtime parity check has run.

The leader accepts an exclusive compactor-reset command against a captured trie catalog and open-block index while its staging pipeline is idle.
`LeaderState` is passive term-owned state; its passive `CompactorReset` retains a block target, completion sender and manifest reservations until adoption or term teardown.
The driver publishes a normal block boundary after replacing the catalog and acknowledges the reset only after adopting that block.
Term loss fails the reset receipt, so the maintenance caller cannot delete compacted files on that receipt.

`ReplicationConfig::default` cuts blocks at the reference library defaults, 102,400 rows or 15 minutes, and the server configuration falls back to the same constants.

A leader's put, delete or erase that fails with an error that is not the caller's writes `crashes/<node-id>/<instant truncated to seconds>/` to the database's object store before the failure stops ingestion, as the reference's `CrashLogger` does.
`crash.edn` holds the failed operation's `:table`, `:tx-key` and `:tx-op-idx`, a `:msg`, and the anomaly as `#xt/error`.
Next to it, the crash log writes `tx-ops.arrow` (the transaction's operations stream re-encoded as an Arrow file), the failed table's `live-trie.binpb` and, when the table has rows, `live-table.arrow`.
Given a `CrashSite`, it also writes `open-tx-table.arrow`, `open-tx-trie.binpb` and `query-rel.arrow`; the resolver does not yet hand its failed operation over, so the driver currently passes no site.
Crash-log progress and write failures are reported through `tracing` at `WARN`, never on stderr, and a write failure never replaces the original error.

Disabled indexing retains source submission and recovered state while the driver waits for shutdown without consuming either log.
An operator-selected skipped transaction saves its source payload under the pinned `skipped-txs` key before staging an aborted `xt.txs` row.
The abort uses the source position and smoothed system time, then follows ordinary append, read-back and apply ordering.
Its Arrow operations are not decoded and its skip does not increment the transaction error counter.

== Ownership and assembly

`ReplicationDriver::new` uses UTC wall time for timestamps generated by the replication layer.
`ReplicationDriver::new_with_clock` shares one supplied timestamp source with the driver, term appender and submission handles.
The source submission API takes caller timestamps, and source-derived transactions use the timestamps recorded by their log provider.
Tokio timers drive term assertions, and each log tail provider implements its own poll timeouts.

`PartitionLogs` is a passive capability over distinct source and replica logs, their epochs, a partition-scoped object store, its buffer pool, and a memory budget.
The encoded bytes of a log record own their retained memory charge after the encoder releases temporary scratch.
`BlockStore` is passive and reads or writes the same scoped storage namespace.
Its `recover` operation loads the greatest published block index, every table file named by that block, the table and trie catalogs, the next live block, the applied source position, and the boundary's replica fence.
Recovery itself does not require writable log capabilities.
Recovered source progress is the greater of the persisted source position and the configured source epoch floor.
The persisted transaction key, external token and block boundary retain their recorded identities.

An indexing-enabled writer restart checks the retained replica suffix for the selected block's matching upload when its boundary belongs to the configured replica epoch.
The writer walks backward across contiguous older catalogs until it reaches a missing catalog or a boundary that cannot anchor replay.
The historical check observes records without applying them to the restored partition.
An elected term queues each missing upload in block order and waits for its admitted read-back before submitting the next.
Each upload carries the original source position, external token, and L0 notifications recovered from that block's table files.
A follower still holding that boundary adopts it and drains its held records.
The restarted writer resumes ordinary source processing after completing the confirmations and adopting any later pending block.
The restored partition generation and applied progress are already in place on the restarted node.
A replica that already installed the block skips its current-storage upload before buffering for a later pending block.
A failure starting that later block during promotion preserves the recovered confirmation and returns the later block to the follower.
Historical replay first tries to open a tail from the oldest retained historical catalog.
If opening the tail reports that its first requested position precedes the retained log, the writer tries the next newer catalog when one exists.
Historical replay must admit the exact selected boundary with a compatible fence.
For a positive-term boundary without a sequence, a same-term unsequenced witness satisfies an unknown startup position.
Ordinary replica replay keeps using the startup fence seeded from the selected checkpoint.
Before appending an older confirmation, the writer verifies that its catalog, table blocks and required L0 files are still present in shared storage.
A failed historical replay discards the older repair candidates.
Failure to verify shared files or prepare an older upload discards the remaining older candidates.
The writer continues with the selected checkpoint in either case.
A follower still holding an unavailable older boundary may need to reopen read-only from the latest persisted checkpoint and replay its retained suffix.

`ProgressMonitor` owns one published value containing the applied source position, transaction key and most recent result, and the most recent non-null external token.
A driver publishes that value only after the corresponding effects apply.
`DriverStatus` is a separate watched value for role, observed term, consumed replica position, open block, adopted block, and the latest failed promotion.

`ReplicationDriver` is the active owner of election, replica input, source input, commands, resolution completion, production completion, and append-pump completion.
`ReplicationDriver::new` starts no task.
It validates a persisted source boundary against the configured log before returning a handle, including when indexing is disabled or the database cannot lead.
A newer source epoch is accepted; an older epoch or a same-epoch log ending before the persisted boundary fails database opening.
The node owns the task running `run`, invokes `ReplicationHandle::shutdown` to cancel it, and joins it before releasing storage, logs, or transaction dependencies.
An append pump completing successfully during that cancellation is an orderly shutdown, including when its completion wins the driver's event selection.
The driver cancels and joins its append pump at term end.
An in-flight transaction future owns its resolver and external writer; demotion drops that future and fails its receipt.
A block-production future observes cancellation between pages and completed storage operations, and the driver awaits it before the region ends.

`TxResolver`, `BlockCycle`, and pending write items are passive transients owned by the current term.
Each pending write owns its transaction or control body, assigned sequence, memory reservation, and optional completion sender.
There is no separate completion map.
`PendingBlock` is a passive transient retained across role changes; it owns the original boundary, its captured partition generation, and the already-admitted records held behind it.
The driver applies both count and byte limits to pending-block records and to readbacks held behind an in-flight resolution.

`DatabaseEffects` is the passive node/catalog capability for database-operation validation and application and primary-database configuration capture.
A secondary database supplies its explicit catalog policy through this capability.
Maintenance adapters call `ReplicationHandle::publish_compaction` and a captured `TermHandle::publish_deletions`.
Both await application; a term-scoped deletion receipt fails when that term ends.
The status stream announces block adoption after the leader has durably re-published the L0 notification to the source log.

== Processing order

The replica reader folds each delivered envelope into `TermFence` exactly once, including claims, stale records, and records later buffered behind a block.
Fenced and voided records are consumed without applying their bodies.
An admitted oversized envelope is fetched and checked against its outer term and sequence before the resolved body is retained or applied.
Held records replay below the fence that already admitted them.

A claim is a durable sequence-zero no-op in the next observed term.
Only a driver without a retained leader can claim, including while an inherited-block leader has not yet published its leading role.
Leadership is confirmed by reading back that node's own claim at a position that opened a strictly newer term.
The append pump assigns subsequent term sequences, fixes each append's order before accepting the next one, and emits heartbeat assertions independently of transaction resolution.
Ordinary transaction writes do not wait for durability before the pump accepts the next write.
Block-upload production retains its durability receipt.

Resolution sees the durable snapshot overlaid with every unresolved predecessor.
While a resolution future owns the resolver, the driver continues term admission and retains admitted readbacks under its configured limits.
A newer term ends the old region, transfers those retained records to follower application, and preserves any pending block.
A completed resolution returns its resolver before the driver enqueues the new transaction and drains held readbacks.

For this term's transaction readback, the driver removes the oldest staged transaction before validating its ID.
It applies the staged write atomically, applies any committed database operation carried by the readback, then publishes applied progress and completes the transaction receipt.
If the selected transaction has a receipt, it carries the original fault from ID validation, partition apply, database-operation application, or progress publication.
External transactions still queued receive `xtdb/leader-term-ended` during demotion.
Transactions from earlier terms import their encoded tables through `rtdb-tx::decode_replica`.
A missing legacy source position uses the transaction ID for ordinary databases and preserves the current source position for external-source databases.
A null external token preserves the last non-null token.

The resolve-side row gauge starts from applied live rows on promotion and advances when a transaction resolves.
A cut queues the boundary in append order and pauses further resolution until its matching upload is adopted.
Production writes L0 data, then its metadata completion marker, then all table-block files, and finally the block catalog.
The original boundary's term, sequence, replica position, source position, and token are persisted even when a later term produces the block.
A retry first reuses an already-published block after validating that boundary.
Partial retries use the boundary log timestamp when calculating table-catalog transitions, so immutable publication does not depend on retry wall time.

Adoption validates the loaded catalog against the retained boundary and changes catalogs, table metadata, and live-block state in one partition publication.
The upload's source watermark is published before held records drain.
A replay failure ends the driver; it does not reopen a follower after discarding the retained prefix.

== Compatibility qualifications

The applied-progress monitor intentionally differs from the pinned `api/log/Watchers.kt` and `db.allium`'s `ProcessingErrorHaltsNode`.
An already-satisfied prefix remains available after a fault or shutdown; unmet waits fail with the current fault or stopped outcome.
The replica driver publishes its stopped state and any fault it reports as one update.
The first recorded fault takes precedence.
The database owner publishes a selected peer fault before requesting worker shutdown when its category differs from `Interrupted`.
A replacement driver can clear an existing fault after its tail opens successfully.
Tail initialization preserves faults reported since driver construction, including on a fresh monitor.
This follows the object-boundaries monitor requirement, and runtime/reference compatibility remains unresolved rather than claimed.

The row gauge follows `BlockCutter.txResolved`, whose resolved count is initially seeded from applied rows.
The `live-index.allium` header and `db.allium`'s `AppendTx` prose name applied rows, while the live-index cut rule names resolved rows.
The existing open question in `live-index.allium` records this disagreement.

Idle empty blocks follow `BlockFlusher.kt` and its retention-anchor behavior from #5778.
The flush timer rearms when the persisted transaction changes; otherwise an elapsed deadline cuts even an empty block.
`LeaderFlushTimeout` currently requires data, so its open question remains unresolved.

Oversized-envelope admission precedes payload fetch, following the format/spec boundary.
The pinned JVM `LogProcessor.kt` resolves the payload before applying the term fence.
A fenced pointer to a missing object therefore has different failure behavior.

A leader applies a database operation carried by an inherited record before importing that transaction.
A follower imports the transaction before applying its committed database operation.
A leader propagates caller failures from database-operation application, and a follower swallows them.
The shared `ApplyDbOpToCatalog` deferred specification currently describes swallowing the fault for both roles.

Boundary-timestamp table transitions make partial immutable retries deterministic.
The pinned `BlockCutter` captures wall time while producing table blocks.
Garbage-age effects of this timestamp choice require reference qualification.

== Remaining review and integration obligations

These sources have not been compiled or exercised.
The node must provide concrete database effects, authorize ordinary submission, supervise the driver task, and supply source and replica log backends satisfying the durable-total-order contract.
A storage upload already started must finish before its owner is joined.
Leadership claims and all append receipts are owner-polled, so waiting for their durability does not block replica admission or cancellation.
A log backend owns accepted writes until its own driver is shut down and joined.
An external writer must own its resources within the supplied future and release them if the term drops that future.

Encoded buffers, pending replica envelopes, append items, transaction deltas, and page scratch use reservations.
Decoded block/table catalogs share their immutable protobuf allocations and reservation owners through recovery and snapshots.
Semantic catalog generations, protobuf container overhead, and metadata serialization still need a complete retained-allocation audit.
Backend tail batches can contain a large durable prefix; their maximum size is a backend obligation not yet enforced by the generic `LogTail` interface.
The block writer reserves selected-cell decoding and Arrow building separately, drops page scratch after each write, and retains a separate metadata estimate until serialization.
It copies leaf rows directly between matching Arrow layouts and reconciles differing input schemas against the captured table schema.
The metadata estimate remains conservative and requires nested-schema allocation qualification.

Promotion rollback, node/database shutdown composition, cross-node election faults, durable transport loss/reordering qualification, and external-source resume/confirmation require the complete node-level traces and Phase 2 fault/parity runs.
No runtime-parity, throughput, bounded-peak-memory, or production-readiness claim follows from this source checkpoint.
