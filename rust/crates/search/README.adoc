= rtdb-search

Bitemporal full-text search: the search files built over trie data files, the lane that builds them, and the accelerator that reads them.
The behaviour is specified in link:../../../dev/doc/fts.allium[fts.allium]; link:../../../dev/doc/fts-implementation.adoc[the implementation plan] maps each piece to the crate it lives in.

== Surfaces

`CREATE SEARCH INDEX name ON table (column, ...)` and `DROP SEARCH INDEX name` write and delete documents in `xt.search_indexes`.
`MATCH(column, query)` and `SEARCH_SCORE(column, query)` are scalar functions evaluated on resolved rows, with the analyzer in `rtdb-text`.
Use `SEARCH_SCORE(column, query, documents, tokens, frequencies)` when the ranking corpus is a filtered relation.
Supply the count of non-null documents, the sum of `SEARCH_LENGTH(column)`, and a list of per-term document counts in `SEARCH_TERMS(query)` order over the same rows.
This score uses only those statistics and the value being scored.
When `CREATE SEARCH INDEX IF NOT EXISTS` finds an existing definition at its ordered position, the original definition and its version are retained.
`MATCH` can still narrow candidates if a search file covers its column.
The node configuration's `search: {enabled, threads}` switches the lane and the scan accelerator together.
The server option `search: {writeFormat: 14}` selects the bounded Arrow layout for newly built files.
The option `search: {writeFormat: 15}` adds snapshot-native search packs and commit-time serving postings.
The option `search: {writeFormat: 16}` adds independent Arrow posting runs for public history-enabled indexes and resolves their candidates through the pinned primary history.
The server defaults to paged Arrow format 13.
During a rolling upgrade from a version without format 13 support, set `search: {writeFormat: 11}` on writers and compaction workers until all readers and maintenance lanes sharing the database support format 13.

== Pieces

`file`::
A search file covers a trie, an eligible partition group or a pack of settled tries with disjoint IID prefixes.
Formats 12 through 15 use Arrow IPC, and format 11 uses Tantivy.
Its manifest maps events, text runs and data pages to the group's members and records each run's bitemporal visibility.
The term directory locates the Arrow frequency and position batches and records score bounds for ranked search.
The artefact format version identifies the Arrow layout.
Format 14 follows authenticated range references from its root to term, posting, document and IID visibility pages.
Format 15 also records stable event versions and their primary Arrow positions.
The maintenance lane builds the configured version from primary data and can repair files in any of these formats.

`definitions`::
Reads the definitions in force from `xt.search_indexes` at a snapshot.

`lane`::
The `search` artefact kind: a builder per database that the core artefact lane drives.

`accelerate`::
The scan accelerator narrows candidate IIDs, accounts for events in other sources and supplies indexed `MATCH` answers.
For eligible ranked SQL limits, the accelerator verifies the competitive candidates at the query snapshot and can use integer `_id` bounds to prune score ties.
The two-argument SQL score uses unit weights.
The five-argument form uses the corpus supplied by the caller.
Held owned ranking uses the exact covered corpus at its retained snapshot.

== Ownership

The builder is a passive object driven by the artefact lane, which is the active object choosing among jobs, block signals and build requests.
The accelerator is passive and completes on the scan's coroutine; the corpus registry it writes is a per-query transient read only after the scan has opened.
Arrow pages hold their storage lease for as long as any reader uses their buffers.
The live worker publishes immutable posting coverage, and a snapshot scans the suffix outside its covered pages.
