= Server composition source

`HealthDriver` owns the health HTTP listener and a bounded set of joined connection tasks.
`HealthHandle` is a passive shutdown capability and retains the resolved address.
Each connection selects HTTP progress or cancellation, requests graceful shutdown, and closes after its drain deadline.
The listener stops accepting before joining every connection.
`HealthApplication` and the Prometheus renderer are passive components.

Routes correspond to `xtdb.healthz`: the index, metrics, started/alive/ready checks and POST `/system/finish-block`.
The finish-block database query parameter retains the reference's raw matching semantics.
The node captures startup replica targets once and evaluates liveness against current membership.
The Prometheus renderer exports counters, gauges and timer observations from the same metric provider used by SQL catalogs; rendered byte slices keep their memory reservation alive.
Each family is written once under Micrometer's `# HELP` and `# TYPE` lines, with a timer or distribution summary's maximum as its own `_max` gauge family.

`ServerDriver::open` decodes passive settings into a node, authenticator, provider registry, shared metrics registry, pgwire listeners, Flight SQL listener and health listener.
Every bind completes before a driver starts.
Ordinary listener-setup failures close the unstarted node and drain its resource region.
Inspection-only callers use `ServerDriver::close_without_run` to release bound listeners and drain resources without starting database workers.
The active server owner requests listener shutdown and joins their connection work before stopping and joining the node.
In Multi mode, shutdown then joins managed operations and closes each local write pipeline.
An active writer settles pending work and orders a lease release before storage closes.
A successor recovers through the sealed end and uses the durable release or lease expiry to establish authority.
Configured tracing starts a bounded OTLP HTTP exporter under the server owner.
Shutdown closes trace admission after joining database work, drains admitted exports within thirty seconds and joins the exporter before returning.
Trace exporter failures report diagnostics without failing user queries or transactions.
Configured CloudWatch and Azure Monitor modules construct native clients and publish from the shared registry's sixty-second step accumulators.
The exporter owner polls rollover independently of in-flight requests, skips overlapping publication for a destination and retains each request's metric snapshot through completion.
Shutdown joins current sends and publishes the final partial step within a thirty-second drain period.
CloudWatch requires the `cloudwatch` feature, included by `all-backends`, and uses the AWS SDK's default credential and region providers.
Its requests retain Micrometer's metric suffixes, millisecond timer units, percentile `phi` tags, value clamping, dimension limits and batches of at most one thousand data points.
The native client further subdivides those batches by a conservative encoded-byte bound to respect CloudWatch's one-MiB request ceiling; the pinned Micrometer partitioner limits only the point count.
Azure Monitor accepts Application Insights connection strings, including sovereign endpoint suffixes and explicit ingestion endpoints.
It publishes native JSON metric envelopes and retries only the rejected retryable indices from partial-acceptance responses.
Copied configuration, projected metric points, wire payloads and decoded response trees acquire reservations before allocation.
AWS SDK and HTTP/TLS internal allocations remain a separate runtime qualification.
The native publishers use bounded request and drain deadlines and a native SDK identity; they do not reproduce Application Insights Java's disk-backed retry channel or its process resource tags.
Closing follows Micrometer's start-time bookkeeping: an in-flight publication is awaited before the partial-step rollover, without another completed-step flush afterward.
Meter observations can cross a wall-clock boundary during live gauge I/O, as in the reference registry; the exporter does not claim an atomic observation of all meters.
`ServerHandle` retains passive node, authentication, metric and cancellation capabilities.
The command-line source handles YAML or EDN node startup, YAML ingest startup, playground startup, password hashing, help and version output.
`--build-info` prints JSON with compiled version, full source revision and time-zone data version/digest without opening a node.
Its values are independent of the `XTDB_VERSION` and `GIT_SHA` runtime overrides used by ordinary version output.
Playground listeners bind all IPv4 interfaces; ordinary Pgwire and Flight settings retain loopback defaults.
The EDN adapter preserves configured backend tags, aliases, numeric millisecond timeouts, `#env`, authentication-rule defaults and ignored top-level keys.
JVM object-valued configuration hooks require native replacements; the EDN reader accepts data and never evaluates code.
The process listens for interrupt and termination signals and reports shutdowns that take longer than ten seconds.
After that diagnostic deadline it continues joining the server owner, including admitted blocking I/O, before returning a failure status.
Announcement, export-capture and signal-registration errors also close or join their already-opened server resources.
JKS and PKCS#12 loading uses the configured store password for private keys and retains a memory charge with the TLS certificate resolver.
JKS password encoding uses UTF-16 code units, including supplementary characters.
The loader selects a usable signing algorithm from the available identities; certificate-alias selection and multiple PKCS#12 private identities still need compatibility work.

== Installed local startup

`rtdb initialize-standalone --state STAGE --name NAME --id UUID` installs one Default Local database in an empty private staging directory.
Supply the original database name and a canonical nonzero UUID chosen by the caller.
Publish the staging directory as the installation authority only after the command succeeds.
Keep the whole authority together, including `native-authority.json`, `journal/LOG`, `journal/REPLICA_LOG`, `objects/`, `token-keys/` and `checkpoint-keys/`.

`rtdb standalone --state AUTHORITY --name NAME --id UUID --certificate PEM --private-key PEM --password-file FILE --ready-file FILE --parent-stdin` reopens that authority and serves PostgreSQL and native Flight on distinct ephemeral IPv4 loopback ports.
Supply a certificate valid for `127.0.0.1`, its matching PEM key, and a private file containing a 64-digit hexadecimal password for `xtdb`.
Select the installed name in the PostgreSQL startup packet and the Flight database header.
The launcher atomically publishes a private protocol 3 receipt containing `database`, `installation`, `host`, `port` and `native_flight_port` after the exact writer has applied the retained startup positions.
`rtdb --build-info` advertises the same version as `standalone_protocol`.
The launcher requires `--parent-stdin` and drains on EOF or a termination signal.

Use `--custody-provider-config FILE` to supply the existing Original provider projection for this name and incarnation.
Server configuration can use `flightSql.custodyProviders[].owner` to select the authenticated Original principal for each native database. The principal needs write access to that database and its writer receipt still has to match the configured custody authority.
The native listener authenticates the configured Original's caller and resolves release authority through the applied writer and provider evidence.
The native launcher requires its own installed authority format.
Classic installations require a separate migration that preserves their data and custody.

== Node configuration

The node applies indexing enablement, skipped transaction IDs, trie limits, flush policy, compactor options, GC options and database membership from its startup settings.
`--memory-limit` or `RTDB_MEMORY_LIMIT_BYTES` controls the allocation ceiling shared by the cache and execution regions.
Without either, it is half the memory the process may use: physical memory, lowered to the tightest `memory.max` (cgroup v2) or `memory.limit_in_bytes` (cgroup v1) on the process's own cgroup, as `/proc/self/cgroup` names it, or on any ancestor.
A small container therefore gets a budget below one GiB rather than one the kernel would kill before it refuses; one GiB applies only when neither memory figure is known.
`ParsedConfiguration` owns startup settings and their allocation reservations until they transfer into the execution region.
CLI and embedded startup reserve parser events before parsing, each expanded YAML alias value before construction, and environment values before copying.
The data-only EDN adapter uses the same charged environment lookup and a bound on its input-derived syntax tree.
The startup owner retains the resulting lease through server shutdown.
`ProcessEnvironment` requires the host to exclude concurrent native environment mutation while configuration is being read.
`XTDB_JOIN_SPILL_THRESHOLD` sets the shared query option that disables join Bloom/IID pushdowns above the configured build-row count.
The default is 100,000, and zero or negative values disable filters for nonempty builds.
A value that is not a signed 64-bit integer fails startup, where XTDB's `parse-long` silently keeps the default.
YAML, EDN, ingest, and packaged server startup use the same captured environment value.
A PostgreSQL session whose client names no zone starts in the host's zone whatever `defaultTz` says, as XTDB seeds pgwire's `TimeZone` from the JVM's default zone.
`rtdb_java_date::default_timezone_id` finds it as OpenJDK does on Unix: the startup environment's `TZ`, else the zone `/etc/localtime` links to, else the file under `/usr/share/zoneinfo` with the same bytes as a copied `/etc/localtime`, else `GMT`.
A `TZ` the JVM does not know gives the host's current `GMT±hh:mm` offset rather than failing startup, and the ID converts to a session zone as `TimeZone.toZoneId` does, so `PST` starts sessions in `America/Los_Angeles`.
`defaultLocalErasure` and `defaultKafkaErasure` enroll fresh Default primaries for physical erasure; both default to `false`.
Without the YAML key, each reads `RTDB_DEFAULT_LOCAL_ERASURE` or `RTDB_DEFAULT_KAFKA_ERASURE`, where exactly `1` enables it, `0` or empty disables it, and any other value is a configuration error.
`defaultLocalErasure` applies only with `defaultV1Serving`; `defaultKafkaErasure` fails startup without native Kafka, `defaultV1Serving` and both original key vaults.
`RTDB_CLASSIC_KEY_VAULT`, `RTDB_V1_TOKEN_KEY_VAULT` and `RTDB_V1_CHECKPOINT_KEY_VAULT` are read with the rest of the startup environment into the node configuration's `key_vaults`, and `retain-repair-base` reads `RTDB_CLASSIC_KEY_VAULT` from its command's environment; backend construction and repair perform no lookup of their own.
`RTDB_APPLE_SYNC` selects the durable-write policy on Apple platforms for every `rtdb` and `rtdb-multi` command: absent, empty or `full` keeps `F_FULLFSYNC`, `fsync` selects plain `fsync`, and any other value fails startup.
`RTDB_TZDB_FILE` names an OpenJDK `tzdb.dat` that replaces the bundled time-zone rules without a rebuild, as replacing a JDK's `lib/tzdb.dat` does for XTDB; it is read on the first region-zone lookup, and a file that cannot be read or decoded fails every region-zone lookup (see link:../types/data/tzdb/README.adoc[timezone data]).
The binary validates and installs it once before dispatching the command; library code performs no lookup, and an embedding host that installs nothing gets `F_FULLFSYNC`.
`query.spillLimitBytes`, or `RTDB_QUERY_SPILL_LIMIT_BYTES` when the YAML sets none, caps the bytes one query's spill files may hold at once, and zero disables spilling.
XTDB has no such setting, so it carries the RTDB prefix; the earlier `XTDB_QUERY_SPILL_LIMIT_BYTES` spelling is no longer read.
Without either, the cap is half the free space on the temporary directory's filesystem when the node's options are built at startup, and at least one GiB; a value that is not a non-negative integer, or another key in the `query` section, fails startup.
Each spilling operator decides from its configured share of memory, never from what the budget has free.
Sorts spill sorted runs once their block, ordering scratch included, passes `sort_memory_bytes`, and merge them; hash aggregation and DISTINCT send rows of keys they do not yet hold to hash partitions on disk once they grow past `hash_memory_bytes` (64 MiB by default), then process each partition in turn.
A sort with a small `LIMIT` keeps only its candidate rows, whatever the input size.
`-Djava.util.Arrays.useLegacyMergeSort=true` selects the legacy OpenJDK object sorter for this node's queries and transaction-time queries.
The option may precede the command or appear among startup and maintenance options; repeated occurrences use the last value.
Only case-insensitive `true` enables it, without whitespace trimming; an absent property, a bare `-Djava.util.Arrays.useLegacyMergeSort`, or another value selects TimSort.
Each property argument is limited to 4096 UTF-8 bytes, and unknown property names are rejected.
The resolved `ObjectSort` value belongs to the unopened node configuration and its query contexts; execution performs no process-property lookup.
The CLI does not interpret `JAVA_TOOL_OPTIONS` or `JDK_JAVA_OPTIONS`; migrate this property into the explicit native argument.
The JVM reference captures the property when its `Arrays.LegacyMergeSort` holder initializes, so cutover inputs must retain the value used at that initialization rather than assuming a later property lookup recovers it.
This property transport does not expose disabled vector null checks; the physical reader and direct-getter migration remains required before that configuration can be accepted.
Transport and cryptographic libraries have allocations outside those explicit regions, and whole-process peak allocation qualification is pending.

The server constructs the shared disk cache from an explicit byte capacity or a ratio of filesystem capacity and registers its pinned, evictable, free and maximum byte gauges.
`export-snapshot DATABASE` opens the configured storage with indexing, compaction, tracing and listeners disabled.
Its dry run lists the captured file manifest; execution copies that manifest below `exports/b<block>_<UTC timestamp>/v06` within the source storage root.
The manifest contains one block catalog, its table blocks and the live/nascent trie pairs needed to recover that block.
Copies preserve object bytes, and identical retries are accepted.
`reset-compactor DATABASE` runs an exclusive maintenance node with compaction, automatic GC and listeners disabled.
Every other node, client and upstream writer must remain stopped until it finishes.
The command catches up, verifies the L0 pairs named by the installed checkpoint and publishes their replacement catalog.
On coordinated stores, it records the superseded compacted pairs before publication and submits them for retirement after adoption.
Physical removal can wait for readers to release their catalog and resumes during subsequent collection, including after a restart.
On uncoordinated stores, the command removes the compacted pairs after adoption.
`--dry-run` reports the replacement tries and prospective retirements after the catch-up flush.
`reset-compactor DATABASE --retained-base EXPORTED_STORAGE` rebuilds primary storage from the persisted repair anchor and the journal suffix through the maintenance node's catch-up checkpoint.
Use the detached export installed by `retain-repair-base` for the same local database and journal.
The reset reconstructs missing L0 pairs in that suffix, publishes rebuilt compacted pairs under fresh names, and retires old compacted files through the coordinated catalog floor.
If an original L0 pair still exists, the synchronized copy accepts identical bytes and refuses a conflicting file.
The replay mode applies to epoch-zero local storage for one database without an external source or owned lifetime replay.
Its dry run stages the rebuild temporarily and reports the prospective retirement without publishing replacement files.
`rtdb repair-checkpoint STORAGE REPLICA_LOG OUTPUT_PARENT BASE@SHA256 THROUGH@SHA256` rebuilds a stopped single local database in a separate directory.
Supply the original storage parent containing `v06`, the file named `REPLICA_LOG`, an existing output parent outside `v06`, and decimal block numbers with the SHA-256 digests of their exact published block files.
Stop the original database and keep its journal and storage stable for the duration of the command.
Select a known-good base whose bound table blocks and live and nascent primary trie files are intact.
Use `--base-storage PATH` to open the base from a separately retained `export-snapshot` directory, even if its original files have been removed from the serving store.
The target can have missing primary files if the original journal still contains the full interval from the base boundary through the target boundary, including any oversized payload objects referenced by the interval.
The command trusts the original local journal and the base's immutable primary trie contents.
This path applies to epoch-zero local storage with both checkpoints in the same replica journal and with all writes coming from RTDB.
The command publishes a separate `repair-…/storage` directory and reports its checkpoint digest, last transaction and original replica epoch.
Use that storage with a new empty local log configured at an epoch higher than the one reported.
The rebuilt catalog contains primary data, so derived indexes can be rebuilt by their normal maintenance paths.
`rtdb retain-repair-base STORAGE REPLICA_LOG EXPORTED_STORAGE BASE@SHA256` protects an independently exported repair base for epoch-zero local storage.
Stop all users of the original store and move a trusted export of its current block outside the serving storage root before installing it.
Supply the export's parent of `v06` as `EXPORTED_STORAGE` and use the original `REPLICA_LOG`.
RTDB checks both checkpoint publications, the exported table blocks and primary file inventory, and the replica boundary.
RTDB synchronizes the exported files and their directory entries before installing the bound.
Keep the detached export and original local journal available.
The native block collector preserves root catalogs, per-table block metadata, and offloaded replica payloads from the retained block onward, including after restart.
Export and retain a newer current block in the same journal to advance the bound and allow collection of older files.
An old target remains usable for `repair-checkpoint` while the active retention bound covers its interval.
`rtdb repair-checkpoint STORAGE REPLICA_LOG OUTPUT_PARENT THROUGH@SHA256 --retained-base --base-storage EXPORTED_STORAGE` selects the durable anchor from the original serving store.
The command checks the detached export against the stored block, digest and replica boundary while holding the journal lock.
The target remains explicit, so an operator can repair to any later retained cut in the same journal.
`compactor` opens the database catalog, follows replica progress, performs deterministic compaction and publishes results through the source log.
It opens no pgwire or Flight listeners and never claims leadership; the configured health listener remains available.
A separate writer must apply its source-log notifications before jobs are acknowledged.
Concurrent operation therefore requires a log provider that supports multiple source writers; the local log retains its exclusive writer lock.
`compactor.scanTieOrderFromNamingEpoch` optionally selects scan precedence for same-system-time ties, starting at the specified positive output naming epoch.
Choose a fresh epoch before enabling it. Stop existing compactor workers, use the exclusive `reset-compactor` workflow to publish that epoch, and start upgraded workers with the same setting before resuming compaction.
Keep the cutover setting when restarting workers in that epoch or any later epoch.
Compaction jobs below the cutover use the legacy byte ordering, including when legacy and upgraded workers coexist.
The pinned JVM command's inspected startup path creates no database compactor registrations, so this useful native command is an explicit behavioral difference awaiting runtime qualification.
The `read-arrow-file`, `read-arrow-stream-file`, `read-hash-trie-file`, `read-table-block-file` and `read-block-file` commands decode local artifacts without opening a node.
They accept a file path and an optional memory limit.
Inspection uses typed JSON rather than the JVM commands' Clojure object pretty-print format; this is an intentional diagnostic-output difference.
Arrow output contains the physical schema and positional typed values, preserving duplicate column names and floating-point bit patterns.
Arrow stream inspection reports the first batch, matching the reference helper's single-relation behavior.
Catalog output retains optional wire-field presence, including absent versus zero boundary term sequence, and retains opaque provider configuration bytes.
The passive inspection routines own their input and decoding reservations for the duration of the call, write output incrementally, and reject declared decoded allocations beyond the budget.
Tracing and cloud metric exporter construction and lifecycle paths are source-written; executable compatibility qualification remains pending.
The local-log `useInstantSourceForNonTx` option controls the writer's timestamp policy.
Exact Micrometer output and the configuration bounds' runtime allocation qualification remain pending.
No binary, listener, test or release artifact has been executed during Phase 1.
HTTP, TLS, configuration, CLI, metrics payload lifetime and server lifecycle test sources are written for Phase 2.

`XTDB_GENERATE_SERIES_END_EXCLUSIVE` is captured when node configuration is read.
A case-insensitive `true` enables exclusive SQL GENERATE_SERIES endpoints; all other values, including whitespace-padded values, leave the inclusive default.
RANGE remains exclusive.
The captured policy reaches prepared SQL, direct queries, static transaction expansion and transaction-time SQL resolution.
`tests/series_setting.rs` contains the environment decoding and shared node-options regression source.

=== Query execution diagnostics

Native `EXPLAIN ANALYZE` reports the peak accounted memory for each operator in `peak_memory_bytes` and the whole query's peak in `query_peak_memory_bytes`.
Operator scopes share the query limit, so their individual peaks can occur at different times.
The report includes optimized Arrow operators, and operator spans carry the same `cursor.peak_memory_bytes` measurements.
Query spans opened through pgwire, Flight SQL, and the embedded API carry the session's `application.name`.
Flight SQL defaults to `XTDB Flight SQL`, and Clojure queries opened on a native database default to `XTDB Clojure API`.
The OTLP exporter emits numeric and Boolean attributes with their corresponding wire types.

Native materialized CTEs reuse small results in memory.
When the result grows beyond the row threshold or its memory allowance (`materialized_memory_bytes`, 64 MiB by default), or the budget refuses a page, the binding writes one spill file, which counts against the query spill limit.
