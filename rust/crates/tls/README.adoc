= TLS key material

`KeyStore` and its borrowed `Identity` values are passive immutable key material.
Decoding completes on the caller and retains the caller's preallocated memory reservation.
Private PKCS8 buffers and temporary PEM encodings are zeroized on release.
Transport-specific certificate selection, TLS policy, and connection lifetime belong to the server or client adapter.
A transport that copies key material retains the store's reservation until those copies are released.
`IssuerNames` and `PemIdentity` are passive result owners with separate reservations for each conversion call.
Their borrowed slices remain valid until the result drops; copying those slices requires another reservation.
`ProtectedKeyStore` is an additive passive owner for Java keystore metadata and encrypted private-key entries.
It follows the deferred recovery boundary of OpenJDK 25.0.1 `KeyManagerFactoryImpl.X509` and `X509KeyManagerImpl`: loading exposes certificate metadata, and `ProtectedIdentity::recover` decrypts only the selected entry.
The decoder checks store integrity and decrypts encrypted certificate sections at load time, without retaining or checking a private-key password.
PEM material remains on the eager `KeyStore` path because Kafka's `DefaultSslEngineFactory.PemStore` decrypts PEM keys before initializing either key manager.
`ProtectedIdentity` is an immutable enumerated-alias binding, and multiple bindings may share one protected entry.
JKS bindings follow raw `Hashtable` enumeration followed by locale-English lowercase lookup, including aliases that resolve to a different stored entry or no private-key entry.
PKCS12 bindings follow normalized `LinkedHashMap` keys and replacement order, including secret-key entries that replace private-key aliases.
Their alias lookup uses pinned Unicode 16 full lowercase and Java's word-boundary final-sigma handling, preserving isolated JKS UTF-16 surrogate units.
PKCS12 friendly-name matching uses Java's simple character case comparison, which differs from full lowercase expansion.
Protected PKCS12 certificate chains compare Java canonical distinguished names and use the first matching issuer when no authority key identifier is present.
With an authority key identifier, an exact match uses its canonical encoded octets and the candidate's original subject-key-identifier extension bytes; otherwise the last matching issuer without a subject-key identifier is the fallback.
Expanded chains have separate retained reservations, and distinguished-name and identifier decoding reserve temporary scratch independently.
Adapters retain the protected store owner while using its metadata and reserve any additional copies separately.
`RecoveredKey` owns a separate reservation and zeroized PKCS8 buffer, so it can outlive the protected store.
Recovery checks Java `PrivateKeyEntry` algorithm equality, leaving proof of possession to the transport; it does not cache results or select another alias after failure.
The existing eager `KeyStore` API retains its public-key equality assertion and existing alias and chain behavior.
In particular, eager JKS identities use stored entries directly, and eager PKCS12 retains its previous Rust lowercase, encoded-name comparisons, issuer fallback order, and retained-chain expansion bound.
The protected API supplies the Java metadata and recovery semantics without changing those existing callers.
`DistinguishedName` is a passive immutable Java principal value with an independent reservation covering decoding and its retained canonical spelling.
It follows OpenJDK 25.0.1 `X500Name`, `RDN`, and `AVA` canonicalization: RDN order remains significant, assertions within an RDN are sorted, and repeated assertions are retained.
Standard RFC2253 keywords decode UTF8String and PrintableString values, including Java's Latin-1 decoding of PrintableString bytes.
Other value types and attribute identifiers retain their encoded value in hexadecimal form.
Escaping, ASCII space collapse and Java trimming precede pinned locale-US case conversion and Unicode 16 NFKD normalization.
Peer issuer hints and certificate issuer or subject names can therefore compare through the same canonical representation.
Malformed UTF-8 uses the shared Java replacement decoder.
The source regressions cover Unicode equivalence, encoding distinctions, RDN order, arbitrary-size OID arcs, BER framing and allocation ownership.

The codec reads JKS and PKCS12 stores, PEM trust certificates, and plain or encrypted PKCS8 PEM identities.
JKS store integrity and private-key protection use independent passwords.
A missing JKS store password skips the integrity check while retaining bounded framing checks.
Trust loading does not require decrypting JKS private keys.
JKS loading retains the last entry for each stored alias, comparing modified UTF-8 aliases as exact UTF-16 code-unit sequences.
Private-key identities retain their stored aliases and Java store enumeration order for transport-owned key-manager selection.
JKS enumeration follows `Hashtable` bucket traversal, collision insertion and resize order.
PKCS12 enumeration follows `LinkedHashMap` insertion order; replacing an existing alias retains its original position.
PEM identities carry no stored alias.
Certificates are validated while loading, and private keys are decrypted after duplicate entries have been replaced.
PKCS12 decoding preserves separate integrity and key passwords, multiple private-key bags, local-key identifiers, certificate chains, and Java trusted-certificate attributes.
BER constructed octets and indefinite lengths are bounded by the encoded input and a nesting limit.
PBES2 uses PBKDF2 with SHA-1/224/256/384/512 and AES or 3DES CBC.
Legacy PKCS12 SHA-1 protection supports RC4, RC2, and two- or three-key 3DES through the native OpenSSL provider.
MAC and password-based encryption iterations are capped at the pinned JVM's 5,000,000 limit.
Certificate-chain expansion beyond the retained material reservation fails before copying the next certificate.
A missing PKCS12 store password skips encrypted certificate sections and the integrity check, matching the JVM load contract.
Raw private-key and non-TLS bags are skipped; public-key-protected stores and unrecognized cryptographic algorithms fail explicitly.

The JKS source mapping is OpenJDK `JavaKeyStore` and `KeyProtector` at `jdk-21+35`.
The protected API was additionally traced against the pinned Temurin 25.0.1+8 `JavaKeyStore`, `PKCS12KeyStore`, `KeyStoreSpi`, `KeyStore.PrivateKeyEntry`, and `X509KeyManagerImpl` sources.
Registry configuration semantics are mapped to Confluent 7.8.0 `SslFactory`.
The server retains the existing `ServerConfig` keystore surface and pinned PostgreSQL TLS fixtures.
Independent pyjks vectors cover protected keys, Unicode and separate passwords, and tampering.
The PKCS12 derivation vectors are the published Stephen Henson vectors also used by Bouncy Castle `PKCS12Test` at `r1rv78`.
The native transport adapters select identities using the requested signature schemes, with the client adapter also matching the peer's acceptable issuer names.
Registry chain verification always runs; its configured endpoint-identification policy determines hostname verification.
Native crypto and system trust-store allocation bounds remain source estimates pending execution and measurement.
No codec or TLS test has been compiled or executed during Phase 1.

`StoreUse::Identity` requires at least one usable key and chain for the server.
`StoreUse::OptionalIdentity` decodes available keys for a client and permits an empty Java identity store.
An empty explicit Java truststore remains an empty trust set until handshake validation.
`tests/fixtures/empty.jks` is a version-two JKS header with zero entries and the SHA-1 integrity digest for password `12345678`.
The fixture was written directly from its wire framing; no JVM or project code was executed to produce it.
