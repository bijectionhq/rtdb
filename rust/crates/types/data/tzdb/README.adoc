= Native timezone data

`2026e.dat` is the unchanged `lib/tzdb.dat` from Eclipse Temurin `jdk-25.0.5+8`, the JDK the reference XTDB runs on.
The native build validates and bundles these bytes, and the process decodes them on first use, without executing Java.
All users of `rtdb-types` in one process, including embedded bindings and remote backends, share the decoded database.

[cols="1,3"]
|===
|Source |Eclipse Temurin `25.0.5+8-LTS` JDK (`IMPLEMENTOR_VERSION="Temurin-25.0.5+8"`, macOS aarch64)
|Source entry |`Contents/Home/lib/tzdb.dat`
|TZDB version |`2026e`
|TZDB SHA-256 |`a02e3a23d67255782b11ab81070902235ab564080f0f65ffe2a989cdaa86fe89`
|===

`LICENSE`, `ADDITIONAL_LICENSE_INFO` and `ASSEMBLY_EXCEPTION` are byte-identical to that JDK's `legal/java.base` directory.
The binary layout follows OpenJDK25 `TzdbZoneRulesCompiler`, `TzdbZoneRulesProvider`, `Ser`, `ZoneRules` and `ZoneOffsetTransitionRule`.
The decoder is native Rust and does not invoke those classes.

Set `RTDB_TZDB_PATH` at build time to bundle another OpenJDK format-version-1 file.
The build validates at most one MiB and records the bundled version and exact input SHA-256 in `rtdb_types::TZDB_VERSION` and `rtdb_types::TZDB_SHA256`.
Cargo tracks both the selection environment variable and the selected file for rebuilds.
Qualification against a JVM artifact requires its actual installed TZDB version and digest to match these values.

Set `RTDB_TZDB_FILE` in a process's environment to load another OpenJDK format-version-1 file in place of the bundled one, without a rebuild; this is RTDB's counterpart of replacing a JDK's `lib/tzdb.dat`, for instance with the output of Oracle's `tzupdater`.
The file is read once, on the process's first region lookup, under the same one-MiB bound and validation; a file that cannot be read or decoded fails region lookups with `xtdb/tzdb-unavailable` rather than falling back to the bundled rules.
The build-information report still names the bundled file.
