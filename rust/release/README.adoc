= Release packaging

Packaging source is written for Phase 2.
No image, binary, native library or JVM binding has been built or qualified.
`matrix.json` lists the intended Linux platforms and feature selections; each requires its own execution evidence before it is advertised as supported.
Local packaging includes the native server, offline configuration migrator, shared and static embedded libraries, C header and build metadata.
The all-backends selection enables Kafka, Kafka Connect, S3, Azure, GCS and PostgreSQL CDC in the server, migrator and embedded library.
It also includes the server's CloudWatch module and the migrator's matching capability check.
The pinned JVM selections are `standalone`, `aws`, `azure`, and `google-cloud`, each built by its matching `:docker:<variant>:shadowJar` task.
Standalone includes local storage and PostgreSQL CDC; each cloud selection also includes Kafka, Kafka Connect, and its own storage provider.
The reference has no combined all-backends image in this matrix.
The Java/Clojure adapter is built separately through the `:bindings:xtdb-rust-bindings` Gradle project with JDK 25.
Its test task receives the native library through `-Dxtdb.native.library=/absolute/path/librtdb_ffi.so`.

`build.py` requires the source completeness gate, a clean checkout and a committed Cargo lockfile for native builds.
The build driver owns its subprocess region and temporary artifact container; source manifests, selections and package records are passive values.
The Docker context comes from a Git archive of the selected revision, including the unchanged protobuf sources used by the Rust codecs.
The original JVM package uses the pinned reference's Gradle shadow-JAR task and Docker recipe, with an explicitly pinned runtime base.
The source checkout is checked for modifications before and after packaging.
Driver provenance captures the implementation revision and driver, matrix, Docker recipe, default configuration, and imported harness digests before building.
Those inputs are checked again before publication, including when the JVM source is a separate pinned checkout.
Every command writes separate stdout, stderr and process-status files; Gradle logs follow the repository's `xtdb-testing` review workflow.

Provide immutable repository digests for both base images.
For Rust, use an official Rust 1.94.1 Bookworm image and a Debian Bookworm runtime image for the selected architecture.
The recipe resolves additional build and runtime packages from a dated, signed Debian snapshot and records that timestamp.
For the JVM reference, use the pinned XTDB custom-JRE builder image and Alpine 3.23.7 runtime image.
Both must be passed by digest even when their human-readable tags are retained in the reference.
Container builds require Docker Buildx and a builder capable of the selected architecture.

[source,shell]
----
python3 rust/release/build.py --phase-two --engine rust \
  --variant local --platform linux/amd64 \
  --builder-image "$PINNED_RUST_BOOKWORM_IMAGE" \
  --runtime-image "$PINNED_DEBIAN_BOOKWORM_IMAGE" \
  --output build/release/rust-local-amd64-001

python3 rust/release/build.py --phase-two --engine jvm \
  --reference /absolute/path/to/pinned-reference \
  --variant standalone --platform linux/amd64 \
  --builder-image "$PINNED_XTDB_JRE_IMAGE" \
  --runtime-image "$PINNED_ALPINE_IMAGE" \
  --output build/release/jvm-amd64-001
----

The output directory must not exist.
`package.json` records the actual image ID, source revision and manifest, build arguments, platform, extracted artifact hashes and saved image archive hash.
The driver creates an owned container to extract artifacts, checks that jemalloc is loaded in the native image, and starts its build-information commands before removing it.
`rtdb --build-info` and `rtdb-config --build-info` report compiled version, full source revision, TZDB version and TZDB SHA-256, independently of runtime version overrides.
Packaging compares both reports with the archived source revision and selected time-zone bytes, and retains the reports and `tzdb.dat` alongside executable hashes.
Client, recovery and performance runners validate those same retained reports and bytes before starting a packaged server, and the client evidence importer repeats that validation after relocation.
Native packaging uses the bundled time-zone data by default; `--tzdb /absolute/path/tzdb.dat` copies an explicit replacement into the retained build context and image.
The build compiles that exact file through `RTDB_TZDB_PATH`; subsequent changes to the original path do not change the captured input.
The extraction owner captures the container's anonymous volume names, removes the container and volumes separately, and checks that each resource is gone.
`extraction-lifecycle.json` retains the primary failure and every cleanup failure; incomplete cleanup cannot publish a package manifest.
The image archive can be loaded using `docker image load --input` and selected by the recorded image ID.
Build success leaves qualification at `built_unqualified`; the package makes no compatibility claim.
Reproducibility requires rerunning the same selection and comparing artifacts; a recorded recipe alone does not establish byte-identical builds.

The default native image starts a local persistent node using `/var/lib/xtdb/log` and `/var/lib/xtdb/buffers`, upstream's standalone paths.
As in upstream's image, the working directory is `/usr/local/lib/xtdb` and the default command is `-f config.yaml`, so a configuration mounted at `/usr/local/lib/xtdb/config.yaml` is the one served.
A configuration mounted at `/etc/rtdb/config.yaml`, where earlier RTDB images read it, is still served when the upstream path holds the bundled default; the entrypoint says so on stderr.
Mount persistent storage at `/var/lib/xtdb` with ownership for UID/GID 20000; the image declares it as a volume, as upstream's does, so a deployment written for upstream's image keeps its data.
Earlier RTDB images used `/var/lib/rtdb/log` and `/var/lib/rtdb/storage`: when the default command finds either and neither of the new paths, the `rtdb-entrypoint` script serves them from there (with `/etc/rtdb/config-var-lib-rtdb.yaml`) and says so on stderr; move the data to the new paths to drop that fallback.
The image is built on Debian Bookworm (upstream's is Alpine) and runs as the user `rtdb` (upstream's is `xtdb`) with the same UID/GID 20000; that changes the shell, package tools and user name inside the container, not the node's behaviour.
As in upstream's image, the default root account trusts every connection unless `XTDB_PASSWORD` is set, in which case it requires that password; mount an explicit configuration at `/usr/local/lib/xtdb/config.yaml`, or select one with `-f`, for anything else.
The cluster configurations (`/etc/rtdb/cluster-default.yaml` and `/etc/rtdb/cluster-multi.yaml`) still read the root password from `RTDB_ROOT_PASSWORD`, which the Terraform module supplies, and still cache under `/var/lib/rtdb/cache`; they are RTDB's own deployment, with no upstream counterpart.
The image serves pgwire on 5432, Flight SQL on 3000 and health/metrics on 8080.
Its `HEALTHCHECK` polls `/healthz/alive` with `wget` after a fifteen-second start period, as upstream's does.
Logs go to stdout; `XTDB_LOG_FORMAT=json`, `XTDB_LOG_JSON_TEMPLATE` (a bundled `classpath:` template or a `file:` URI; a resolver RTDB cannot honour refuses startup) and `XTDB_LOGGING_LEVEL[_NS]` behave as upstream's.
The image uses jemalloc with a background purge thread, a one-second dirty-page decay and immediate release of muzzy pages.
`playground --port 5439 --flight-sql-port 3000` selects the original client-suite mode.
The process receives SIGTERM directly and drains its database and listener owners before returning.

An image built with Multi supports `deploymentAdminPrincipals` in the node's YAML.
Use `node --multi --config-env NAME` to load complete node YAML from a host-injected environment variable.
Supply either `--config-env` or the configuration file option.
List the exact authenticated principal names that may create, delete, export, restore or fork deployments.
The default configuration grants no deployment administration access.
Use the ordinary Flight listener with a verified password or client credential.
The `rtdb admin` client reads its authorization value from the file supplied through `--authorization-file`.
Multi nodes use private TCP port 3001 to forward admitted native writes to the selected writer.
The cluster catalog token authority authenticates and encrypts the peer requests and replies.
The peer port belongs on the node security group. Clients use the ordinary Flight listener.
On a durable Default Local installation, export selects a retained plain checkpoint whose published Basis matches the request.
Set `defaultCheckpointRestoreDirectory` to an absolute, provisioned Local directory to enable RestoreDeployment and ForkDeployment on that installation.
The selected destination first installs independent storage and its fresh incarnation. The Default catalog then orders its attachment.

Use the link:../conformance/README.adoc[packaged client runner] against the produced image and manifest.
Backend, fault, storage-interoperability, performance and rollback receipts remain separate release requirements in the matrix.
Use the paired `rtdb-config` artifact for link:../crates/config/README.adoc[offline configuration qualification] before cutover.
Its feature selection matches the server, and its extracted digest is retained alongside the server digest.
The command reads explicit configuration/environment/provenance files and prints a redacted report; it opens no node or backend and never grants cutover eligibility by configuration alone.

== Matrix execution evidence

link:input-contracts.adoc[Release evidence input contracts, version 1] lists every runner input, producer binding, artifact path root and CLI result contract.

`matrix_plan.py` expands both native Linux architectures, all eight native feature selections, and all four pinned JVM package variants.
It retains the original unit, integration, property, cloud, excluded-tag, client and scheduled SQL-logic selections.
The property lane requests 500 property and 1000 simulation iterations.
The nine scheduled SQL-logic directories remain separate invocations; the commented-out expression directory receives no coverage credit.
The embedded lane uses `:bindings:xtdb-rust-bindings:test --rerun-tasks -Dxtdb.native.library=...`, as declared by `settings.gradle.kts` and `bindings/jvm/build.gradle.kts`.
Its reports come from `bindings/jvm/build/test-results/test`.

`run_matrix.py --phase-two --plan PLAN.json --reference PINNED_CHECKOUT --output NEW_DIRECTORY` is the active invocation owner.
The plan names the retained `matrix.json` artifact and one explicit binding per expanded lane, preserving its exact `id`, `runner`, and `selection`.
Each binding supplies its own `inputs` and any required environment variable names.
The driver does not invent credentials, backend endpoints, native target inventories, expected assertions or mappings.
An artifact input is `{path, sha256, bytes}` relative to the plan; a predecessor input is `{from_lane, path}` beneath a declared, successfully verified dependency's output.
Missing inputs leave the lane unmet and independent lanes continue.
Cancellation propagates after the current invocation owner drains; it cannot become a successful missing-input receipt.

Native builds record Cargo's terminal successful build message and the exact declared package, target and feature selection.
Test execution must match the discovered names exactly, including ignored tests selected for execution.
The original Gradle task recordings are copied into one inventory bundle; duplicate task executions or conflicting discovery artifacts fail reconciliation.
The invocation manifest must explicitly bind every parameter/configuration identity to the ledger.
The link:../conformance/external-inventory.adoc[external evidence validator] handles retained client and SQL-logic invocations separately from JUnit descriptors.
A complete inventory and passing original assertions are different report fields, and both are required by the matrix.

Every lane retains its command logs, process receipts, input digests and complete output-file closure.
`verify_matrix.py` can combine workers only when they used the same exact plan, matrix bytes, implementation revision and pinned reference revision.
It checks every retained artifact and process drain again, requires native execution on the selected architecture, and rejects ambiguous duplicate successful lane receipts.
One architecture's result cannot stand in for the other.
Successful builds remain unqualified until every required lane is present.

Each compatible package pair has required link:../conformance/packaged-recovery-inputs.adoc[packaged recovery lanes] for every shared local, remote, log, and external-source capability.
These execute real writes, retained-tail and storage-only handoffs, acknowledged canaries, second-node/restart/fallback observations, and exact failed compaction publication against the selected images.
The existing Node-level recovery runner remains a separate local acceptance path.
Missing credentials, endpoints, or exact fault policies leave their selected scenarios unmet; local execution never stands in for remote evidence.
The shared packaged performance runner is described in link:../conformance/performance.adoc[matched performance evidence].
The new orchestration, observer, fixtures and regression tests are source-only and have not run.

== Cutover prerequisites

The link:input-contracts.adoc#_cutover_plan[version 1 cutover contract] defines complete partition and per-stage receipt fields.

`cutover_evidence.py PLAN.json REPORT.json` is a passive validator over an isolated preproduction rehearsal's retained evidence.
The plan must declare `evidence_scope: isolated_preproduction_rehearsal`.
It opens no node, uses no credentials, pauses no producer, changes no publication authority and grants no production authorization.
The operator or control plane supplies the observations and their evidence artifacts.
Artifact integrity cannot prove that a credential or writer lease was revoked; the report keeps that authority boundary explicit.

The validator requires independently pinned deployed JVM, native server, fallback JVM and migrator artifacts, a compatible configuration report, and every attached database partition.
Partition boundaries retain storage version/epoch, finalized block, distinct source and replica positions, transaction/system time, term, optional term sequence and opaque external-token digest.
An absent sequence remains distinct from zero.
The rehearsal receipts cover publisher/client inventory, protected retention, read-only shadow queries, pause/drain and ambiguous outcomes, JVM fencing, exact handoff, native restore, acknowledged canary read-back and second-node observation, restart, reverse recovery after the canary and partial compaction, native fencing, and exact fallback recovery within the declared budget.
Matching historical observations are mandatory.
The plan supplies an explicit assessment time; expired rollback deadlines remain expired in the report.
Canary, restart and fallback receipts must identify the same latest acknowledged partition/transaction boundaries, including external tokens.
Publisher completeness needs a retained runtime inventory tied to the configuration and authority; its absence remains unresolved.
A live deployment still needs its own controlled handoff after the rehearsal.
Neither a successful subprocess exit nor a compatible configuration alone satisfies these prerequisites.
