= Native RTDB verification

The references are an ordered history of complete batches and a captured read admission.
Each successful native read must agree with the history admitted by its basis.
Each durable acknowledgement must refer to an applied batch recoverable under the declared log and object-store contracts.
Maintenance steps must preserve that history's observable answers and the availability promised to live readers.

See link:../dev/doc/rtdb-formal-verification-design.adoc[the full design] and link:../dev/doc/rtdb-verification.adoc[the individual studies].
The first combined run is recorded in link:results/2026-11-21.adoc[the evidence ledger].
The inherited-read disposal study is recorded in link:results/2026-11-22.adoc[the next evidence entry].
The link:../dev/doc/rtdb-engine-verification-ledger.md[engine-wide catalog ledger] tracks the status of individual properties across the classic and multi-mode baselines.

== Independent derivations

Three isolated GPT-6.2 Astra designers received the same requirements brief, with the production source and the other reports withheld.
Each derived an ordered log of atomic batches, a private resolution prefix, a captured read horizon, and a representation boundary.
All three chose a separate system coordinate for time travel and an admission horizon for the ERASE cutoff.

[cols="1,2,2",options="header"]
|===
|Design |Choice that distinguishes it |Constraint or alternative it exposed

|A
|Publish a whole resolved batch with a version precondition.
Reject new admissions to horizons before the latest erase, while an already admitted handle may finish.
|A serial writer turn can replace validation of an optimistic resolver.
Without either rule, two conditional withdrawals can both read the same balance and commit incompatible decisions.

|B
|Serialize resolution and durable extension.
Expose fresh historical system reads under the current admission horizon.
|A private batch list suffices for read-your-writes.
A copied immutable answer can replace generation pins if copying and admission are atomic.

|C
|Append resolved facts, with a separate erase horizon and historical system basis for a fresh admission.
|Persistent interval maps can replace a history fold as the physical representation.
An old root alone cannot implement fresh retrospective erasure.
|===

The erase policy under study allows an existing pin to retain its admitted view.
A fresh read within the current captured view uses that view's ERASE cutoff even if its requested system coordinate predates the erase.
Reopening an old admission and requesting an old system coordinate must be distinguished in API contracts.
The study does not decide which old handles may be reopened, how long their storage must survive, or what physical destruction of backups promises.

== Mechanisms under comparison

[cols="1,2,2",options="header"]
|===
|Mechanism |Minimal observation it explains |Weakened variant and witness
|Ordered atomic publication
|Commit order resolves conflicts and the full batch is the public step.
|Publish only a debit or acknowledge a staged request, then crash.
|Validated or serialized resolution
|A resolved batch reads its own ordered prefix and an eligible committed basis.
|Two staged increments read zero before either is published.
|Bitemporal point resolution at an admitted horizon
|Corrections can change valid-time history, and ERASE masks older versions in fresh admissions.
|Treat ERASE as a delete whose scope starts at the query's system time, or merge across a write's origin.
|Stable admission and representation lifetime
|A reader holds either the bytes or the right to use a reachable generation.
|Retire one member of a shared file and delete the object while a sibling or reader still holds it.
|Durable root replacement
|Publication switches the recoverable representation atomically and retains its log suffix.
|Publish a root that has not reached durable storage.
|Search refinement
|Candidates can narrow work if the resolved result and top K remain the same.
|Admit a rank witness that fails a second predicate, or prune an unseen score tied at the cutoff.
|===

The choices here concern semantic transitions.
Replication providers, SQL, partition layouts, deletion protocols, index caches and query plans can spell or implement those transitions in different ways.
Retry identity is conditional on the product contract.
Protocol-level exactly-once effects require durable request identity and defined receipt retention.
Reclamation liveness requires readers to release or expire and storage calls to complete.
