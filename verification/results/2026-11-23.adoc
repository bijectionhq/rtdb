= RTDB kernel study results, 2026-11-23

== W1 · Successor trie collector and lease expiry

The collector contract in link:../../dev/doc/gc.allium[gc.allium] starts a new wait after a collector restarts or takes over.
The study covers a newly selected trie under that contract.
It compares an observation scoped to one collector with a weaker design that permits a predecessor's observation to carry over.

== W1 · Transaction catalog retention through the local ledger

The external transaction fixture uses two independent local store handles on the same filesystem ledger.
It checks that the floor stays at its previous position while the resolver owns the capture.
The writer stages a row and opens a cursor over the transaction's overlay.
The cursor retains the captured catalog after resolution returns, still reads the row, and releases the hold on drop.
The next attempt advances the floor.
A source transaction attempting to use the earlier capture then receives `rtdb.storage/catalog-not-current` from the store.
The overlay mutation fails at the assertion that the cursor retains the hold after resolution.

== W1 · Remote provider response drain

The production remote adapter admits a read into a child I/O region and consumes the response body within that operation.
The native fixture pauses the response stream, drops the caller and starts draining the parent region.
The catalog owner remains alive and the drained region refuses new provider requests while the response is pending.
Finishing the stream releases the owner and completes the drain.
All 15 remote lifetime tests passed against the production adapter and a controlled in-memory provider.
The fixture exercises the provider response stream in-process.

== W1 · Idle successor and exact hosted retirement

The two-node fixture uses the production replication and maintenance drivers, a shared in-memory journal and a shared filesystem catalog ledger.
The first node remains serving while the second wins a later replica term.
The successor compacts the trie and installs its retirement receipt while the predecessor still owns the earlier cursor.
Both files remain readable and the cursor returns its original result.
The cursor then closes and the successor completes the receipt with no further transaction or block.
The native control disables the idle retry and fails at the completion assertion.

== Replica payload retirement, streaming transfer and receipt retention

Ordinary serving cursors retain offloaded deliveries and the provider work they start.
Hosted versioned S3 retirement binds the exact object version to a certified replica position in the directory before advancing its replay frontier.
The dedicated trim protocol requires each known physical journal to sync a trim event, including when it previously acknowledged or applied that position.
The reaper matches the exact durable candidate, checks lineage references and retries removal of the same version.

The transfer fixture reconstructs two detached Arrow payloads over 8 MiB in total across source terms.
It rejects a modified source body and an unadmitted target object, activates and reseeds after losing the source key, reopens the durable directory, and advances intake from 501 to 502 after a subsequent oversized write.
The fallback reader requires the exact ordered v1 bootstrap digest.

Enrolled local archive keys support operation-only use, scheduled denial at the vault's observed deadline, and physical settlement on the original archive media after outstanding work drains.
The recovery test restarts the authority across an accepted schedule and confirms that an existing handle loses access while an independent archive remains readable.
Qualification of a fixed wall-time deadline for live SQL erasure depends on the serving and replay key custodians, active grants and backup scope.

The runtime separates ordered receipt time from source-clock observations and the transaction's temporal SQL label.
Ordinary, bounded, private and enrolled placed receipts can be retired by an ordered transaction without rewriting the surviving transaction history.
New user metadata is stored separately and projected against the installed retirement floor, including for historical SQL reads.
The same-history retry outcome and still-live rows survive retirement and restart.
Historical checkpoint, log, archive and backup copies retain separate physical custody obligations.
