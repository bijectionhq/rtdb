= RTDB Multi on consensus keepers, 2026-11-26

RTDB Multi ran on Logkeeper's keeper-hosted consensus streams through `journal-contract`, as described in link:../../dev/doc/rtdb-multi-consensus-keeper.md[rtdb-multi-consensus-keeper.md].
The first runs pinned Logkeeper `749260efc462527b31609f6a3d22ae240a9e8b04`, which adds `ConsensusJournal` and the `consensus-testing` local cluster.
The later runs pin Logkeeper `a2059e33063869675c726d3a3856cc362c684e74` on Logkeeper `main`, which adds keeper batches (`83fb9b9`), failure-domain placement (`3a299f5`), timed originals and transient-refusal retry (`a2059e3`).
All runs used one Apple M6 host with keepers and RTDB on loopback.

== Process qualification

`rust/bench/v1_consensus_keepers.py` started three voter keepers in distinct failure domains and a catalog keeper as separate `logkeeper keeper` processes, each with enrolled media and mutual TLS.
It started release `rtdb dev --multi` with `--multi-journal-url logkeeper-consensus://...` and drove rtdb.v1 Transact commits over TLS Flight with 5-second phases.
Each phase checked every key it acknowledged with rtdb.v1.TxStatus, which must return the exact original receipt.
Each recheck replayed every key acknowledged since the start.

=== Comparison with the stream Writer and the local journal

`rust/bench/v1_journal_comparison.py` ran the same release `rtdb dev --multi` and 10-second rtdb.v1 Transact phases on three journals: the local `FileJournal`, three stream keepers through the stream Writer, and the consensus keepers above.
Every acknowledged commit was verified with TxStatus.

|1 |238 |542 |571 |1.6 / 4.3

|64 |282 |6,750 |failed |–

At 64 clients one Transact returned "The write outcome is unknown. Recover it with TxStatus", so the consensus run stopped.
Before keeper batches the consensus journal stayed near 600 commits/s at every client count.
The causes and the fixes are in Logkeeper's design proposal: per-round WAL cost, four entries per replication message, and a flat 500 ms backoff on refused peer frames.

=== Comparison after the snapshot page-budget fix at `1e8a0df`

The 64-client failure above came from the keeper, not from RTDB.
A snapshot could rewrite at most 12 index pages since the previous one, and 256-record keeper batches change hundreds, so the snapshot failed and OpenRaft stopped the stream's group.
Logkeeper `67c0a16` removes that budget, sends 64 entries per replication message instead of 4, and retries a refused peer append after 5 ms doubling to 500 ms instead of a flat 500 ms.
Logkeeper `423854d` adds a WAL stall watchdog, 128 writes per WAL round and stream slot release on delete, and `1e8a0df` fixes a placement panic when the first two voters both become ineligible.
